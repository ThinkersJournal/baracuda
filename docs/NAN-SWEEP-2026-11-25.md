# NaN / infinity / tie sweep of baracuda-kernels (2026-11-25)

Written by the baracuda lane so the audit survives a restart. Evidence for each fix is in its PR body. Every fix below was proven on an RTX 4070 Laptop (sm_89) through `gpu-run`: the new test fails on the old code, passes on the new, and the existing tests of the area pass on the same build. The CI device job (`device-tests.yml`) was queued behind a serial ~5.5 h run all day: no PR claims it green.

## Conventions adopted (torch, and Fuel's CPU kernels where Fuel has one)
- A NaN is the largest value in orderings (sort, argsort, msort, topk); ties go to the lowest index; direction does not change that.
- cummax / cummin: NaN is sticky (the first NaN becomes the running value and stays).
- Max / Min reductions and `reduce_max_to` / `reduce_min_to` propagate NaN; the first-seen of `-0.0` / `+0.0` is kept; the `_to` identity is `-inf` / `+inf`.
- argmax / argmin: the first NaN wins, otherwise the first index of the extremum.
- Max / Min backward splits `dy` evenly across the tied positions of a group (`dy / count`, count clamped to 1; a NaN row gets zeros, torch gives NaN there). JAX (`_reduce_chooser_jvp_rule`) and torch (`scale_grad_by_count`) both split; the old header's "JAX convention = full dy" was wrong.
- Var / Std divisor `max(0, n - correction)` with IEEE division (NaN at `n == correction`, inf below).
- logsumexp / logcumsumexp: infinite inputs follow torch (`logsumexp [-inf, -inf] = -inf`, a +inf gives +inf, NaN is sticky).
- histogram ignores NaN and out-of-range values.

## Audited, passed
cumsum (NaN propagates; known deviation: a first element of `-0.0` comes out `+0.0`, torch keeps `-0.0`), cumprod, reduce Sum / Prod / Mean / Norm2 with NaN and inf (Norm2 of `[1e30, 1e30]` in f32 is inf, as in torch f32), Var / Std with NaN and inf, `unique_consecutive` (NaN each distinct, `-0.0` / `+0.0` one value), selective_scan NaN propagation (a NaN in `u` reaches only its own channel from that step on; BSZ 1, f32), bincount (integer input).

## Read only, left as is
logsumexp backward (`dy * exp(x - y)`, `inf - inf` gives NaN as in torch's own formula); scan log_cumsum_exp backward (same form).

## NOT reached
softmax / attention rows that are fully masked (all `-inf`) or hold a NaN or +inf (priority next: torch gives NaN for an all `-inf` softmax row, many attention kernels return 0; a convention question for Fuel's contract; report before changing), searchsorted, kthvalue, topk backward, sort backward, ssd_chunk_scan, scan / selective_scan backward kernels, f16 / bf16 NaN tests for scans and unique, Std backward at a zero divisor (formula changed with #438, not separately tested), the real `UniquePlan` composition (ROADMAP E0b), the sign of zero in scans.

## Stub scan (published family)
Two scans over `crates/*/src`: (1) the pattern `let _ = args.*; Ok(())`; (2) a `run` function whose `Args` struct output field is never named in its body (286 `fn run(.., args: XArgs)` against 298 Args structs with `TensorMut` outputs). Only `UniquePlan` (fixed) and `HistogramddPlan` (an API stub that declines at `select`) were found. Limits: only `run` functions whose parameter is named `args`; an output named but never launched is not caught; FFI-only paths without a Plan are not scanned.

## Reach
Fuel (`origin/main`, fuel-cuda-backend, fuel-cuda-dispatch, fuel-dispatch, fuel-ir) binds `TopkPlan`, `cumsum`, `arg_reduce` and `reduce_max_to`; it has no binding for the sort plans, `UniquePlan`, cummax / cummin, logsumexp, histogram or the max / min backward kernels (each grep had a positive control: `baracuda_kernels` is used in the same directories). Fuel's Var is a recipe and never binds the fused Var / Std kernels. No GHSA and no RustSec advisory for any item; any yank is the repo owner's.
