## Findings

1. **Error information is thrown away, and the negative-return mapping is lossy.** `check` (`lib.rs:29-35`) tests `rc.err.0 == 0` and, on failure, builds `Error::Status { status: rc.err }`; the second field of `CUfileError_t`, `cu_err: c_int` (the CUDA driver error, `-sys` `CUfileError_t`, read) is dropped, so a cuFile "CUDA driver error" status arrives without the CUDA code. `FileHandle::read`/`write` (`lib.rs:193-196`, `219-222`) turn a negative `isize` return `n` into `CUfileOpError(n as i32)`. From memory (**not checked**), cuFile returns `-errno` for POSIX failures and a negated `CUfileOpError` for cuFile failures, so the same `Error` type carries two number spaces, and the `as i32` cast truncates a 64-bit return on a 64-bit target with no check. `CUfileOpError` (in `-sys`) defines 6 constants (`SUCCESS`, `INTERNAL`, `DRIVER_NOT_INITIALIZED`, `IO_NOT_SUPPORTED`, `NOT_REGISTERED`, `INVALID_FILE_HANDLE`, counted in `-sys`), with every other code named `CU_FILE_UNRECOGNIZED`; cuFile's header defines many more (from memory, **not checked**). Decision before the freeze: carry `cu_err` (a second field, or a distinct `Error` arm) and split errno from cuFile codes; both change what `read`/`write` return, so they are breaking later. Severity: medium.
2. **Lifetimes are documented, not enforced, so drop order is the caller's problem.** Nothing ties `FileHandle`, `BufRegistration`, `StreamRegistration` or `BatchIO` to the `Driver` that must outlive them: the crate doc (`lib.rs:63-64`) says "Keep the returned handle alive for the lifetime of any I/O you do", and `Driver`'s `Drop` (`lib.rs:131-139`) calls `cuFileDriverClose` while handles can still exist. `FileHandle::register(fd: i32)` (`lib.rs:154`) is `unsafe` with the contract "`fd` must stay open for the lifetime of the returned handle" (`lib.rs:151-153`): a raw `i32` rather than a borrowed descriptor, so closing the `File` first (field order, scope end) is a use-after-close the type system cannot see; `FileHandle` has `Drop` (`lib.rs:230-241`) that deregisters the fd, which must precede the close. `BufRegistration` stores `ptr` only (`lib.rs:246-249`): no length, no accessor, and the device allocation it points to is a bare pointer, so freeing the buffer before dropping the registration is the same shape of hazard (contract at `lib.rs:255-258`). `read_async`/`write_async` take `stream: *mut c_void` (`lib.rs:336`, `365`) with "must be previously registered via `StreamRegistration`" (`lib.rs:328`) and no link to the `StreamRegistration` value. The `Driver` doc claims `cuFileDriverOpen` "is idempotent inside the library" while each `Driver::open` is matched by a close on drop (`lib.rs:54-56`); whether cuFile reference-counts open/close, so that dropping one of two `Driver`s closes it under the other, is **not checked**. Shapes to decide now, because the alternatives (a lifetime parameter `FileHandle<'a>`, `BorrowedFd<'a>`, `&'d Driver`) are all breaking later: (a) `register(fd: BorrowedFd<'_>)` behind `cfg(unix)`, or keep the raw `i32` and say so; (b) whether `Driver` is a proof token the other constructors take by reference. Severity: high (design), the current `unsafe` markers make it sound on paper.
3. **Offset and size types.** `read`/`write` take `size: usize`, `file_offset: i64`, `buf_offset: i64` (`lib.rs:182-188`, `208-214`) and return `Result<usize>`; the `-sys` `PFN_cuFileRead`/`Write` use `usize`, `i64`, `i64` and return `isize` (read). `i64` offsets match a signed `off_t` and are consistent with the async variants (`*mut i64`, `lib.rs:332-333`); no function rejects a negative offset or a `size` above `isize::MAX` before the call, and `Ok(n as usize)` (`lib.rs:198`, `224`) is safe because `n >= 0` was just tested. Inconsistencies a freeze would pin: `BufRegistration::register(.., flags: i32)` (`lib.rs:259`) against `StreamRegistration::register(.., flags: u32)` (`lib.rs:299`) and `BatchIO::submit(.., flags: u32)` (`lib.rs:421`), matching `-sys` (`c_int` for `cuFileBufRegister`, `c_uint` for the others, read; whether the C header does the same is **not checked**); `BatchIO::submit` does `params.len() as u32` (`lib.rs:427`) and `poll` does `events.len() as u32` (`lib.rs:445`), silently truncating above `u32::MAX` entries (unreachable in practice); `Driver::set_*_kb(size_kb: usize)` (`lib.rs:83`, `90`, `97`) and `version()` returns `i32` after a redundant `v as i32` on a `c_int` (`lib.rs:49`, harmless); `use_count() -> Result<i32>` (`lib.rs:384`). Recommendation: pick one flag type per concept and make the cast sites checked (`u32::try_from`). Severity: low-medium.
4. **Thread-safety is decided by accident of the field types.** `Driver` is `!Send + !Sync` on purpose (`_nonsend: PhantomData<*const ()>`, `lib.rs:58-60`), `BufRegistration` carries a `PhantomData<*const ()>` (`lib.rs:248`) that is redundant since `ptr: *mut c_void` (`lib.rs:247`) is already `!Send + !Sync`, and `FileHandle` (`lib.rs:143-145`), `StreamRegistration` (`lib.rs:289-291`) and `BatchIO` (`lib.rs:400-402`) are `!Send + !Sync` only through a raw-pointer field. The file has 0 `unsafe impl` (grep `unsafe impl`: 0; control: grep `unsafe` finds 36 lines), so nothing declares the intent and none of the five is shown `!Send` by a test (not compiled; no `assert_not_send`). Staying `!Send` is the safe default and loosening later is non-breaking, so this is "decide, do not rush": cuFile documents file handles as usable across threads (from memory, **not checked**), and a loader that wants to read from a worker thread cannot move a `FileHandle` today. Severity: low.
5. **`BatchIO`: doc drift, a vacuous `unsafe`, and `-sys` structs as public vocabulary.** The `poll` doc says "`timeout_ns = None` blocks indefinitely" (`lib.rs:435-436`) but the function has no timeout parameter (`lib.rs:441`); it passes `core::ptr::null_mut()` to the C call (`lib.rs:451`), so it always blocks until `min_nr` complete, and the "Wait for at least `min_nr`" contract does not reject `min_nr > events.len()`. `poll` is `unsafe fn` with the safety text "`events` is written up to its capacity" (`lib.rs:438-440`), which a `&mut [CUfileIOEvents_t]` already guarantees; the real hazard (the cookie pointers inside reaped events) is not stated. `submit`'s only contract is "Every entry's pointers must stay live until reaped" (`lib.rs:420`); a dropped `BatchIO` (`lib.rs:471-479`) with submitted-but-unreaped entries calls `cuFileBatchIODestroy` with I/O possibly in flight (from memory, behaviour **not checked**). The `pub use` (`lib.rs:393-395`) makes `CUfileIOParams_t` (8 public fields), `CUfileIOEvents_t` (3), `CUfileBatchHandle_t` (`*mut c_void` alias) and `CUfileOpcode` this crate's API. `CUfileOpcode` is not an enum: it is a `pub mod` of two `i32` consts (`READ = 0`, `WRITE = 1`) in `-sys`, while `CUfileIOParams_t::opcode` is a bare `c_int`, so nothing prevents an invalid opcode; the types have no `#[non_exhaustive]` and, being `repr(C)` with public fields, cannot gain a field without a breaking change. Recommendation: a typed `BatchEntry` / `Opcode` enum with `#[non_exhaustive]` built on top, keeping `-sys` types out of the safe signature, before the freeze. Severity: medium.
6. **`Driver::properties` takes an untyped pointer and the doc steers to a size nobody checked.** `pub unsafe fn properties(&self, props: *mut c_void)` (`lib.rs:110`) writes through a pointer whose type is never defined in the workspace (`CUfileDrvProps_t` appears only in the doc comment, `lib.rs:104`, `109`; grep over `crates/**/*.rs`: 2 hits, both there). The doc recommends "`std::mem::zeroed::<[u8; 64]>()` first and then reinterpret the bytes" (`lib.rs:105`); whether `sizeof(CUfileDrvProps_t)` is at most 64 is **not checked** and from memory the struct is larger, in which case following the doc is a buffer overflow in a function documented as safe-if-followed. Decision: either define the struct in `-sys` and return it by value, or delete the 64-byte advice; the signature `(*mut c_void) -> Result<()>` is not a shape to freeze. Severity: high if the size is wrong, otherwise medium.
7. **Struct layouts reached through the safe-ish path look wrong against the C headers (from memory, NOT CHECKED: the header is not in the repo).** `FileHandle::register` builds `CUfileDescr_t { handle_fd: fd, ..Default::default() }` (`lib.rs:158-161`), whose `-sys` layout is `handle_type: c_int`, `handle_fd: c_int`, `_reserved: [u8; 40]`, `fs_ops: *mut c_void` (read), putting `handle_fd` at offset 4 and `fs_ops` at offset 48. cuFile's `CUfileDescr_t`, as I remember it, is `{ type; union { int fd; void *handle; } handle; const CUfileFSOps_t *fs_ops; }`, in which the union is pointer-aligned, so `fd` would sit at offset 8 and `fs_ops` at 16. If that is right, cuFile would read `fd = 0` (the zeroed `_reserved`), not the caller's descriptor. Likewise `-sys` `CUfileIOParams_t` orders `mode, fh, opcode, cookie, dev_ptr_base, file_offset, dev_ptr_offset, size` (read), while the C struct, from memory, is `mode`, then a union holding `{devPtr_base, file_offset, devPtr_offset, size}`, then `fh`, `opcode`, `cookie`. The `-sys` doc admits the descriptor models "only the Unix-fd path" (`-sys` comment, read). `tests/read_write.rs:52-55` registers a real fd, but this lane has no record of that test having run on a device (state unknown). Action: compare both structs to `cufile.h` and to the on-device test result before any freeze of `FileHandle::register` and `BatchIO::submit`; this belongs to the `-sys` freeze but gates this crate. Severity: high if confirmed, **unverified**.
8. **Documentation drift: the README describes a different API.** README (53 lines, read) against `src/lib.rs`: (a) "`Driver::close`" (`README.md:11`): no such method (grep `Driver::close` in `lib.rs`: 0; control: `Driver::open` is found by the same grep style in the doc at `lib.rs:11`; the close is the `Drop` at `lib.rs:131`); (b) "typed `BufferRegistration`" (`README.md:17`): the type is `BufRegistration` (grep `BufferRegistration`: 0, `BufRegistration`: found at `lib.rs:246`); (c) "`BatchHandle::setup` / `submit` / `poll` / `cancel` / `destroy`" (`README.md:22`): the type is `BatchIO` and the constructor `BatchIO::new`; no `destroy` method, it is `Drop` (grep `-w BatchHandle`: 0; control: `BatchIO` found); (d) "typed `OpStatus` with `error_string` helper" (`README.md:27`): neither exists; the function is `op_status_error_string` (`lib.rs:120`); (e) the example imports `OpenFlags` and calls `FileHandle::open("dataset.bin", OpenFlags::ReadOnly)` and `fh.read(&mut buf, 0)` (`README.md:31-41`): `OpenFlags` is not defined (grep: 0), the only constructor is `unsafe FileHandle::register(fd: i32)` (`lib.rs:154`; `fn open` appears once in the file, in `Driver::open`), and `read` takes `(*mut c_void, usize, i64, i64)` (`lib.rs:182-188`); the example is not compiled (the README is not `include_str!`ed, grep `include_str` in the crate: 0, control: the umbrella `crates/baracuda` was not grepped, so only this crate is covered), so it would fail to build. (f) "Comprehensive across the cuFile API" and "pre-registering device or pinned host buffers" overstate a crate whose `Cargo.toml:4` calls it "scaffolding at v0.1"; `BufRegistration` documents device pointers only (`lib.rs:243-244`, `255-258`). (g) The crate doc "On Windows and macOS every API returns `UnsupportedPlatform`" (`lib.rs:4-7`) holds for functions that call `cufile()`, which returns `UnsupportedPlatform` off Linux (`-sys` `:409-414`, read); the types are not constructible there. Fix: rewrite the README against the code. Severity: medium (docs only).
9. **`#[non_exhaustive]` and public enums.** The census column is 0 on all 31 rows (summed by me from `items.tsv`) and the source agrees: `lib.rs` has 0 `#[non_exhaustive]` (grep) and 0 `pub enum` (grep; control: `pub struct` matches 5, the five structs). All five public structs have private fields, so adding a field is non-breaking and `non_exhaustive` is not needed on them. `Error` is `baracuda_core::Error<CUfileOpError>` (`lib.rs:25`), a type owned by `baracuda-core` (its own review covers the attribute). The open-ended vocabulary is `CUfileOpError`, a `#[repr(transparent)] struct CUfileOpError(pub i32)` with associated constants in `-sys`: new codes are non-breaking by construction, and `non_exhaustive` is irrelevant. The `-sys` types re-exported by the `pub use` are the exception (finding 5). Verdict: no `non_exhaustive` is missing in this crate's own source.
10. **Unsafe accounting.** `src/lib.rs` has 36 lines containing `unsafe` (grep -c), of which 26 contain `unsafe {` (blocks), 10 are `pub unsafe fn` (`properties`, `FileHandle::register`, `read`, `write`, `BufRegistration::register`, `StreamRegistration::register`, `read_async`, `write_async`, `BatchIO::submit`, `BatchIO::poll`); 10 `# Safety` doc sections (grep -c; each unsafe fn has one, `write` and `write_async` by reference "Same as [`Self::read`]"); **0 `SAFETY:` comments** on the 26 blocks (control: the same grep style finds the 36 `unsafe` lines); 0 `unsafe impl`. 5 `impl Drop` (grep -c): all of them ignore the status of their cuFile call, and 4 of 5 silently skip the release when `cufile()` fails, so a failed lookup leaks the registration with no signal. Only `FileHandle`'s `Drop` guards a null handle (`lib.rs:232-234`); `BatchIO::new` and the others cannot reach `Drop` with a null handle on a `Ok` path. Safe functions with unsafe bodies (`version`, `Driver::open`, `set_*`, `use_count`, `BatchIO::new`, `cancel`) call plain `extern "C"` pointers with no pointer arguments from the caller, which reads correctly. `FileHandle::use_count` and `BatchIO::cancel` are safe while operating on handles that a `Drop` may free: not reachable because each takes `&self`. ## Recommended order

1. Finding 7 (struct layouts vs `cufile.h` and an on-device run) with the `-sys` freeze, since a wrong offset invalidates `register` and `submit`; finding 6 (`properties` typed struct or removed advice) in the same pass.
2. Finding 2 (lifetime shape: `BorrowedFd`, `Driver` token) and finding 1 (carry `cu_err`, split errno from cuFile codes): both change signatures, so they must precede the freeze.
3. Findings 5, 3, 4 as freeze decisions: typed `BatchIO` entries and a real `poll` timeout, one flag type, `Send`/`Sync` intent stated.
4. Findings 8, 9, 10, 11, 12 as cleanup: README rewritten against the code, `SAFETY:` comments, `baracuda-types` and `thiserror` removed after a build check, more tests.

Nothing in this review was built, run, or checked against NVIDIA's documentation or headers: findings 1 (the errno split, the code list), 2 (cuFile reference counting), 3 (flag types against the header), 4, 5 (destroy with I/O in flight), 6 (the struct size) and 7 (both layouts) rest in part on cuFile behaviour recorded here as **not checked**; findings 8-12 are read from source and greps with the controls stated, except the umbrella crate, which was grepped only for `cufile`.
