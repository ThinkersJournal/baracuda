## Findings

1. **`Table::column` / `columns` return non-owning views that nothing ties to the `Table`: a safe use-after-free.** `Column { raw, owned: bool }` (`lib.rs:82-85`); `Table::column(&self, ..)` returns `Column { raw: col, owned: false }` (`:206-209`) with no lifetime, and `Table::columns` returns a `Vec<Column>` of them. The doc says "drop them before dropping the `Table`" (`:217-218`), a rule the type system does not enforce: `let c = t.column(0)?; drop(t); c.len()` passes the freed table's column pointer to libcudf from safe code (read, not run). The same holds for `Column::as_raw`/`Table::as_raw` (safe fns returning raw pointers, `:118`, `:213`; harmless to read). Whether libcudf keeps the column alive independently of the table is **not checked**; the crate's own doc says it must not outlive it. A borrowed view type (`ColumnRef<'t>`, or `Column<'t>` with a lifetime and an owned variant) fixes it, but it changes the signature of every `Column` item, so this is the first freeze decision. The `owned` flag also makes one type carry two ownership models; the `Drop` (`:124-137`) is the only place that reads it.
2. **`Column::new_empty` produces a value that nothing can use.** It allocates "`size` elements of `type_id`", "values are uninitialized until written" (`:88-89`), but the crate has no way to write to a column and no way to build a `Table` from columns: the `-sys` crate declares `cudfTableCreate` (`-sys` `lib.rs:189`, `:281`) and the safe crate never names it (grep for `cudf_table_create` in `baracuda-cudf/src/lib.rs`: 0 hits; control: `cudf_column_get_size` is found in the same file by the same kind of grep, 1 hit; in `-sys` the grep for `cudf_table_create|cudfScalar_t` finds line 281 and the unused `cudfScalar_t` alias at `:40`). The crate doc advertises "hand-roll empty `Column`s of any supported `TypeId`" (`:6-7`) as a feature. There is no `Table::new(columns)`, no `Column::from_slice`, no `data`/`null_count` getter, so the whole safe surface is: read file, count, get column type and size, write file. Adding these later is non-breaking, but a `Column` with only type and length is easy to freeze by accident; decide whether `new_empty` stays.
3. **`Table` is not tied to the library and has no `Send`/`Sync` statement; the path helper is triplicated.** `Table` and `Column` hold a `*mut c_void`, so both are `!Send + !Sync` by the auto-trait rules (not compiled, no `assert_not_send` test in `tests/`; control: `public_types_impl_debug` is the only trait-bound test, `tests/cudf_smoke.rs:128-134`). Whether libcudf tables can move between threads is **not checked**; a data-loading pipeline will want it either way, and it cannot be added from outside later. `from_csv`, `from_parquet`, `write_parquet` repeat the same 5 lines (`to_str`, `Error::Path`, `CString::new`) at `lib.rs:150-154`, `:163-167`, `:176-180`; the error `Error::Path(String)` holds a lossy `display()` of the path, not the path (`:153`). `from_csv` takes no options (delimiter, header, dtypes) and `from_parquet` none (columns, row groups); the `-sys` PFNs take only a path (`-sys:213-223`), so adding options later means a new function, not a changed signature: `from_csv` would then stay as the "defaults" entry point. README claims "CSV reader / writer" (`README.md:20`): there is a CSV reader and no CSV writer (grep for `write_csv|WriteCsv` in `crates/baracuda-cudf*/src`: 0 hits; control: `write_parquet` is found).
4. **`TypeId` is the `-sys` enum, closed, written through an FFI out-pointer, and shares a name with `std::any::TypeId`.** `pub use sys::cudfTypeId_t as TypeId` (`lib.rs:40`); the enum is `#[repr(i32)]` with 29 variants (`-sys:45-106`, `Empty = 0` .. `Struct = 28`), 0 `#[non_exhaustive]` (grep `non_exhaustive` in `baracuda-cudf-sys/src/lib.rs`: 1 hit, `finish_non_exhaustive` at `:254`, a different thing; control: the pattern is found, so it reaches that file; the safe crate: 0 hits). `Column::type_id` initialises `let mut t = TypeId::Empty;` and passes `&mut t` to libcudf (`lib.rs:113-114`): if the library writes a value not in the 29 (cudf adds type ids over time, from memory, **not checked**) that is an invalid enum in safe Rust, undefined behaviour. This is the same shape as `r6/nvml.md` finding 3. `Column::new_empty` also passes the enum by value into C. Decision: read into an `i32` and convert with an `Other(i32)`/`Unknown` arm, `#[non_exhaustive]`, in the `-sys` crate; the variant names `Timestamp_Days`, `Duration_Nanoseconds` etc. (10 of the 29 have an underscore, `-sys:73-91`) break Rust naming, which is hard to change after the freeze (the `-sys` crate has `#![allow(non_camel_case_types, non_snake_case, non_upper_case_globals)]` at `-sys:19-24`; whether the variant names need it was not compiled). The name `TypeId` collides with `std::any::TypeId` in glob imports; `Column::type_id()` also shadows `Any::type_id` for any caller with `Any` in scope (not compiled). All 29 variants carry the placeholder doc "`X variant.`" (read at `-sys:48-105`; not grep-counted).
5. **`Error` has a different shape from its siblings, and its doc names a variant that does not exist.** `Error` is a crate-local `#[derive(Debug, thiserror::Error)]` enum with 4 variants (`lib.rs:43-57`): `Loader(#[from] baracuda_core::LoaderError)`, `Status(cudfStatus_t, &'static str)`, `Path(String)`, `Nul(#[from] NulError)`. `baracuda-nvml` uses `baracuda_core::Error<nvmlReturn_t>` (`r6/nvml.md` finding 2), so `baracuda_core::Error<S>` is the portfolio convention and this crate does not use it (grep `baracuda_core::Error` in `baracuda-cudf/src`: 0 hits; control: `baracuda_core::LoaderError` found at `lib.rs:47`). Consequences: (a) `Status`'s second field is `status.description()` (`:66`), a `&'static str` that is a function of the first field, redundant (the `Display` prints both, `:49`); (b) the crate has `Path` and `Nul`, which core's `Error<S>` lacks, so a unification is not a drop-in; (c) the crate doc says missing symbols map to `Error::FeatureNotSupported` (`:12`) and README says the loader "fails fast with a clear error on Windows / macOS" (`README.md:30-31`): the crate's `Error` has no `FeatureNotSupported` variant (the only `FeatureNotSupported` hits in the crate are that doc line, `grep FeatureNotSupported`: 1 hit; in core it is a variant of `Error<S>` and `BaracudaError` at `error.rs:140`, `:190`, not of `LoaderError`), and a missing symbol arrives as `Error::Loader(LoaderError::SymbolNotFound { .. })` (`baracuda-core/src/error.rs:36`). So the headline forward-compatibility sentence is wrong, and it is wrong for the one behaviour (new libcudf, old crate) the doc is selling. (d) The enum is **not** `#[non_exhaustive]` (0 hits in the crate), so adding a variant (a `Utf8` arm, an I/O arm, a `FeatureNotSupported`) is breaking; with the `Path`/`Nul` pair being host-side validation errors that will grow (options, schema), this is the most important cheap fix. (e) Not `Clone`/`PartialEq`, like the other crates. `README` says cuDF "is Linux-only" yet the loader has Windows candidates (`-sys:237-241`) and `platform::versioned_library_candidates` generates `.dll` names; the README claim and the code disagree.
6. **`Result`-returning getters that cannot fail except by the loader.** `len`, `is_empty`, `type_id`, `num_columns`, `num_rows` each call `sys::cudf()?` (a `OnceLock` lookup after the first call) and a status-checked FFI. `Column::is_empty` is `Ok(self.len()? == 0)` (`:106-108`), so it has the failing path of `len`. This is deliberate (every item is a possible C call), but `Result<usize>` for a length makes iterating `for i in 0..t.num_columns()?` awkward and is a freeze commitment; the alternative (cache the length at construction, return plain `usize`) is not available later without a breaking change. `Table::columns` is O(n) FFI calls and 1 `Vec`; `columns()` repeats `num_columns` per call, fine. There is no `Drop` error surface: both `Drop`s ignore the status with `let _ = f(self.raw)` (`:133`, `:235`), the same as other crates; `Column::drop` is also silent when `sys::cudf()` fails (`:129-131`), which leaks the handle.
7. **`version()` returns `i32` documented as "a packed integer".** `lib.rs:70-76`; the test asserts `v >= 22_00_00` and the comment says "an integer such as 25_06_00" (`tests/cudf_smoke.rs:157-159`), so the encoding is `YY_MM_PP`-style decimal, written in a test comment but nowhere in the public doc. That is a contract the crate needs to state (or replace with a `Version { year, month, patch }` struct) before the freeze. The `-sys` signature takes `*mut c_int` (`-sys:168`), so `i32` is faithful. Whether libcudf's C ABI reports it that way is **not checked**.
8. **A `stable` classification for a crate that is a skeleton against a proposal.** `Cargo.toml:4` says "Safe Rust API skeleton"; `-sys` says "Status: skeleton ... the symbol names below reflect the RAPIDS **libcudf_c** proposal" (`-sys:8-15`); `-sys` `cudf_candidates` tries `libcudf_c.so`/`cudf_c.dll` and versioned names for majors 25, 24, 23, 22 (`-sys:230-241`). If no shipped libcudf exports `cudfReadCsv`, every one of the 23 items returns `LoaderError` on every machine. Whether it does is **not checked** and cannot be settled by reading source. Decision for the PM: freeze these 23 as `stable`, mark the crate `experimental`/pre-freeze in the census, or hold it out of the freeze until at least one real libcudf (or the documented C shim) has been exercised on the device runner. The `device-tests` tests exist (3, finding 9) but there is no record in the tree that any of them has run against a real libcudf (not checked; the tests skip through `require_optional!`).

## Recommended order

1. Finding 1 (borrowed `Column` view tied to `Table`) and finding 2 (what `new_empty` is for): both change the shape of `Column`, the crate's central type.
2. Finding 5 (the `Error` shape: use or deliberately depart from `baracuda_core::Error<S>`, `#[non_exhaustive]`, drop the redundant `&'static str`, fix the `FeatureNotSupported` doc) and finding 4 (`TypeId`: out-pointer enum UB, naming, `#[non_exhaustive]`), the latter together with the `-sys` freeze.
3. Finding 8 (is a skeleton against a proposal a `stable` freeze?), a PM decision that can reorder the rest: if the crate leaves the freeze, findings 1 through 7 become cleanup.
4. Findings 3, 6, 7, 9 as decisions or cleanup: `Send`/`Sync` argument, options-less readers, `Result` getters, `version` encoding doc, `SAFETY` comments, tests for the 7 uncovered `Table` methods, README corrected (no CSV writer, Windows claim, `FeatureNotSupported`).

Nothing in this review was built, run, or checked against RAPIDS or `libcudf`: findings 2, 3 (counts), 5 (a, b, d), 6, 7 (test comment), 9 are read from source and greps with the controls stated; findings 1 (libcudf's ownership of a column view), 3 (thread-safety), 4 (new type ids), 8 (whether any shipped libcudf exports these symbols) rest in part on library behaviour recorded here as **not checked**, and the `-sys` item "the loader does or does not fail on Windows" was read from the candidate list, not tested.
