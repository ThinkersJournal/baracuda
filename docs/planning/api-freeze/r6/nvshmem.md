## Findings

1. **Nothing ties `SymmetricBuffer` or `Team` to the `Context` that makes them valid, so safe code can free after finalize.** `Context::finalize(&mut self)` is a safe fn (`lib.rs:321-329`) and `Context`'s `Drop` finalizes (`332-343`). `SymmetricBuffer::new` is an associated fn on its own (`457`) and `Context::malloc` (`159`) returns a buffer with no lifetime or borrow of `&self`; `Team::split_strided` (`365`) likewise. So `let ctx = Context::init()?; let b = ctx.malloc::<f32>(8)?; drop(ctx);` is accepted by the type system, and `b`'s `Drop` (`504-515`) then calls `nvshmem_free` after `nvshmem_finalize`. The same holds for `ctx.finalize()?` followed by any `put`/`barrier_all`. The doc says "After this no further NVSHMEM calls are valid" (`320`); that is a safe API whose misuse is documented rather than prevented. Whether NVSHMEM's behaviour there is UB or a clean error is **not checked**. In addition `Context` has no singleton guard: `init` is safe and "Call exactly once per process" (`91`) is prose only, and `Context` is `Send + Sync` by the auto-trait rules (fields `i32, i32, bool`, `73-77`; not compiled), so two threads can each hold one. Decision before the freeze: borrow `&'ctx Context` in `SymmetricBuffer` and `Team` (breaking later), or make `init`/`finalize` `unsafe`, or add a process-global once-guard, or document the whole crate as experimental (finding 9).
2. **The stream-ordered calls let the buffers be dropped while work is in flight.** `put_on_stream` / `get_on_stream` (`266-290`, `293-317`) borrow `dest` and `src` only for the call; the enqueued operation outlives the borrow. A caller can drop the `SymmetricBuffer` (which runs `nvshmem_free`, `512`) before the stream has executed the transfer, with no `unsafe` anywhere in their code. The doc says "pair with `quiet`" for remote completion (`264-265`) but says nothing about keeping the buffers alive. Same shape as the sibling-crate stream findings in earlier R6 reviews; whether `nvshmem_free` implicitly synchronises is **not checked**. Fix by documenting a stream-synchronise-before-drop contract, or by taking the buffers by a stream-tied guard (breaking later). Blocking `put`/`get` (`214`, `240`) do not have this problem on their face.
3. **Other safe-fn contracts that are prose only.** (a) `put`/`get` and the stream forms `assert!` the count against `dest.len()` and `src.len()` (`221-224`, `247-250`, `274-277`, `301-304`) and panic, not `Result`, on violation (4 `assert!`, 1 `expect("size overflow")` at `462`; grep `assert!\|expect(`: 5 hits, control: the same grep finds each of the five lines listed). `pe: i32` is not validated against `n_pes` or `>= 0` (`219`, `245`, `271`, `298`); what NVSHMEM does with an out-of-range PE is **not checked**. (b) `dest` and `src` may be the same `&SymmetricBuffer<T>` (self-put with overlapping ranges), allowed by the types. (c) Collective calls (`malloc`/`SymmetricBuffer::new` at `457` "every PE must call it with the same `len`", `barrier_all`, `split_strided`, `destroy`) are safe fns whose contract is "every PE calls"; a violation hangs or aborts rather than corrupting memory, from memory and **not checked**, so `unsafe` is not warranted but the docs on `barrier_all` (`171-177`), `sync_all` (`189`), and `split_strided` (`365`) do not say "collective". (d) `SymmetricBuffer::as_mut_ptr(&self)` (`499`) returns `*mut T` from a shared borrow and `put` writes through `dest: &SymmetricBuffer` (`229`): the buffer is shared-mutable by design (a remote PE writes it anyway), harmless for raw pointers, but a decision: freeze `&self` or move to `&mut self` for the receiving side.
4. **`Team` is `Copy` and `destroy(self)` does not consume it.** `#[derive(Copy, Clone, Debug, Eq, PartialEq, Hash)] pub struct Team(nvshmem_team_t)` (`350-351`). `destroy(self)` (`413-422`) takes `self` by value, which for a `Copy` type leaves the caller's copy usable, so a destroyed team can be reused (and `Team` values from `split_strided` can be destroyed twice) with no `unsafe`. The `Team` doc requires a manual `destroy` (`347-349`); there is no `Drop`. And the doc says destroying a predefined team "is a programmer error and is rejected here" (`411-412`), but the code returns `Ok(())` (`414-417`): the doc and the code disagree (an Ok, not a rejection). Decision: drop `Copy` for created teams (a separate owned `TeamHandle` or a `Drop`), or document `Team` as a plain handle and rewrite `destroy`'s doc to "no-op on predefined teams". The `my_pe`/`n_pes`/`translate_pe` returns of `-1` (`387`, `403`) are raw C sentinels in an `i32`, not `Option`; `Team::my_pe` returning `Result<i32>` with `-1` for non-member while `split_strided` uses `Option<Team>` for the same condition is inconsistent. Both are freeze commitments.
5. **Sizes, panics, and the synthetic error.** `SymmetricBuffer::new` panics via `expect` on size overflow (`460-462`) where every other failure is a `Result`; the OOM branch returns `Error::Status { status: nvshmemResult_t(1) }` (`468-470`), a hard-coded invented status code (the `-sys` crate defines `Success` at `baracuda-nvshmem-sys/src/lib.rs:145`; whether it names a code for 1 was not read). A zero-length buffer is accepted: `nvshmem_malloc(0)` may return null and `Drop` skips null (`506-508`), so `as_ptr()` on an empty buffer can be null; what NVSHMEM returns for 0 is **not checked**. `SymmetricBuffer<T: DeviceRepr>` carries the bound on the struct itself (`439`), so it can never be relaxed without a breaking change. `Drop` swallows all errors (`509-513`, `337-341`), same convention as other crates. The doc says `SymmetricBuffer` is not `Send`/`Sync` (`437-438`); that follows from the `*mut c_void` field (auto-trait rule, not compiled) and no compile-fail or `assert_not_send` test pins it (grep `Send` in `tests/`: 0; control: grep `Team` in the same files finds 8 hits). The claim that NVSHMEM is "bound to the PE's owning thread" is **not checked**.
6. **Shapes that are hard to change after 1.0.** (a) `Context::init_with_attr(flags: u32, attr: *mut c_void)` (`115`) is `unsafe`, untyped, and documents `flags` as "pass flags" with no vocabulary; it is the only way into a unique-id init, so the safe `UniqueId` has no safe consumer (finding 7). (b) `put`/`get` live on `Context` and take `&self` without using it (`214-262`: `self` is never read in those bodies; the loader `nvshmem()` is called directly), so `Context` is a proof token that nothing checks, the same pattern as `Nvml` in the R6 `nvml` finding 2; moving them to `SymmetricBuffer` methods later is breaking. (c) `put`/`get` take `count` from offset 0 only: no offset or sub-range, so a partial or strided transfer cannot be expressed (additive later via new methods, non-breaking). (d) `my_pe`/`n_pes`/`pe` are `i32` (`135`, `141`, `219`), mirroring C; a `usize`/newtype is a breaking change later. (e) `Context::version(&self)` (`146-153`) and the free `version()` (`556-563`) have byte-identical bodies and `Context::version` never reads `self`; one of the two is redundant, and the free one is the capability probe the docs describe (`553-555`). (f) `world()` (`165`) returns `Team::WORLD` and duplicates the const. (g) `Context::my_pe`/`n_pes` are cached at init (`133`, `139`) while `Team::my_pe`/`n_pes` query the library and return `Result`; fine, but the asymmetry is permanent.
7. **`UniqueId` is a dead end in the safe layer, and exposes a `-sys` struct.** `UniqueId::new` (`534-540`), `as_raw` (`543`), `from_raw` (`548`) wrap `nvshmemx_uniqueid_t` (`#[repr(C)]`, public fields `version: c_int`, `internal: [c_char; 124]`, read at `baracuda-nvshmem-sys/src/lib.rs:108-113`), and the doc admits the id cannot be wired into init through this crate (`524-527`). So the safe type has no safe consumer; its layout (128 bytes, the `-sys` struct's public fields) becomes this crate's API via `as_raw`/`from_raw`, and `Team::as_raw` (`426`) likewise exposes `nvshmem_team_t(pub i32)` (`-sys:70`). `UniqueId` derives `Copy`, `Debug` (a manual `Debug` on the `-sys` struct elides `internal`, read). Whether `nvshmemx_get_uniqueid` may be called before `init` is **not checked**. Decision: keep `UniqueId` outside the freeze until a safe init path exists, or add that path.
8. **`#[non_exhaustive]`: nothing is needed, and the census is right.** `src/lib.rs` has 0 `#[non_exhaustive]` (grep `non_exhaustive`: 0; control: grep `pub struct` finds the 4 structs at 73, 351, 439, 530) and 0 `pub enum`. The 4 public structs all have private fields (`Context` `73-77`, `Team(nvshmem_team_t)` `351` tuple-private, `SymmetricBuffer` `439-443`, `UniqueId(nvshmemx_uniqueid_t)` `530`), so adding fields is non-breaking and `non_exhaustive` would add nothing. The `non_exhaustive` census column is 0 for all 40 rows, consistent with the source. `Error` is `baracuda_core::Error<nvshmemResult_t>` (`48`), a type alias of an enum with 3 variants (`Status`, `Loader`, `FeatureNotSupported`; read, `baracuda-core/src/error.rs:123-145`; the R6 `core` review records it as `non_exhaustive`, not re-checked here), so the error enum is open. `nvshmemResult_t` and `nvshmem_team_t` are transparent newtypes over `i32`, not enums (read), so a value outside the named constants is not UB, unlike the enum out-pointers in R6 `nvml` finding 3.
9. **Should this crate be outside the freeze?** Recommendation, for a PM ruling: **yes, treat it as experimental, like `baracuda-optim::distributed` in `README.md` item 3a** (read at `docs/planning/api-freeze/README.md:36`: experimental, outside the freeze, census still says `stable` because the classifier has no per-module class). Evidence: (a) it is behind a default-off feature in `baracuda-kernels` (`Cargo.toml:213-219` `nvshmem = [...]`, comment "default OFF" at 102 of the workspace `Cargo.toml` too) and is **not** in the `baracuda` umbrella (grep `nvshmem` in `crates/baracuda/Cargo.toml` and `crates/baracuda/src`: 0 hits; control: the same dir has `nccl` at `src/lib.rs:22` and `nvml` at `:27`); (b) `baracuda-kernels/src/lib.rs` mentions it once, in a doc line (`:57`, grep `nvshmem`: 1 hit), and no code in the repo calls `baracuda_nvshmem::` (grep over `baracuda-kernels/src`: 0; control: the grep on `nvshmem` in that dir finds the doc line), so no in-repo consumer has exercised the API shape; (c) it is a Tier 1 surface that leaves device-side NVSHMEM out (`lib.rs:11-28`) and has no safe `UniqueId` init (finding 7); (d) findings 1, 2 and 4 are soundness gaps whose fixes (lifetime ties, `Team` ownership) are breaking. The `class = stable` on all 40 rows therefore overstates; read them as not frozen until the PM rules. This is not a class change: nothing was regenerated.

## Recommended order

1. Finding 9 first: a PM ruling on experimental status, because it sets how much of the rest is a freeze blocker. If experimental, state it in the crate doc and `Cargo.toml` description and in `README.md` item 3a's list.
2. Findings 1, 2 and 4 together (lifetime ties for `SymmetricBuffer`/`Team` to `Context`, a stream-completion contract, `Team` ownership): all breaking, all change the same types.
3. Findings 3, 5, 6, 7 as freeze decisions (panic vs `Result`, PE validation, `put`/`get` placement and offsets, the duplicate `version`, the `UniqueId` init path), recorded even if the answer is "keep".
4. Finding 10 as cleanup: remove `thiserror` after a build, add `// SAFETY:` comments to the 25 `unsafe { }` call sites (the `# Safety` section on `init_with_attr` already exists), fix the doc drift in `lib.rs:211`, `:411`, `:34` and the README, add a `Send`/`!Send` compile-fail or static assert, and make the device tests safe under one-`Context`-per-process.

Nothing in this review was built, run or checked against NVIDIA's documentation: findings 1, 2 (the types' acceptance of the misuse), 4, 5 (panics), 6, 8 and 10 (counts, drift, dependencies) are read from source with controls stated; findings 1, 2, 3, 5 and 7 rest in part on NVSHMEM behaviour recorded as **not checked**; the CI facts in finding 10 (serialisation, runner contents) were not read.
