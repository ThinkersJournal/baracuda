## Findings

1. **`Dims` has public fields that break its own invariant, and the invariant reaches a C++ call.** `Dims { pub dims: [i64; 8], pub rank: usize }` documents "only the first `rank` entries are meaningful" and "`0..=TRT_MAX_DIMS`", and `Dims::new` enforces it (`rank = len.min(8)`). Nothing else does: `Dims { dims: [0; 8], rank: 100 }` is a safe struct literal, `as_slice` then panics (`&self.dims[..100]`), and `to_raw` (`doc(hidden)`, used by `set_input_shape` and by the builder crate) passes `nb_dims: 100` to TensorRT with an 8-element array behind it. `ExecutionContext::set_input_shape(&self, name, dims: Dims)` is a safe function, so `set_input_shape("x", Dims { dims: [0; 8], rank: 100 })` can make TensorRT read `d[8..100]` past the array if TensorRT does not check `nb_dims` (read, not run; **not checked** against the TensorRT headers or documentation). The derived `PartialEq` compares all 8 entries plus `rank`, so two `Dims` that agree on the meaningful axes but differ in the unused tail are unequal (`Dims::new(&[1, 2])` against a literal with a stale third entry), which contradicts the doc. `from_raw` indexes `raw.d[i]` for `i < nb_dims` and panics when TensorRT returns `nb_dims > 8`. Decision before the freeze: private fields with `rank()`/`as_slice()`/`new`, a manual `PartialEq` over `as_slice()`, and `rank: u8`; breaking after the freeze.
2. **`PluginLibraryHandle` is `Copy`, and the safety argument says it is not.** `#[derive(Copy, Clone, Debug, Eq, PartialEq)] pub struct PluginLibraryHandle(*mut c_void)`; `deregister_library(&self, handle: PluginLibraryHandle)` carries the comment "consuming it by value here means it is deregistered once". With `Copy`, `registry.deregister_library(h); registry.deregister_library(h);` compiles, is not `unsafe`, and hands TensorRT a handle it has already released (read, not run; what `deregisterLibrary` does on a stale handle is **not checked**). The two `unsafe impl Send/Sync` on the handle and the two on `PluginRegistry` rest on prose ("TensorRT documents as thread-safe", not read). Decision: drop `Copy`/`Clone` so the move is real (breaking, so before the freeze), or make `deregister_library` `unsafe`.
3. **`PluginRegistry::load_library` runs a foreign library's initializers from safe Rust.** It passes a caller-supplied path to `IPluginRegistry::loadLibrary`, which loads the shared library and runs its constructors and registration code; the function is a safe `pub fn`. A path to any native library is arbitrary code execution from safe code. By the usual convention (`libloading::Library::new` is `unsafe` for this reason) it would be `unsafe`. Decision: make it `unsafe` (breaking) or document it as a trust boundary; at minimum say so in the doc, which today says only that it returns `NullHandle` on failure.
4. **`Error` is closed and mixes three layers.** 5 variants (`Loader`, `NullHandle`, `Call`, `Utf8`, `ShimNotBuilt`), 0 `#[non_exhaustive]` (grep). `Loader(#[from] baracuda_core::LoaderError)` makes `baracuda_core`'s type part of this crate's public API. `Utf8(#[from] std::ffi::NulError)` is named for UTF-8 but holds an interior-NUL error (the message says "invalid C string"); a rename is breaking. `Call { op }` and `NullHandle { op }` carry only a static entry-point name, so the reason is only in the logger's output (the docs say so for `add_optimization_profile` and `build_serialized`). `ShimNotBuilt` exists with and without the `shim` feature. Every other wrapper crate uses `baracuda_core::Error<Status>`; this one cannot (TensorRT has no status codes), so a caller handling errors across the stack needs two paths. Recommendation: `#[non_exhaustive]`; rename `Utf8`; decide whether `Loader` should be `Box`ed or flattened.
5. **Logger design is a behaviour freeze.** TensorRT keeps one logger per process, so every `Logger` shares one never-freed C++ `ILogger` and every message goes to every live `Logger` (`LOGGERS: Mutex<Vec<..>>`), including messages from runtimes the logger was not handed to; `Logger::as_raw()` returns the same process-wide pointer for all instances. The doc states it. Consequences to accept before the freeze: a `Logger` cannot filter by source; `Runtime::_logger: Option<Arc<Logger>>` keeps the *Rust* logger alive although the C++ side no longer depends on it (the field's comment says the logger "must outlive the runtime", true of the old design, no longer needed); `Logger::stderr(min)` compares `severity as i32` with `min as i32`, which relies on the `-sys` `Severity` discriminants being TensorRT's (`severity_from_raw` maps `0..=4` and clamps the rest to `InternalError`, with a test). `unsafe impl Send/Sync for Logger` is argued correctly in the comment (a never-freed pointer and `Send + Sync` closures; read, not compiled).
6. **Getters that return `Result` and cannot fail.** `Engine::num_io_tensors`, `Engine::num_optimization_profiles`, `HostMemory::len`, `HostMemory::is_empty` always return `Ok(..)` (their bodies are `Ok(unsafe { .. })`); `ExecutionContext::optimization_profile` returns a bare `i32` for the same kind of call. Removing the `Result` later is breaking and every caller writes `?` today. Decision: return the plain value for the four infallible ones (and `usize` from `len`, which makes `is_empty` match the standard convention) before the freeze. `tensor_address`, `tensor_io_mode`, `tensor_data_type`, `tensor_shape` and `tensor_bytes_per_component` return `Result` for the interior-NUL `CString` and are legitimately fallible.
7. **Enums and re-exports.** `pub use sys::{trtDataType_t as DataType, trtExecutionContextAllocationStrategy_t as AllocStrategy, trtSeverity_t as Severity, trtTensorIOMode_t as IoMode}` makes four vendor `-sys` enums this crate's (and, through `baracuda-tensorrt-builder`, that crate's) public vocabulary; their variants and discriminants are `-sys` definitions I did not read, and whether they are `#[non_exhaustive]` is **not checked** (the builder crate matches `0..=10` onto `DataType` and returns `None` for the rest, which suggests TensorRT's type list grows). `OptProfileSelector` (3 variants, `#[repr(i32)]`) and `PluginCreatorKind` (`V2`, `V3One`, `Unknown`) are closed; `PluginCreatorInfo` has 4 public fields and no `#[non_exhaustive]`. `PluginCreatorKind::Unknown` is a catch-all, so adding a creator interface is not a breaking variant only if the enum is `#[non_exhaustive]` (it is not). Recommendation: leave `OptProfileSelector` closed (min/opt/max cannot grow); `#[non_exhaustive]` on `PluginCreatorKind` and `PluginCreatorInfo`; read the four `-sys` enums before freezing them.
8. **The run path is correctly `unsafe`, with two rough edges.** `set_tensor_address`, `enqueue_v3` and `enqueue_v3_raw` are `unsafe fn` with `# Safety` sections (5 `pub unsafe fn` in the crate, 5 sections), `Runtime::new` takes a raw `ILogger*`. Rough edges: (a) `Runtime::new`'s doc starts with `# Safety` and has no summary sentence, so rustdoc's first line for it is empty; (b) `enqueue_v3` says "the [`Stream`] itself is valid by construction", true for the call, and a `Stream` dropped right after is not tied to the queued work (stream destruction with pending work is the driver crate's question, **not checked here**); `set_optimization_profile_async(&self, index, stream: &Stream)` is a safe function that orders a TensorRT call on the stream and is the only safe stream-taking method. `tensor_address` returns a raw `*mut c_void` from a safe method (reading is harmless; the pointer's validity is the caller's).
9. **Lifetimes are right.** `Engine<'rt>` borrows `&Runtime`, `ExecutionContext<'e>` borrows the engine, and `Drop` order follows from the borrows; `HostMemory` (from `Engine::serialize`) has no lifetime and owns its buffer; `PhantomData<&'e Engine<'e>>` ties the context to one lifetime for both the borrow and the engine's own parameter (a stricter bound than `&'e Engine<'_>`; whether it ever blocks valid code is not tested). All of `Runtime`, `Engine`, `ExecutionContext`, `HostMemory` hold a raw pointer, so they are `!Send` and `!Sync` by the auto-trait rules (not compiled; no `assert_not_send` test): a caller that wants one `ExecutionContext` per thread cannot move it across threads. Whether TensorRT allows that (engines are shared across threads and contexts are per-thread in NVIDIA's guidance, from memory, **not checked**) decides whether `Send` should be added before the freeze.
10. **Feature gating.** Only `plugin` is behind `shim` (`lib.rs:84`): `Runtime`, `Engine`, `ExecutionContext`, `Logger` compile without it and return `Error::ShimNotBuilt` where they need it. So on docs.rs (`DOCS_RS` skips the shim build, `baracuda-tensorrt-sys/build.rs:28`; the manifest has no `[package.metadata.docs.rs]`) 62 of 79 rows render and the 17 plugin rows (`PluginRegistry`, `PluginCreatorInfo`, `PluginCreatorKind`, `PluginLibraryHandle`, `init_builtin_plugins`) do not. Milder than `baracuda-tensorrt-builder` (finding 7 of its review), the same remedy. `Logger::new` returns `ShimNotBuilt` as a runtime error where a compile-time gate could express it; whether that is intended is a design choice.
11. **Documentation drift, 5 places.** (a) `README.md` says "TensorRT's builder ... is C++-only ... Use `trtexec` or the Python bindings to produce engine blobs" and has no word of the sibling `baracuda-tensorrt-builder`. (b) It says "A typed safe `Logger` is a future addition", and `Logger` exists (`lib.rs:248`). (c) Its example uses `Runtime::with_null_logger()` with the comment "No logger (TRT 10 accepts null)", while `with_null_logger`'s own doc says "TensorRT 10 refuses a null logger and this returns `Error::NullHandle` there (measured against TensorRT 10.16)": the README example fails on the version it targets. (d) `lib.rs` is titled "Safe-ish TensorRT runtime-side bindings" and the README "Safe Rust wrappers". (e) The README lists `Runtime` as "Created with a raw `ILogger*` (`unsafe Runtime::new`) or none", missing `with_logger`, the path the rest of the repository uses. The README is not included in the crate docs (`include_str!`: 0 in `src`), so its example is never compiled.
12. **Dependencies and tests.** `Cargo.toml` has six dependencies; `baracuda-core`, `baracuda-cuda-sys`, `baracuda-driver`, `baracuda-tensorrt-sys`, `thiserror` are used in `src/`; **`baracuda-types` is not** (grep: 0 in `src/lib.rs`, `src/plugin.rs` and both test files; control: `baracuda_driver` and `baracuda_core` are found by the same grep). One unused dependency. 13 `#[test]` (2 unit tests in `lib.rs` on severity mapping and the trampoline, 8 in `runtime_smoke.rs`, 3 in `plugin_smoke.rs`; the integration tests are gated by `device-tests`, and the plugin ones by `shim` too). Nothing tests `Dims` with a rank over 8 (finding 1), a double `deregister_library` (finding 2), `set_input_shape`, `enqueue_v3`, or `Engine::serialize` round-trip beyond what the 8 runtime tests cover by name (`deserialize_garbage_blob_is_graceful` is the only engine-path test I could name). 38 + 9 `unsafe {` blocks and 9 + 11 `SAFETY` comments (grep), so about 27 blocks have no `SAFETY` comment of their own (a comment can cover adjacent blocks), mostly the one-line engine getters.

## Recommended order

1. Findings 1, 2, 3 (soundness of safe code): private `Dims` fields, non-`Copy` handle, `unsafe` or documented `load_library`.
2. Finding 6 (plain getters) and finding 4 (`Error`: `#[non_exhaustive]`, rename) together, since both change signatures callers write.
3. Finding 7 (read the `-sys` enums) and finding 9 (`Send` decision).
4. Findings 5, 8, 10, 11, 12 as cleanup (README rewritten against the code, one unused dependency removed, `# Safety` summary line, docs metadata).

Nothing in this review was built, run, or measured against NVIDIA's documentation: findings 2, 4, 6, 11, 12 are read from source and greps with the controls stated; findings 1, 3, 5, 7, 8, 9 rest in part on TensorRT behaviour recorded here as **not checked**.
