## Findings

1. **Async decode is not tied to the borrows that make the crate's lifetime claim true.** `lib.rs:20-32` and `README.md:56-58` say the `CodeStream<'data>` and `Image<'buf>` borrows make use-after-free "unrepresentable". They hold only while the two structs are alive. `Decoder::decode(&self, code_stream: &CodeStream<'_>, image: &Image<'_>, params: &DecodeParams) -> Result<Future>` (`lib.rs:431-436`) returns `Future { raw }` (`lib.rs:453`), a struct with no lifetime and no field but the raw handle (`lib.rs:476-478`). Safe code can therefore do `let f = d.decode(&cs, &img, &p)?; drop(img); drop(cs); drop(bytes); drop(buf);` and the decode, which the doc says "runs asynchronously on the image's stream" (`lib.rs:427-429`), has lost its input slice and output buffer (read, not run; whether nvImageCodec has finished reading or writing by the time `decode` returns, or whether `Future`'s `Drop` waits, is **not checked**; `Future::drop` calls only `nvimgcodec_future_destroy`, `lib.rs:528-535`). The test itself relies on the discipline rather than the types: `drop(image)` after `future.wait()` (`tests/gpu_smoke.rs:90-92`). Also `Future::wait` waits on the host; the doc's alternative "or synchronize the stream" is not checkable from the types because the stream is not carried (finding 2). Decision before the freeze: `Future<'a>` carrying `PhantomData<(&'a CodeStream, &'a mut Image)>` (breaking after the freeze), or `decode` takes the image by `&'a mut` and the future borrows it, or mark `decode` `unsafe`. `driver`'s `Drop for DeviceBuffer` has a stream-ordered-free path for async allocations (`memory.rs:1005-1019`); the test's buffer comes from `DeviceBuffer::zeros` and whether its drop synchronizes was **not read**.
2. **No owner links: `Instance` can be dropped first, and the stream is not carried.** `Image::new_interleaved_rgb8(instance: &Instance, buffer, width, height, stream: Option<&Stream>)` (`lib.rs:316-322`), `CodeStream::from_host_mem`, `from_file` and `Decoder::new` all take `&Instance` and keep only the raw child handle (`CodeStream` has `PhantomData<&'data [u8]>` and `Image` has `PhantomData<&'buf mut DeviceBuffer<u8>>`, neither an `&Instance`). `let d = Decoder::new(&inst)?; drop(inst);` compiles, and `d`'s `Drop` then runs `nvimgcodec_decoder_destroy` after `nvimgcodec_instance_destroy` (`lib.rs:126-134`, `463-471`; library behaviour **not checked**). `Instance` is `Send + Sync` (`lib.rs:86-87`) so this can also cross threads. The stream is written into `info.cuda_stream = stream_raw(stream)` (`lib.rs:342`) and not stored; dropping the `Stream` before the decode finishes is safe code. `Decoder::decode` has no stream parameter (the stream lives in the `Image`), unlike the shape the module doc sketches at `lib.rs:16` (`decoder.decode(&stream, &image, &params)`, where `stream` there means a different object). Same pattern as the nvjpeg review, findings 2 and 4 (`State::new(&Handle)`, `stream: Option<&Stream>`). Decision: `&'i Instance` carried in each child (a lifetime parameter on `Decoder`, `CodeStream`, `Image` is breaking after the freeze), and the stream either borrowed for `'buf` or documented as a caller obligation.
3. **`unsafe impl` Send and Sync: 6, none justified in a comment.** `Send` for `Instance`, `CodeStream<'_>`, `Image<'_>`, `Decoder`, `Future` (`lib.rs:86, 154, 298, 404, 480`) and `Sync` for `Instance` only (`lib.rs:87`) (grep: `unsafe impl` 6). 0 `SAFETY` comments in the crate (grep `SAFETY` over `src/lib.rs`: 0; positive control: grep `unsafe` over the same file finds 23 lines). `Sync for Instance` lets safe code call `Instance::new`-derived children from several threads against one instance (`&Instance` in every constructor); whether nvImageCodec instances are thread-safe for concurrent create, decode and destroy is **not checked**. The other five are `Send` only; with raw-pointer fields they are `!Sync` automatically (read, not compiled; no `assert_not_sync` test). `ImageInfo` stores a `RawImageInfo` holding `*mut c_void` fields (`buffer`, `struct_next`, `-sys` 512 and 535), so `ImageInfo` is `!Send + !Sync` (read, not compiled), which blocks probing a stream on one thread and handing the metadata to another. Unsafe totals: 23 lines match `unsafe` in `src/lib.rs` (grep): 6 `unsafe impl` + 17 `unsafe { ... }` blocks (17 counted from the grep listing: `lib.rs:103, 112, 131, 171, 193, 215, 236, 263, 347, 366, 423, 443, 468, 495, 505, 508, 533`); 0 `unsafe fn`; 0 `# Safety` sections. The public API has no `unsafe fn`, so every precondition is a safe-fn contract: findings 1, 2 and 4 follow from that.
4. **`Image::new_interleaved_rgb8` panics where it should return `Err`, and its size check is the only one.** It does `assert!(buffer.len() >= needed, ...)` (`lib.rs:324-328`; the crate's only `assert`, grep: 1) with `needed = (width as usize) * (height as usize) * 3` (`lib.rs:323`; on a 32-bit target `usize` arithmetic can wrap, **not checked** whether any 32-bit target is supported). A panic across a safe constructor is a footgun for a data-loading path; `Err(Error::Status { status: INVALID_PARAMETER })` is the shape `from_file` already uses (`lib.rs:211-213`). The doc says "at least `width * height * 3`" (`lib.rs:310-311`) and does not say it panics. The check is correct for the buffer it is given, so the borrow-for-`'buf` part is sound: `buffer.as_raw().0 as *mut c_void` (`lib.rs:340`) is valid for the image's life. Decision: return `Err`; this changes a panic into a `Result` and is not breaking.
5. **`new_interleaved_rgb8` is the only output layout, and the type name hard-codes it.** One constructor, 8-bit interleaved RGB (`lib.rs:331-339`), `Uint8`, `StridedDevice` only. `README.md:23` and the module doc (`lib.rs:34-35`) list encode, batch decode and other formats as follow-ups: each is an addition, not breaking, unless the follow-up changes `Image<'buf>`'s one `PhantomData<&'buf mut DeviceBuffer<u8>>` (a 16-bit or planar output needs `DeviceBuffer<u16>`, or several buffers). **Decision**: freeze `Image` as a family (`Image::new_*` constructors) and make sure the lifetime parameter can hold more than one buffer, or accept a breaking change at the first planar or 16-bit constructor. `Decoder::decode` is single-image (batch size `1` hard-coded at `lib.rs:448`) and `Future::processing_statuses` returns a `Vec` per batch (`lib.rs:500`), so the batch API is already half-shaped for a later `decode_batch`.
6. **`DecodeParams` and `Properties` are closed literal structs.** `DecodeParams { pub apply_exif_orientation: bool }` (`lib.rs:374-378`), `Copy + Clone + Debug + Default`, 0 `#[non_exhaustive]`; the `-sys` struct it maps to has one field (`apply_exif_orientation`, `-sys` 636) but nvImageCodec's decode parameters will grow (backend selection, ROI, allow-lossy flags: **not checked** against the header, from memory only). Adding a pub field is a breaking change for anyone writing `DecodeParams { apply_exif_orientation: x }` without `..Default::default()`. `Properties { pub version: u32, pub cudart_version: u32 }` (`lib.rs:137-143`), `Eq + PartialEq + Copy`, same shape. Recommendation: `#[non_exhaustive]` on both (and builder-style setters for `DecodeParams`); `ImageInfo`'s private `raw` field (`lib.rs:257`) already makes `ImageInfo` un-constructible and un-exhaustively-matchable outside the crate, so the effect of `#[non_exhaustive]` there is nil (read; the attribute would still document intent).
7. **`ImageInfo` surfaces less than it holds and lies by omission about orientation.** The pub view has `width`, `height` (from `plane_info[0]`, `lib.rs:269-271`; doc "component 0"), `num_planes`, `codec_name: String`, `sample_format`, `color_spec` (`lib.rs:244-258`); `chroma_subsampling` and `orientation` exist in the raw struct (`-sys` 520-526) and are reachable only through `raw()` (`lib.rs:284`), which hands out the whole `-sys` layout (`RawImageInfo`, `#[repr(C)]`, 1:1 with the vendor header: any vendor struct change is breaking in this crate's API). `DecodeParams::default()` sets `apply_exif_orientation: true` (`lib.rs:383`) while the example sizes the output from `info.width`/`info.height` of the unrotated stream (`README.md:43`; `tests/gpu_smoke.rs:79`): whether an EXIF-rotated image's decoded dimensions are swapped relative to `plane_info[0]` is **not checked**, and if they are, the doc example's buffer is for the wrong shape. `width`/`height`/`num_planes` are `u32` (consistent with nvjpeg's `frame_dimensions` but not its `ImageInfo::width() -> i32`, nvjpeg finding 8). `ImageInfo` has no `PartialEq`; `codec_name` is a lossy decode of a fixed buffer (`lib.rs:263-267`, `from_utf8_lossy`). Recommendation: expose `chroma_subsampling()`/`orientation()` (this is the use for the `ChromaSubsampling` re-export, finding 8), keep `raw()` documented as unstable or `#[doc(hidden)]`.
8. **`ChromaSubsampling` is re-exported and used nowhere.** `pub use ... nvimgcodecChromaSubsampling_t as ChromaSubsampling` (`lib.rs:55`); grep for `ChromaSubsampling`, `ColorSpec`, `SampleFormat` in `src/lib.rs`: `ChromaSubsampling` appears only on line 55 (the other two are used in `ImageInfo`, `lib.rs:254, 256`, and in `new_interleaved_rgb8`, `lib.rs:331-332`). A frozen public type that no function takes or returns (only reachable via `raw().chroma_subsampling`). Either surface it (finding 7) or drop it from the frozen set.
9. **The re-exported enums are vendor `-sys` types, `#[repr(i32)]`, 0 `#[non_exhaustive]`.** `SampleFormat` has 19 variants (`-sys` 153-193), `ChromaSubsampling` 8 (`-sys` 228-246), `ColorSpec` 8 (`-sys` 250-268), each `Copy, Clone, Debug, Eq, PartialEq`; grep `non_exhaustive` in `baracuda-nvimagecodec-sys/src/lib.rs`: 2 hits, both `finish_non_exhaustive()` calls (lines 572, 845), 0 attributes (control: the same pattern finds those 2). nvImageCodec's own versioning (`struct_type`, `struct_size`, `struct_next` on every struct) shows it expects growth; a new `SampleFormat` (`-sys` already names 5 families: Y, YA, RGB, BGR, YUV, RGBA, YCCK, CMYK) or `ColorSpec` is a plausible vendor addition and would break exhaustive matches in this crate's users. Constructing a `#[repr(i32)]` enum from a value the vendor library returns that is not a listed variant is undefined behaviour: `raw.sample_format` / `raw.color_spec` are copied from the library's out-struct (`lib.rs:275-276`) into these enum types, so a future library that reports a new `SampleFormat` value would produce an invalid enum value in safe code (read; whether `nvimgcodecImageInfo_t` fields are validated is **not checked**, none is in this crate). This is the more serious half of the finding. Compare nvjpeg finding 9 (same pattern: `-sys` enums re-exported, 0 `#[non_exhaustive]`), but there the status type was a newtype; here the *value* enums are read from library output. Recommendation: newtype-with-constants for the three value enums read back from the library (like `nvimgcodecStatus_t(pub i32)`, `-sys` 309), or `#[non_exhaustive]` plus a range check in `ImageInfo::from_raw`.
10. **`CodeStream::from_file` converts the path lossily.** `path.to_string_lossy().as_bytes()` into `CString` (`lib.rs:210-213`): a non-UTF-8 path (legal on Linux, and on Windows the path is `WTF-16` that `to_string_lossy` turns into U+FFFD) is silently changed and the library opens, or fails to open, a different file. An interior NUL maps to `INVALID_PARAMETER` (read). `from_file` lives in `impl CodeStream<'static>` (`lib.rs:204`), which makes `CodeStream::from_file` the only constructor with an inferred `'static`; fine. No test calls `from_file` (grep `from_file` in `tests/`: 0; control: `from_host_mem` has 1 hit). Recommendation: reject non-UTF-8 paths with `INVALID_PARAMETER` (`path.to_str()`), or on Unix use `OsStrExt::as_bytes`.
11. **`Error`, `Result` and `Future`'s status handling.** `Error = baracuda_core::Error<nvimgcodecStatus_t>`, `#[non_exhaustive]` at `baracuda-core/src/error.rs:122` (read); `nvimgcodecStatus_t` is `pub i32` newtype (`-sys` 309), so new statuses are not breaking. `Result<T, E = Error>` (`lib.rs:66`) follows the crate family. `Future::all_succeeded` compares each status to `== NVIMGCODEC_PROCESSING_STATUS_SUCCESS` (`lib.rs:518`) over a `u32` bitfield the `-sys` doc calls a bitfield (`-sys` 283-285): `SATURATED = 0x2`, `FAIL = 0x3` (`-sys` 292-298) are values, not independent bits, so the equality is correct for the listed values; a combined future value would read as failure (**not checked** against the header). `processing_statuses` returns the raw `Vec<u32>`, and a caller must know the constants live in `-sys`: those constants are not re-exported (grep `NVIMGCODEC_PROCESSING_STATUS` in `src/lib.rs`: 3 hits, `lib.rs:47` (import), `499` (doc), `518` (use); none is `pub use`). A caller wanting to tell `IMAGE_CORRUPTED` from `FAIL` must depend on `-sys`. All 5 `Drop` impls ignore errors (`let _ =`, grep: 5), and silently skip destroy if the loader fails (`if let Ok(n) = nvimgcodec()`), recorded so the freeze does not claim leak-freedom. Getters returning `Result` (`image_info`, `properties`, `processing_statuses`) call the library and are legitimately fallible.

## Comparison with the nvjpeg review

Same patterns: (1) child handles with no owner lifetime (nvjpeg findings 2 and 4; here finding 2); (2) async work not tied to buffers or stream (nvjpeg finding 4; here finding 1, but this crate is better placed: `Image<'buf>` and `CodeStream<'data>` already borrow, so the fix is a `Future<'a>`, not a new design); (3) re-exported `-sys` enums with 0 `#[non_exhaustive]` (nvjpeg finding 9; here finding 9, worse because the values are read back from the library); (4) `Send`-only handles with `Sync` on the root handle (nvjpeg finding 10; here finding 3); (5) unused dependencies, 0 `SAFETY` comments, README drift (nvjpeg findings 12 and 13; here findings 12 and 13). Differences: this crate has 0 `unsafe fn` (nvjpeg has 3), so the size-check problem in nvjpeg finding 1 does not exist for the output buffer (the one assert covers it, finding 4, with a panic instead of `Err`); this crate has no `PixelFormat` of its own (no closed-enum problem of nvjpeg finding 7) but takes the vendor `SampleFormat` instead; no `Result`-returning infallible getter (nvjpeg finding 11); 0 `-sys` newtype status problem (both use `nvimgcodecStatus_t(pub i32)`-style).

## Recommended order

1. Findings 1 and 2 (soundness of safe code: `Future<'a>` and an `&Instance` lifetime on the children, the stream), since both change public type parameters and are breaking after the freeze; finding 3 is the documentation of what stays an obligation.
2. Findings 9, 6, 7, 8 together (value enums read from the library, `#[non_exhaustive]` on `DecodeParams` and `Properties`, the `ImageInfo` view, the unused `ChromaSubsampling` re-export), then finding 5 (what `Image` is a family of).
3. Findings 4 and 10 (panic to `Err`, lossy path) as non-breaking fixes; finding 13 (two unused dependencies, tests) and finding 12 (README rewritten against the code) as cleanup; finding 11 is a doc note plus a re-export of the status constants.
