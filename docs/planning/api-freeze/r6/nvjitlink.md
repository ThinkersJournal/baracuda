## Findings

1. **Safe functions panic on a NUL byte in caller input.** `Linker::new` (`lib.rs:92`), `add_data` (`:108`) and `add_file` (`:124`) call `CString::new(..).expect(..)`: 3 `expect` sites, one per string argument, so `new(&["a\0b"])` panics instead of returning an `Error`. The sibling crates return errors for the same case (`r6/nvml.md` finding 11: an interior NUL maps to `INVALID_ARGUMENT`). The panic is in the signature's contract and becomes the frozen behaviour. Decision: return an `Error` (breaking later: the `Result` is already there, so the change is non-breaking in type but breaking in behaviour).
2. **`add_data` may rely on a NUL terminator it does not state.** The only mention is a test comment, "nvJitLink expects NUL-terminated PTX bytes" (`tests/gpu_smoke.rs:35`), and the test appends a `0` (`:36-37`); the crate-level example passes `b"/* some PTX... */"` with no terminator (`lib.rs:12`), `add_data`'s doc says nothing (`:104`), and the function passes `data.as_ptr()` and `data.len()` (`:113-114`). Whether nvJitLink reads past `len` for PTX is **not checked**; if it does, a safe fn is unsound for `&[u8]` without a NUL. Decision: check against NVIDIA's documentation, then either append the NUL inside `add_data` or document it. `add_file` takes `&str` for a path (`:121`), so a non-UTF-8 path cannot be passed (`AsRef<Path>` would be wider and non-breaking only as a generic).
3. **No ordering enforcement, and the README promises output the type does not have.** `linked_cubin` before `complete` is left to nvJitLink's status code (`:136`, doc "Call after complete"); a typestate or a `complete(self) -> Cubin` shape is a freeze decision. `complete` returns `Result<()>` (`:129`); README's example `let cubin = linker.complete()?;` (`README.md:18`) and `add_data(b"...", "modA.ptx")` with no `InputType` (`:16-17`) do not match the code, and `README.md:29` lists `info_log`, which does not exist (grep `info_log` in `src/lib.rs`: 0; control: the `-sys` crate declares `nv_jit_link_get_info_log` at `baracuda-nvjitlink-sys/src/lib.rs:251`, so the symbol is loadable and unwrapped). The `-sys` crate also declares `nvJitLinkGetLinkedPtx` (`:246-247`), not wrapped, so LTO-to-PTX output is not reachable from the safe crate. The README example is not compiled (`include_str` grep in `src/lib.rs`: 0). `error_log` decodes with `from_utf8_lossy` (`:163`), so bytes are replaced silently, acceptable for a log.
4. **`Linker` is `Send`, not `Sync`, with an uncommented `unsafe impl`.** `unsafe impl Send for Linker {}` (`lib.rs:73`) carries no `SAFETY` comment. The struct holds a raw `nvJitLinkHandle` and the option `CString`s (`:67-71`); whether nvJitLink allows a handle to move between threads, and whether it copies the option strings (the `_option_storage` field keeps them alive "for at least as long as the linker", `:69`, which is safe either way), is **not checked**. `Sync` is absent, so `&Linker` cannot be shared, although `linked_cubin` and `error_log` take `&self` (`:136`, `:148`); that is the conservative choice and adding `Sync` later is non-breaking. `as_raw` (`:168`) is a safe fn returning the raw handle ("use with care"); with `Drop` calling `nvJitLinkDestroy` on it, a caller who destroys it through FFI gets a double destroy only through their own `unsafe`. `Drop` ignores the destroy status (`:183`, `let _ =`), as the other crates do.
5. **`InputType` is a closed 6-variant enum that hides the `-sys` `None`.** `InputType` (`:36-49`) is not `#[non_exhaustive]` (census column 0; grep `non_exhaustive` in `src/lib.rs`: 1 hit, `finish_non_exhaustive` at `:79`; control: the same grep finds that call). The `-sys` enum has 7 variants including `None = 0` (`baracuda-nvjitlink-sys/src/lib.rs:26-40`, read) and the private `raw` (`:54`) maps 6 of them. A new nvJitLink input kind forces a major bump unless the enum is made `non_exhaustive` now; the cost is a `_` arm in downstream matches (nobody matches on it in this crate). Decision: add the attribute before the freeze.
6. **Result-returning functions that cannot fail past the loader.** Every method does `nvjitlink()?` plus a symbol lookup before the FFI call; none has an infallible body, so no finding-6-style removal. `version()` returns `(u32, u32)` as `(major, minor)` (`:189`), fine. `linked_cubin` and `error_log` allocate `vec![0u8; size]` from the size nvJitLink reports (`:142`, `:157`) with no cap; acceptable.
7. **Dependencies: 2 unused, 1 dev-dep used.** `Cargo.toml:20-24` lists `baracuda-types`, `baracuda-core`, `baracuda-nvjitlink-sys`, `thiserror`. Greps over `src/lib.rs` and `tests/gpu_smoke.rs`: `baracuda_core` 1 (`lib.rs:26`), `baracuda_nvjitlink_sys` 1 (`:23`'s `use`), `baracuda_types` 0, `thiserror` 0 (also 0 for `derive(Error)`); positive control: the same greps find `baracuda_core` and `baracuda_nvjitlink_sys`, and `baracuda_driver` (the dev-dependency, `Cargo.toml:27`) 3 times in `tests/gpu_smoke.rs`. So `baracuda-types` and `thiserror` are unused direct dependencies; remove after a build check (a re-export through `baracuda-core` would not show in the grep). The umbrella exposes the crate as `baracuda::nvjitlink` behind the `nvjitlink` feature (`baracuda/src/lib.rs:94-95`, read). There is no feature gating on the API itself; `device-tests = []` (`Cargo.toml:18`) gates tests only.
8. **Unsafe accounting and tests.** `src/lib.rs` has 11 lines containing `unsafe`: 1 `unsafe impl Send` (`:73`) and 10 `unsafe {` FFI call blocks (`:97, 109, 125, 132, 141, 143, 153, 158, 183, 194`); 0 `SAFETY` comments (control: the same grep finds the 11). The calls pass `&mut` locals and buffers sized from the library's own size query, which reads correctly but is not written down. Tests: 2 `#[test]` (`grep -cE '^\s*#\[test\]'`: `tests/gpu_smoke.rs` 2, `src/lib.rs` 0): `nvjitlink_loads` (`:16`) calls `version()` through `require_optional!` (`baracuda-driver/src/test_support.rs:118`; its skip semantics not read in full), and `link_ptx_to_cubin` (`:25`, `device-tests` only) covers `new`, `add_data`, `complete`, `error_log` (failure path only), `linked_cubin` and `version`: 6 of 8 functions by name. No test touches `add_file`, `as_raw`, the other five `InputType` variants, the `Drop` path as an observable, or NUL input (finding 1). One doctest (`lib.rs:7-17`, `no_run`).

## Recommended order

1. Findings 5 and 3 (`#[non_exhaustive]` on `InputType`, the `complete` / `linked_cubin` shape): both change types.
2. Findings 1 and 2 (NUL input returns an error; settle the PTX terminator question against NVIDIA's documentation).
3. Finding 4 (SAFETY argument for `Send`; decide on `Sync`).
4. Findings 6, 7, 8 as cleanup: README rewritten against the code (`complete`, `add_data` arity, `info_log`), two unused dependencies removed, SAFETY comments, tests for `add_file` and NUL input.

Nothing in this review was built, run, or checked against NVIDIA's documentation: findings 1, 3, 5 (counts), 7, 8 are read from source and greps with the controls stated; findings 2 and 4 rest in part on nvJitLink behaviour (PTX terminator, thread-safety, option-string lifetime) recorded here as **not checked**, and the `require_optional!` skip behaviour was not read beyond its definition line.
