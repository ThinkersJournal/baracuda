## Findings

1. **16 safe `Layer` setters cast the layer to a kind without checking it.** `Layer` is one type for every layer kind. `set_concat_axis`, `set_conv_stride`/`padding`/`dilation`/`num_groups`, `set_deconv_*` (4), `set_resize_output_dims`, `set_resize_mode`, `set_pool_stride`, `set_pool_padding`, `set_reshape_dims`, `set_first_transpose` and `set_second_transpose` are safe `pub fn`s that call a shim function doing `static_cast<IConvolutionLayer*>(asLayer(layer))` (and the matching cast for each kind). The shim has 19 `static_cast<I...Layer*>(asLayer` lines (grep) and the same file has 0 `dynamic_cast` (grep; control: it has 94 `static_cast`/`reinterpret_cast`/`dynamic_cast` in all). So `network.add_element_wise(&a, &b, Sum)?.set_conv_stride(&dims)` compiles, is not `unsafe`, and is a C++ cast to the wrong layer type followed by a call through it: undefined behaviour from safe Rust. `Network::add_activation` and `add_softmax` do the same internally but on a layer they just created, so those are sound (read, not run). Decision before the freeze: typed layers (`ConvolutionLayer<'n>` and so on, returned by `add_convolution`; breaking), or a kind check in the shim that returns `Err`/`false` (observable, so it must precede the freeze), or `unsafe`. Any of the three is breaking after the freeze.
2. **Objects from different builders and networks can be mixed in safe code.** The doc and the `SAFETY` comment on `build_serialized` say the network and config "borrow this builder", but the signature is `build_serialized(&self, network: &Network<'_>, config: &BuilderConfig<'_>)`: the two lifetimes are unconstrained, so a network from builder A and a config from builder B go to builder C. The same holds for `BuilderConfig::add_optimization_profile(&self, profile: &OptimizationProfile<'_>)` and for `OnnxParser::new(network: &'n Network<'_>, ..)`. Tensors are tied to a network only by a shared `'a` that the compiler can pick as the shorter of two live borrows, so `net_a.add_element_wise(&tensor_from_a, &tensor_from_b, op)` with two live networks compiles (read, not compiled: I could not build the crate here). TensorRT's own behaviour on a foreign-network tensor is **not checked** (documentation not read); the shim passes the raw pointers through (`trtBuilderBuildSerialized` dereferences `*asNetwork(network)` and `*asConfig(config)` with no check). Decision: tie `Network<'b>`/`BuilderConfig<'b>`/`OptimizationProfile<'b>` to the same builder by taking `&'b self` types (`network: &Network<'b>`), and make `Tensor`/`Layer` carry an invariant network lifetime. Breaking after the freeze.
3. **The census does not count the 9 enums or their 72 variants.** `items.tsv` has 0 rows of kind `enum` and 0 of kind `variant` for this crate; `api.rs` declares `ElementWiseOp` (14 variants), `Activation` (14), `UnaryOp` (21), `ReduceOp` (5), `MatrixOp` (3), `InterpolationMode` (3), `PoolingType` (3), `MemoryPool` (5) and `BuilderFlag` (4) through `trt_enum!`, a local `macro_rules!` (`api.rs:11`). 9 + 72 = **81 public items missing: 99 + 81 = 180 rows with macros.** Control for the method: the 76 methods in the census equal the 71 + 5 `pub fn` I counted in the source, so the walker reads the `impl` blocks and misses only what the macro emits. The README's note 1 says macro-generated items are now counted; this macro is a case it does not cover (the "macro" it handles may be limited to a named list; I did not read `classify.py` for this). Reported for the census; the verdict on the enums is finding 4.
4. **All 9 enums are closed, and they mirror enums TensorRT grows.** 0 `non_exhaustive` in the crate (grep: `api.rs` 0, `onnx.rs` 0, `lib.rs` 0). `BuilderFlag` says it is "the `nvinfer1::BuilderFlag` values this crate exposes", a subset by design, so adding a flag is a new variant, breaking without `#[non_exhaustive]`; the same holds for `ElementWiseOp`, `ActivationType`, `UnaryOp` and `MemoryPool` as TensorRT adds members (that TensorRT has added members is from memory, **not checked** against NVIDIA's headers). `MemoryPool` has a gap (discriminant 4 is unused) and `TacticSharedMemory = 5` is documented as "Host memory the builder may use for tactics' timing caches", which reads like a different member than the name (also unchecked against NVIDIA documentation). The discriminants are passed to the shim as `i32` (`pool as i32`), so a wrong value is a wrong TensorRT call, not a compile error. Recommendation: `#[non_exhaustive]` on all nine (the macro adds one attribute line); verify every discriminant against the header before the freeze.
5. **`NetworkFlags(pub u32)` exposes its representation and has no way to test a flag.** The field is `pub`, so any bit pattern is constructible (`NetworkFlags(0xFFFF_FFFF)`); the type has `NONE`, one named flag (`STRONGLY_TYPED = 1 << 1`), `BitOr` and `Default`, and no `BitAnd`, `contains` or `is_empty`. Decision: make the field private (`pub(crate)`, breaking) and add `contains`, or accept the open representation. `1 << 1` is from TensorRT's `NetworkDefinitionCreationFlag` (not checked).
6. **ONNX errors: public fields on structs that TensorRT may grow, and a second error type.** `ParserError` has 5 `pub` fields and no `#[non_exhaustive]`; `OnnxParseError(pub Vec<ParserError>)` exposes its tuple field. `OnnxParser::parse` returns `OnnxParseError`, while the rest of the crate returns `baracuda_tensorrt::Error`; a caller that wants one `?` chain needs a `From` impl, which does not exist (grep `impl From`: 0 in the crate). `ParserError::code` is a raw `i32` of `nvonnxparser::ErrorCode` documented by examples (`0`, `3`, `8`) with no enum. `parse` invents code `4` for an interior-NUL path, a value that is also TensorRT's (unchecked), so a caller cannot tell the crate's own error from the parser's. Recommendation: `#[non_exhaustive]` on `ParserError`, an `ErrorCode` enum, a `From<OnnxParseError> for Error` (or fold it into `Error`), and a private field on the tuple struct.
7. **The whole API is feature-gated, and docs.rs renders one function.** With default features the crate's public surface is `shim_built()` and nothing else (`lib.rs:25`; `api` and `onnx` are `#[cfg(feature = "shim")]`). The manifest has no `[package.metadata.docs.rs]` (grep over `Cargo.toml`: 0 matches; the crate's `Cargo.toml` is the file read), and `baracuda-tensorrt-sys/build.rs:28` skips the C++ shim when `DOCS_RS` is set, so `shim` cannot be built on docs.rs and a docs.rs page shows `shim_built` alone. The 98 other census rows are therefore items that the published documentation does not show and that `cargo doc` without the SDK headers cannot show. Decision: either make the API compile without the shim (the types and the `*` signatures, with the shim only behind the C calls; the larger fix) or add docs metadata that renders the API from a stub `-sys` surface. A freeze that no reader can see in rendered docs is a review problem even if the code is right.
8. **Signatures use `baracuda-tensorrt` types that this crate does not re-export.** `DataType`, `Dims`, `Error`, `Result`, `Logger`, `HostMemory` appear in public signatures (`add_input`, `Tensor::data_type`, `Builder::new`, `build_serialized`); the crate re-exports only `OptProfileSelector` (`api.rs:6`). A user of this crate must also depend on `baracuda-tensorrt` at the matching version to name them (the lockstep rule makes that safe, and the module doc's example uses them without saying so). `Severity` in the example is likewise not from this crate. Decision: re-export the six (non-breaking to add now, and removes a coordination burden), or document the dependency.
9. **Safe functions with unchecked arguments.** `set_optimization_level(level: i32)` documents `0..=5` and checks nothing; `add_reduce`/`add_softmax` take `axes: u32` as a raw bitmask with no check against the input rank; `add_gather(.., axis: i32)`, `set_concat_axis(axis: i32)`, `set_conv_num_groups(groups: i64)` and the `add_convolution` `num_output_maps: i64` are raw integers; `set_first_transpose` fills the rest of the permutation with the identity and does not check that `order` is a permutation (duplicates, out-of-range). `add_convolution` and `add_deconvolution` do not check that `kernel.len()` equals `num_output_maps * C / groups * kernel volume` (`add_constant_bytes` does check count against `dims` for constants, `api.rs:618`, so the pattern exists). What TensorRT does with each (error at build, error in the logger, or an out-of-range read) is **not checked**: for the convolution weights the count passed is the real buffer length, so a host over-read is not possible from the count alone, but whether TensorRT reads `expected` elements rather than `count` is a question for the documentation. Recommendation: validate what is cheap (`optimization_level` range, weight count, permutation), document the rest.
10. **Unsafe-block hygiene.** 80 `unsafe {` blocks (72 in `api.rs`, 8 in `onnx.rs`), 78 `SAFETY` comments (71 + 7). Two blocks lack their own comment: `api.rs:661` (`trtSoftMaxSetAxes`) and `onnx.rs:161` (covered by the comment at `onnx.rs:158`). Many comments are one boilerplate sentence ("`self.raw` and every tensor / layer / profile handle passed are live, non-null handles of the same network or builder; the borrow checker ties their lifetimes to `self`") pasted onto calls where it is not true (`BuilderConfig::set_flag` has no tensor, layer or profile argument) or where finding 2 shows the claim does not hold (`build_serialized` states the network and config borrow the builder; they need not). No `Send`/`Sync` impl and no `assert_send`/`assert_not_send` test (grep: 0 in the crate): `Network` holds a `RefCell` and every handle a raw pointer, so all are `!Send` and `!Sync` by auto-traits (not compiled); whether a `Builder` may move across threads is **not checked** against TensorRT's thread-safety rules.

## Dependencies, tests, docs

- `Cargo.toml`: two runtime dependencies (`baracuda-tensorrt`, `baracuda-tensorrt-sys`), both used; no unused ones. The `device-tests` feature and the `shim` feature are documented in the manifest.
- Tests: 24 `#[test]` (17 + 3 + 4) over three files, gated by `require_optional!`. `grep` finds `add_conv`/`add_slice`/`add_gather` in 4 lines of the tests, so most layer kinds the API offers (deconvolution, select, resize, pooling, cast, reduce, softmax) have no test I could find by name (approximate; not every call is `add_*`-named in the tests). There is no test that a wrong-kind setter fails (finding 1), none that mixes builders (finding 2), and no `compile_fail` doctest.
- README: 21 lines, accurate about the `shim` gate; it has no API list to drift.

## Recommended order

1. Findings 1 and 2 (soundness of safe code); one design, since typed layers fix both the wrong-kind cast and the foreign-network tensor.
2. Finding 4 (`#[non_exhaustive]` plus a header check of the discriminants) and finding 3 (census gap; flag to the PM).
3. Findings 5, 6, 8 (small, decided together).
4. Finding 7 (documentation reachability) before beta.0; findings 9 and 10 as cleanup.

Nothing in this review was built, run, or measured against NVIDIA's documentation: findings 1, 3, 7 and 10 are read from source and greps with the controls stated; findings 2, 4, 5, 9 rest in part on TensorRT behaviour recorded here as **not checked**.
