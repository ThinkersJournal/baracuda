## Findings

1. **`decode_interleaved` and `decode_planar` are safe functions that cannot check the destination size.** `decode_interleaved(handle, state, jpeg_bytes, format, output: &mut DeviceBuffer<u8>, width: i32, stream)` writes `pitch = width as usize * 3` bytes per row into `output.as_raw()` for as many rows as the JPEG has; the function takes no height and never calls `output.len()` (read; `src/lib.rs` has 2 `assert`, one on `is_interleaved`, one in `decode_batched`; none on a length). The doc says "sized at least `width * height * 3` bytes", a precondition of a safe fn. A 1x1 buffer with a 4096x4096 JPEG compiles and lets the decoder write past the allocation on the device (whether nvJPEG checks is **not checked**). `width` is `i32` and `width as usize` of a negative value is a huge pitch. `decode_planar` has the same shape (`widths[i] as usize` per plane, a silent `.take(4)` on `channels`, unfilled channels left null, no check that `channels.len()` matches the component count or that `format` is planar), and its doc says "Pass the full `ImageInfo`" while the parameter is `widths: [i32; 4]`. Decision before the freeze: take the `ImageInfo` (or width and height) and check `output.len() >= pitch * height` returning `Err`, or make both `unsafe` like `decode_batched` and `decode_device`; either is breaking after the freeze.
2. **`Handle`, `State` and friends have no lifetime link, so safe code can destroy the owner first.** `State::new(&Handle)`, `Decoder::new`, `JpegStream::new`, `BufferPinned::new`, `BufferDevice::new`, `DecodeParams::new`, `EncoderState::new`, `EncoderParams::new` copy the raw handle and keep no borrow (8 structs hold one raw pointer each). `let s = State::new(&h)?; drop(h);` compiles; `s`'s `Drop` then calls `nvjpegJpegStateDestroy` after `nvjpegDestroy` (read; what nvJPEG does is **not checked**). Every operation takes `handle: &Handle` as a separate argument, so a state from handle A can be used with handle B; nothing compares them. Decision: carry `&'h Handle` (or an `Arc` to the handle) in each child type and drop the repeated `handle` parameter from the method signatures (breaking, so before the freeze), or document the drop order and the pairing as caller obligations.
3. **`attach_to` buffers are not tied to the state, and phase order is unchecked.** `BufferPinned::attach_to(&self, state: &State)` and `BufferDevice::attach_to` hand a raw buffer to the state and keep nothing: dropping the buffer (it has a `Drop`) while the state still points to it, or attaching one buffer to two states, is safe code (read, not run; nvJPEG behaviour **not checked**). `Decoder::decode_host`, `decode_transfer_to_device` and the `unsafe fn decode_device` must be called in that order and with a `JpegStream` that was parsed; all three are expressible in safe code in any order, and `decode_device` is the only one marked `unsafe` (for the destination pointers, not the order). Decision: a typed state machine (`State` -> `HostDecoded` -> `Transferred`) or document the order; and an `attach_to` that borrows the buffer for the state's lifetime.
4. **Async work is not tied to its buffers or its stream.** Every function takes `stream: Option<&Stream>` and keeps nothing (no lifetime, no clone; 12 `let stream_handle` lines build it from `s.as_raw()`). The decode and encode calls are queued on a stream, while the destination `&mut DeviceBuffer<u8>` (and `&DeviceBuffer<u8>` in `encode_image`) is borrowed only for the call: `decode_interleaved(.., &mut out, .., Some(&s))` then `drop(out)` or `drop(s)` is safe code, and whether the work has finished is up to the caller (read; whether the driver crate's `DeviceBuffer` drop synchronizes, and whether nvJPEG decode is synchronous on the host for the interleaved path, are **not checked**). The same remedy as in the cufft review (finding 3): return a handle that borrows the buffers, or mark `unsafe`. `None` selects the default stream (null handle); the doc does not say so.
5. **`decode_batched` and `encode_image` are `unsafe` but under-specified.** `decode_batched(.., data: &mut [*const c_uchar], lengths: &mut [usize], images: *mut nvjpegImage_t, ..)` asserts `data.len() == lengths.len()` inside the `unsafe` block (so it panics instead of returning `Err`, and the `# Safety` section does not mention it) and never compares them to the batch size given to `decode_batched_initialize`; `&mut` slices are taken though nvJPEG only reads them (the C signature is not `const`, that is why). `encode_image` has 9 parameters (`#[allow(clippy::too_many_arguments)]` is absent; the crate has `[lints] workspace = true`, the workspace lint set was not read), takes `channels: [&DeviceBuffer<u8>; 4]` so an interleaved image needs the same buffer passed four times, and `pitches: [usize; 4]`. Its `# Safety` says "device pointers of the correct size" for what are borrowed `DeviceBuffer`s (the length is checkable, see finding 1). 3 `pub unsafe fn`, 3 `# Safety` sections (grep): the counts match.
6. **`retrieve_bitstream` two-call protocol is a type problem.** `out: Option<&mut [u8]>` returns the needed length for `None`, then is "re-called with a properly-sized buffer"; `length` is initialized from the slice length and passed as in/out (read). A caller that passes a too-small slice gets whatever nvJPEG returns (**not checked**). A `Vec`-returning form (`retrieve_bitstream_vec`) or `Result<usize, Needed>` would be an addition; the current shape is fine to freeze with a doc note. The call also takes `handle` and `state` that are used only as pass-through.
7. **`PixelFormat` is closed, narrower than the vendor enum, and used for two jobs.** 4 variants (`Rgbi`, `Bgri`, `Rgb`, `Y`), 0 `#[non_exhaustive]` (grep: 0 attributes; the 8 textual hits for `non_exhaustive` are `finish_non_exhaustive()` calls in `Debug`). `nvjpegOutputFormat_t` in `-sys` has 7 (`Unchanged`, `Yuv`, `Y`, `Rgb`, `Bgr`, `Rgbi`, `Bgri`), so `Unchanged`, `Yuv` and planar `Bgr` are unreachable, and adding them later is breaking without `#[non_exhaustive]`. The same enum is passed to `encode_image` as `input_format.raw() as c_int` where nvJPEG's encoder uses its own input-format enum (`nvjpegInputFormat_t`); the numeric values of the four overlapping variants agree in the `-sys` source for the output enum, whether they agree with the input enum, and whether `Y` is a valid encoder input, is **not checked** (from memory of the header, unverified). `bytes_per_pixel` returns `1` for `Rgb` with the comment "per-plane", so a caller computing a size from it gets a third of the buffer. Recommendation: `#[non_exhaustive]`; split `PixelFormat` into decode-output and encode-input enums or document the shared meaning.
8. **`ImageInfo` public fields are raw and inconsistent with the rest of the crate.** `pub components: u32`, `pub subsampling: u32` (an untyped vendor code, "e.g. `444`", while the crate re-exports `ChromaSubsampling` and `JpegStream::chroma_subsampling()` returns it, and `ChromaSubsampling` discriminants are 0 to 7, so the "e.g. `444`" in the doc is wrong against `-sys`: `Css444 = 0`), `pub widths: [i32; 4]`, `pub heights: [i32; 4]` (doc: "only the first `components` are valid", unenforced). `components as u32` casts a `c_int` with no check. `width()` and `height()` return `i32` where `JpegStream::frame_dimensions()` returns `(u32, u32)`. `ImageInfo` derives `Copy, Clone, Debug` and not `PartialEq`, `Eq`; it is never consumed by this crate (finding 1), so it is output only: making the fields private with `width()`, `height()`, `components()`, `subsampling() -> ChromaSubsampling` is the cleaner freeze and is breaking after it.
9. **Enum re-exports are vendor `-sys` types.** `pub use ... nvjpegChromaSubsampling_t as ChromaSubsampling` (8 variants) and `nvjpegBackend_t as Backend` (7 variants), both `#[repr(i32)]` with no `#[non_exhaustive]` (read in `baracuda-nvjpeg-sys/src/lib.rs`); each has a `-sys` doc comment of the form "Css444 variant". New nvJPEG backends and subsamplings are plausible (`Lossless` is already the newest in `Backend`; whether it is the newest in NVIDIA's header is **not checked**). `Backend::HybridGpu` in the `Decoder::new` doc does not exist: the variant is `GpuHybrid` (drift). Recommendation: `#[non_exhaustive]` on both in `-sys` (or wrap).
10. **Auto traits and `Error`.** `unsafe impl Send` on 9 types (`Handle` and 8 others) plus `unsafe impl Sync` on `Handle` (10 `unsafe impl`, grep: 9 + 1). `Handle` is `Send + Sync` and shared by `&Handle` in all calls, so concurrent calls on one handle from several threads are possible in safe code; whether nvJPEG allows that for the calls here is **not checked**. The other 8 are `Send` only; `set_quality(&self, ..)` and the other setters mutate through `&self`, correct for `!Sync` (read, not compiled; no `assert_not_sync` test). `Error = baracuda_core::Error<nvjpegStatus_t>` is the standard crate error; `baracuda_core::Error` has `#[non_exhaustive]` (`error.rs:121`, read), `nvjpegStatus_t` is a newtype `(pub i32)`, so new statuses are not breaking. `Drop` impls ignore errors (9 `let _ =`), recorded so the freeze does not claim leak-freedom.
11. **Getters returning `Result`.** `JpegStream::frame_dimensions`, `num_components`, `chroma_subsampling` and `Handle::image_info` call the library and are legitimately fallible; no infallible `Result` getter in this crate (unlike the tensorrt review, finding 6). The three `JpegStream` getters are only meaningful after `parse` succeeded; unchecked.
12. **Documentation drift, 6 places.** (a) README example uses `JpegState` (the type is `State`), `Handle::new(&ctx)` (takes no argument; the test uses `Handle::new()`), `handle.get_image_info(..)` (the method is `image_info`), and `Handle::new(&ctx)?` suggests a context binding the crate does not take; the example is `no_run` in a README that is not part of the crate docs (`include_str`: 0 in `src`), so it never compiles. (b) README "DecodeParams: pick output format (RGB, BGR, RGBI, BGRI, YUV420, YUV422, YUV444)": `set_output_format` takes `PixelFormat`, which has none of the YUV or `Bgr` planar variants (finding 7); the YUV names are chroma subsamplings. (c) README "both poolable": `BufferPinned::new` and `BufferDevice::new` pass a null allocator (no custom allocator or pool); `BufferPinned::new`'s doc says "(pass `None`)" and there is no parameter. (d) README "Batched decode: simple batched + three-phase hybrid" and "Comprehensive coverage"; the batched path is one `unsafe fn` over raw pointers, and `lib.rs` itself says to "reach for `-sys` when adding a function the safe layer doesn't expose yet". (e) `Handle::new` says "default (hybrid) backend"; it calls `nvjpegCreateSimple` (backend meaning **not checked**). (f) `lib.rs` says the crate "compiles on Windows but `nvjpeg()` returns `LoaderError::LibraryNotFound`"; the README does not mention a platform limit. Also `lib.rs` points to `baracuda-nvimagecodec` as the replacement while README says "fully supported": reconcile before the freeze (a deprecation decision).
13. **Dependencies, feature gating, tests, unsafe.** `Cargo.toml` has 6 dependencies; `baracuda-core` (1 hit in `src`), `baracuda-nvjpeg-sys` (3), `baracuda-driver` (1 in `src`, 2 in tests) are used. **`baracuda-types`, `baracuda-cuda-sys` and `thiserror` are not**: 0 hits for each of `baracuda_types`, `baracuda_cuda_sys`, `thiserror` in `src/lib.rs` and `tests/gpu_smoke.rs` (control: the same grep finds `baracuda_core`, `baracuda_driver` and `baracuda_nvjpeg_sys`); three unused dependencies. No feature gating: 0 `cfg` in `src/lib.rs`, one feature (`device-tests`, tests only), no `[package.metadata.docs.rs]`, and the library is loaded at runtime, so all 65 rows render on docs.rs (the facade `baracuda` gates it as `nvjpeg = ["dep:baracuda-nvjpeg", "driver"]`, `Cargo.toml:46`). Tests: 1 `#[test]` (`decode_tiny_jpeg` in `tests/gpu_smoke.rs`, `device-tests`, decodes a 1x1 grayscale JPEG with `Handle::new`, `image_info`, `State::new`, `decode_interleaved` `Rgbi`); no test names for `decode_planar`, `decode_batched*`, `Decoder`, `JpegStream`, the buffers, `DecodeParams`, or the encoder (grep for each of these names in `tests/`: 0 except the ones above), and none for a too-small buffer (finding 1) or a handle dropped first (finding 2). Unsafe: 40 `unsafe {` blocks, 0 `SAFETY` comments (grep), 3 `# Safety` doc sections on 3 `pub unsafe fn`; every FFI call block has no comment, mostly one-line.

## Recommended order

1. Findings 1 and 2 (soundness of safe code): size checks (or `unsafe`) on both decode functions, and `Handle` ownership carried by the child types; finding 3 with them, since it changes the same signatures.
2. Findings 7, 8, 9 together (`PixelFormat`, `ImageInfo`, re-exported enums: `#[non_exhaustive]`, private fields, a typed `subsampling`), then finding 4 (stream and buffer ties) as one design pass with the cufft one.
3. Finding 13 (three unused dependencies, tests) and finding 12 (README rewritten against the code, the `HybridGpu` doc fix) as cleanup; findings 5, 6, 10, 11 are doc notes.

Nothing in this review was built, run, or measured against NVIDIA's documentation: findings 7 (partly), 8, 11, 12 and 13 are read from source and greps with the controls stated; findings 1 to 5, 9 and 10 rest in part on nvJPEG behaviour recorded here as **not checked**.
