## Findings

1. **Safe `exec_*` methods take buffers of unchecked length.** Every `exec_*` method (`Plan1d::exec_r2c`, `exec_c2r`, `exec_c2c`; `Plan2d::exec_c2c`; `Plan3d::exec_c2c`; `PlanMany::exec_r2c`/`c2r`/`c2c`; the 9 `exec_d2z`/`z2d`/`z2z`) is a safe `pub fn` that takes `&mut DeviceBuffer<T>` for input and output and passes `input.as_raw().0 as *mut T` to cuFFT. `src/lib.rs` has 3 `assert` (all in `unsafe fn`s, findings 4 and 10) and 7 `.len()` (none comparing a buffer length to a plan size; grep, same grep finds the 3 asserts, so it can see them). A plan made for `nx = 1024` executed on a 4-element `DeviceBuffer` compiles, is not `unsafe`, and lets cuFFT read and write past the allocation on the device. The plan types do not record their transform size or kind, so there is nothing to check against (`Plan1d { handle }` is the whole struct). Decision before the freeze: store `n`/rank/kind in the plan and check `len()` before each call (returns `Err`; observable, so it must precede the freeze), or make the `exec_*` functions `unsafe`. Breaking after the freeze either way.
2. **Exec kind versus plan kind is not checked, and the asymmetry between plan types is accidental.** `Plan1d::exec_c2c` on a plan built with `Transform::R2C` is a safe call; what cuFFT does (an error code is expected, `CUFFT_INVALID_TYPE`) is **not checked** against NVIDIA's documentation. The method sets differ without a stated reason: `Plan1d` has `set_stream`, `exec_r2c`, `exec_c2r`, `exec_c2c` and the 3 double-precision methods; `Plan2d` has `exec_c2c` and the 3 double ones but **no `set_stream`, no `exec_r2c`, no `exec_c2r`**; `Plan3d` has `set_stream` and `exec_c2c` only (**no R2C, C2R or double**, although `Plan3d::new` accepts `Transform::D2Z`); `PlanMany` has all of them; `Plan` has `set_stream` and no `exec_*` at all. So a `Plan2d` cannot be bound to a stream through the safe API, and a 3-D real transform cannot be run. Typed plans (`Plan2d<R2C>`) or one plan type with a stored kind would remove findings 1 and 2 together.
3. **The stream is not tied to the plan, and the buffers are not tied to the work.** `set_stream(&self, stream: &Stream)` passes `stream.as_raw()` and keeps nothing: no lifetime, no clone. `baracuda_driver::Stream` destroys its stream when the last owner drops (`impl Drop for StreamInner`, `stream.rs:459`), so `plan.set_stream(&s); drop(s); plan.exec_c2c(..)` runs cuFFT on a destroyed stream from safe code (read, not run). Separately, `exec_*` borrow the buffers only for the call, while cuFFT launches asynchronously on the bound stream, so after the method returns the buffers can be dropped (freed) while the transform is still queued. Whether the driver's `DeviceBuffer` drop synchronizes is a question for that crate and is **not checked here**. Decision: hold a `Stream` clone in the plan (`Plan { stream: Option<Stream> }`) and make `exec_*` return a handle borrowing the buffers until the stream completes, or document and mark `unsafe`.
4. **`PlanMany::new` is a safe function with unchecked array lengths.** `rank: i32`, `n: &mut [i32]`, `inembed: Option<&mut [i32]>` and `onembed: Option<&mut [i32]>` go to `cufftPlanMany` as raw pointers; cuFFT reads `rank` entries of each. Nothing checks `n.len() == rank` (the safe `new` has no assert; the `unsafe fn Plan::make_plan_many` checks it with `assert_eq!(n.len() as i32, rank, ..)`, `lib.rs:866`, so the check exists in the sibling and is missing here). `PlanMany::new(8, &mut [1, 2], ..)` is a host over-read from safe Rust. The signature also takes 10 positional parameters (4 `i32` strides/dists in a row, 2 optional slices), easy to transpose. Decision: check `n.len() == rank` and each present embed length (`Err`, observable), take a builder or a `Layout` struct, and drop the `&mut` that is only there because cuFFT's C signature is not `const` (the docs say cuFFT may write them in some versions: **not checked**).
5. **`unsafe impl Send` on three types, and the auto traits are `Sync` as well.** `cufftHandle` is `c_int` (`baracuda-cufft-sys/src/lib.rs:23`), so every plan type is `Send + Sync` by the auto-trait rules whether or not the explicit `unsafe impl Send` (4 of them, on `Plan1d`, `Plan2d`, `Plan3d`, `Plan`) exists; the 4 impls are redundant and `PlanMany` has none and is `Send` all the same (read, not compiled). `Sync` lets two threads call `exec_c2c(&self, ..)` on one plan at once and `set_stream(&self, ..)` mutate it under a reader; whether cuFFT allows that is **not checked** (my recollection is that a plan is not safe for concurrent execution; unverified). Decision: add a `PhantomData<*mut ()>` to opt out of `Sync` (breaking after the freeze) or confirm concurrent use is legal.
6. **`set_stream` takes `&self`, the setters on a plan mutate it, and `Drop` hides failures.** The four `Drop` impls ignore every error (`let _ =` and `if let Ok(c) = cufft()`); a plan whose library did not load leaks the handle silently. Acceptable for `Drop`; recorded so the freeze does not later claim leak-freedom.
7. **Free functions take a raw `cufftHandle` in safe signatures.** `set_auto_allocation(plan: cufftHandle, auto: bool)`, `get_size(plan: cufftHandle)`, `callback::clear`, `callback::set_shared_size` are safe `pub fn`s on a bare `c_int`: any integer compiles; a handle that belongs to a live plan owned by other code is mutated (`set_auto_allocation(other.as_raw(), false)` changes another object's behaviour) and a stale handle is an error return or, if reused by cuFFT, another plan. The `unsafe` ones (`set_work_area`, `xt::set_gpus`, `xt::malloc`, `xt::free`, `xt::memcpy`, `xt::exec_descriptor`, `callback::set`, `Plan::make_plan_many`, `Plan::make_plan_many64`: 9 `pub unsafe fn`, each with a `# Safety` section, 9 sections by grep) take the same bare handle. These belong on the plan types (`plan.set_auto_allocation(..)`), not on a handle integer; moving them is breaking after the freeze. `xt::malloc(plan, subformat: i32)`, `xt::memcpy(.., ty: i32)` take raw integers where cuFFT has enums.
8. **Enums.** `Transform` (6 variants), `Direction` (2), `CallbackType` (8, `#[repr(i32)]`) are closed (0 `non_exhaustive` in the crate, grep). `Transform` is the set of 6 cuFFT types and complete; a new cuFFT type (half precision `cufftXt` transforms exist, from memory, **not checked**) would be a new variant. `CallbackType`'s discriminants mirror `cufftXtCallbackType` and are passed as `cb_type as i32`; a wrong discriminant is a wrong call. Recommendation: `#[non_exhaustive]` on `Transform` and `CallbackType`; verify the 8 discriminants against the header; leave `Direction` closed (forward/inverse cannot grow). `Direction` derives `Default` (Forward).
9. **`Plan` (two-step) has no `exec_*` and no way to know it is finalized.** `Plan::create()` returns a plan that is "unusable until you finalize it"; `make_plan_1d`/`2d`/`3d`/`many`/`many64` return the workspace size and can be called twice on one handle (what cuFFT does on a second `MakePlan` is **not checked**). The type has `set_stream` and `as_raw` and no way to execute, so the only use is `as_raw()` into a raw `-sys` call. A finalized plan should be a different type (`Plan::create()` -> `UnplannedPlan`, `make_plan_*(self) -> Plan1d`), which would also remove the Plan1d/Plan duplication; breaking after the freeze. The `estimate_1d`/`2d`/`3d` free functions duplicate `make_plan_*` sizing without a plan.
10. **Panics inside `unsafe fn`s.** `Plan::make_plan_many`, `make_plan_many64` and `callback::set` use `assert_eq!` for a length mismatch (3 asserts): a documented-`# Safety` unsafe function that also panics on a violated precondition. The first two document `n` "of length `rank`" under `# Safety`, so the assert is a check on a safety precondition: fine, but `PlanMany::new` (finding 4) shows the other case, with no check. Decide one policy: check and return `Err`, never panic.
11. **Documentation drift, 5 places.** (a) `README.md` calls the enum `TransformType` (the code has `Transform`; the README example does not compile) and shows `plan.exec_c2c(&mut data, Direction::Forward)` (the method takes `input`, `output`, `direction`; in-place is not expressible because both are `&mut`, so cuFFT's in-place transform is unreachable from the safe API). (b) README lists `PlanXt1d` and `PlanXtMany` (0 matches in `src/`; the code has the free `xt` functions, finding 7). (c) README says stream binding is `Plan::set_stream` and a work-area override is `Plan::set_work_area`; `set_work_area` is a free function and `Plan2d` has no `set_stream` (finding 2). (d) The crate header says "Multi-GPU (`cufftXt`) and batched descriptor-style plans land in a follow-up" while `xt`, `PlanMany` and `Plan` ship in the same file. (e) The README is not included in the crate docs (`include_str!`: 0), so its example is never compiled by a test; the `lib.rs` doctests are `no_run` (they are type-checked).
12. **Dependencies and tests.** `Cargo.toml` has six dependencies; `baracuda-types`, `baracuda-core`, `baracuda-cufft-sys`, `baracuda-driver` are used in `src/lib.rs`; `baracuda-cuda-sys` and `thiserror` do not appear in `src/`, `tests/` or `examples/` (grep: `baracuda_cuda_sys` 0, `thiserror` 0; control: `baracuda_driver` and `baracuda_types` both found by the same grep). Two unused dependencies, as in cusolver finding 9. Tests: 3 `#[test]` in `tests/gpu_smoke.rs`, all behind `device-tests` (`c2c_forward_then_inverse_roundtrip`, `version_is_queryable`, `strided_c2c_columns_match_contiguous`): nothing exercises `Plan2d`, `Plan3d`, R2C/C2R, double precision, `xt`, `callback`, `Plan::make_plan_*`, or a wrong-size buffer (finding 1).

## Recommended order

1. Findings 1, 2, 3, 4 (soundness of safe code). One design covers 1, 2 and 4: a plan that stores `n`, rank, kind and layout, with `exec_*` checking them, and a `Stream` held by the plan (3).
2. Finding 7 (move raw-handle free functions onto the plan types) and finding 9 (two types for the two-step flow), decided together with 2.
3. Findings 5, 8 (small: `Sync`, `#[non_exhaustive]`, discriminants against the header).
4. Findings 6, 10, 11, 12 as cleanup (README rewritten against the code, two unused dependencies removed).

Nothing in this review was built, run, or measured against NVIDIA's documentation: findings 1, 4, 7, 11, 12 are read from source and greps with the controls stated; findings 2, 3, 5, 8, 9 rest in part on cuFFT behaviour recorded here as **not checked**.
