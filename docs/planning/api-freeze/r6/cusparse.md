## Findings

1. **Descriptor constructors do not check the extents they document.** `SpMat::csr` says "`row_offsets.len()` must equal `rows + 1`; `col_indices.len()` and `values.len()` must equal `nnz`" and checks none of it: `src/lib.rs` has 3 `.len()` (one is `DnVec::new`'s `values.len() as i64`, the other two are in prose) and 0 `assert` (grep; the same grep finds the `DnVec` line, so it can see them). `csc`, `bsr` and `coo` take the same unchecked `rows`/`cols`/`nnz`/block dimensions as `i64`, and `DnMat::new(rows, cols, ld, order, values)` does not compare `ld * cols` (or `ld * rows` for row-major) with `values.len()`. A descriptor with `nnz` larger than the buffers is a safe call that hands cuSPARSE a descriptor that reads and writes past the allocation on the next `spmv` (read, not run). The lifetimes are right (each descriptor borrows its buffers `&'buf mut`, so they cannot be freed while it lives, which the crate header claims and the types deliver for the descriptors), but the sizes are not enforced. Decision before the freeze: check lengths and return `Err` (observable, so it precedes the freeze), or make the constructors `unsafe`. Breaking after the freeze either way.
2. **Workspace buffers are borrowed for one call, but cuSPARSE keeps using them.** `spsv_analysis` and `spsm_analysis` take `workspace: &mut DeviceBuffer<u8>` and `spsv_solve`/`spsm_solve` take no workspace at all; the plan (`SpSVPlan`, `SpSMPlan`) holds only the descriptor. My recollection of the cuSPARSE documentation is that the external buffer given to `*_analysis` must stay valid and unmodified until `*_solve` finishes (the descriptor keeps the pointer); if so, `spsv_analysis(.., &mut ws); drop(ws); spsv_solve(..)` is a use-after-free from safe code. **Not checked against NVIDIA's documentation** (docs.nvidia.com was not read). The same applies to `spmm_preprocess` and `sddmm_preprocess` ("subsequent [`spmm`] calls ... are faster"), whose `workspace` is borrowed only for the preprocess call. The three `spgemm_*` functions document the buffer contract in `# Safety` (`unsafe fn` for two of them), so the pattern is already known to the crate. Decision: make the plan own the workspace (`SpSVPlan` holding a `DeviceBuffer<u8>`) or borrow it for the plan's lifetime; breaking after the freeze.
3. **Sizes and shapes between operands are not checked, and the stream is not tied to anything.** `spmv`, `spmm`, `spsv_*`, `sddmm`, `axpby`, `rot` take descriptors whose shapes the Rust types do not relate; whether cuSPARSE rejects a mismatch (an error code is expected; `INVALID_VALUE`) or reads out of range is **not checked**. `workspace: &mut DeviceBuffer<u8>` is never compared with the value the matching `*_buffer_size` returned (`workspace.len()` is never read: the 3 `.len()` are not that). `Handle::set_stream(&self, stream: &Stream)` keeps the raw stream and no clone, and `baracuda_driver::Stream` destroys itself when its last owner drops (`StreamInner`'s `Drop`, `stream.rs:459`), so `handle.set_stream(&s); drop(s); spmv(..)` runs on a destroyed stream (read, not run); this is the same shape as cuFFT finding 3 and cuBLAS. Operations are asynchronous on that stream while the buffers are borrowed only for the call; whether `DeviceBuffer::drop` synchronizes is a question for the driver crate and is **not checked here**.
4. **Five `pub unsafe fn`, each with a `# Safety` section (5 sections, grep), and `spgemm_copy` is safe.** `set_csr_pointers`, `set_csc_pointers`, `set_coo_pointers` take `*mut c_void` ("must stay valid until the next operation on this descriptor completes") and rebind a descriptor whose `'buf` lifetime still names the old buffers, so the type system keeps the old buffers alive and the new ones unnamed: the descriptor's own safety story (finding 1) no longer holds after a rebind. `spgemm_work_estimation` and `spgemm_compute` take `*mut c_void` scratch and a `&mut usize` size. `spgemm_copy` is a safe `pub fn` that must follow the two unsafe phases with the same plan (the "3-phase" contract is in prose; the plan type does not track the phase). Stable with the note that the safe and unsafe halves of one 3-phase protocol sit side by side; a typed state (`SpGEMMPlan<Estimated>`) would be breaking later.
5. **Enums and re-exports.** `Op` (3 variants), `Order` (2), `Fill` (2), `Diag` (2) are closed: 0 `#[non_exhaustive]` attributes (the 3 grep hits for `non_exhaustive` are `finish_non_exhaustive()` calls in the `Debug` impls). All four are complete for what they model; recommendation: leave `Order`, `Fill`, `Diag` closed, `#[non_exhaustive]` on `Op` as a precaution (cuSPARSE's `cusparseOperation_t` has 3 members; whether it grows is **not checked**). `Op` is the fourth `Op` in the workspace (cuBLAS, cuSOLVER, here; same `N`/`T`/`C`), each a separate type. The one re-export row covers 8 `-sys` enums renamed (`SpMVAlg`, `SpMMAlg`, `SpGEMMAlg`, `SpSVAlg`, `SpSMAlg`, `SDDMMAlg`, `Csr2CscAlg`, `IndexBase`): their variants are vendor definitions and part of this crate's public API, and whether the `-sys` enums are `#[non_exhaustive]` I did not read; `Error` is `baracuda_core::Error<cusparseStatus_t>`, so the freeze also fixes the identity of `baracuda_core::Error` (as in cutensor finding 2).
6. **Thread-safety.** `Handle`, `SpMat<T>`, `DnVec<T>`, `DnMat<T>` have `unsafe impl Send` (4 impls, grep) and no `Sync`; the three plan types have neither (raw-pointer field, so `!Send` and `!Sync` by auto traits; not compiled). `unsafe impl<T> Send for SpMat<'_, T>` carries no `T: Send` bound (a descriptor of `T` cannot hold a `T`, so this is harmless in practice). Whether a cuSPARSE handle may move across threads, and whether a descriptor may move without its handle, is **not checked**; there is no `assert_send`/`assert_not_send` test (grep: 0).
7. **Fixed index type, base and compute type.** Every constructor hardcodes `cusparseIndexType_t::I32I` and `cusparseIndexBase_t::Zero` (`csr`, `csc`, `bsr`, `coo`, lines 352, 353, 354 and the others), so 64-bit indices and one-based matrices cannot be described; `csr2csc_ex2` takes an `idx_base: IndexBase` and `m`, `n`, `nnz` as `i32`, so one crate has two different views of the index base. Every operation passes `T::data_type()` as the compute type (`spmv`: `T::data_type()`), so mixed-precision compute (for example `f16` values with `f32` compute) is not expressible. `SparseScalar` is sealed to `f32`, `f64`, `Complex32`, `Complex64`. These limits are legitimate scope for a first release; they are freeze decisions because adding `I64I` later means a new constructor family or a breaking signature.
8. **Legacy aliases with no legacy.** `pub type CsrMatrix<'buf> = SpMat<'buf, f32>` and `pub type DenseVector<'buf, T> = DnVec<'buf, T>` are "kept for callers from v0.1"/"Legacy alias", in a crate whose only releases are `0.1.0-alpha.N`; the README's "typed descriptor builders (`SparseMatrixCsr::new`, etc.)" names a type that does not exist (grep: 0 `SparseMatrixCsr` in `src/`). Decision: delete both aliases (2 of the 4 `type` rows) or keep and say why; fix the README.
9. **Documentation drift.** (a) `Cargo.toml`'s description is "(generic-API SpMV at v0.1)" for a crate that covers SpMM, SpGEMM, SpSV, SpSM, SDDMM and conversions. (b) The README names `SparseMatrixCsr::new` (finding 8). (c) The crate header says descriptors "borrow the underlying [`DeviceBuffer`]s and tie their lifetime to them so the buffers can't be freed while cuSPARSE is still holding references": true for the descriptors (finding 1) and false for workspaces and for asynchronous work (findings 2, 3). (d) The README says workspace handling is "explicit and allocation-free at op time" and does not mention that the buffer must outlive later calls (finding 2).
10. **Dependencies and tests.** `Cargo.toml` has six dependencies; `baracuda-types`, `baracuda-core`, `baracuda-cusparse-sys`, `baracuda-driver` are used; `baracuda-cuda-sys` and `thiserror` do not appear in `src/` or `tests/` (grep: `baracuda_cuda_sys` 0, `thiserror` 0; control: `baracuda_core` 1 in `src/lib.rs`). Two unused dependencies, as in cufft and cusolver. 53 `unsafe {` blocks and 0 `SAFETY` comments (grep). One `#[test]`, `csr_spmv_matches_cpu_reference`, behind `device-tests`: nothing exercises CSC/COO/BSR, SpMM, SpGEMM, SpSV/SpSM, SDDMM, the conversions, `Complex*`, or a wrong-extent descriptor (finding 1).

## Recommended order

1. Findings 1, 2, 3 (soundness of safe code): validated constructors, plans that own their workspace, a stream the handle keeps alive. One design.
2. Finding 7 (index/base/compute type in the descriptor types) decided with 1, since the constructors change anyway.
3. Findings 4, 5, 6 (small: typed GEMM phases, `Op` `#[non_exhaustive]`, thread-safety checks).
4. Findings 8, 9, 10 as cleanup (aliases, README and description, two unused dependencies, tests).

Nothing in this review was built, run, or measured against NVIDIA's documentation: findings 1, 7, 8, 10 are read from source and greps with the controls stated; findings 2, 3, 5, 6 rest in part on cuSPARSE behaviour recorded here as **not checked**.
