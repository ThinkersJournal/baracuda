## Findings

1. **`get_next_record` swallows every error and uses unnamed status numbers.** The `match` at `lib.rs:126-134` maps `SUCCESS` to `Ok(true)`, status `10` or `11` to `Ok(false)`, and any other status to `let _ = check(err); Ok(false)` (`lib.rs:130-133`): a real CUPTI error (bad buffer, invalid parameter) is reported as "end of records", the `check` result is dropped, and the function can never return `Err` after the loader lookup. `10`/`11` are bare literals (`status.0 == 11 || status.0 == 10`, `lib.rs:129`); `-sys` names `CUptiResult` constants for 0-8, 13, 14 and 999 only (read, `-sys` lines 31-60), so 10 and 11 have no name anywhere. Which CUPTI statuses they are was **not checked** against NVIDIA's header. Decision before the freeze: return `Result<Option<..>>` and propagate real errors, name the two statuses in `-sys`. Changing `Ok(false)`-on-error to `Err` later is a behaviour change callers can observe.
2. **The record-walker API cannot return a record in its type and the doc disagrees with it.** The doc (`lib.rs:111-112`) says it "Returns the next `*mut CUpti_Activity` pointer, or `None` when exhausted"; the signature returns `Result<bool>` (`lib.rs:118-122`) and the next record comes back through `record_inout: &mut *mut c_void`. The activity-record layout structs this walker is meant to feed are not in this crate at all: `CUpti_ActivityKernel9` and `CUpti_ActivityMemcpy5` live in `-sys` (`-sys` lines 243 and 323, the only two `pub struct` besides `CUptiResult` and the `Cupti` loader, grep `pub struct\|pub enum`: 4 hits), are `#[repr(C)]` mirrors with the comment "partial — KERNEL + MEMCPY" (`-sys` line 236), and are not re-exported from `baracuda_cupti::activity`. So the safe crate offers a loop with a `*mut c_void` cursor and the caller must name a `-sys` struct and cast. This is the hardest shape to change after 1.0: record structs mirroring a C layout are version-suffixed (`Kernel9` is "CUPTI 12.x+", `-sys` lines 238-242), their field order and widths became public API the moment they are public, and I have **not verified them against `cupti_activity.h`** (the read header of `Kernel9`, lines 243-262, has `cache_config: u32` then `shared_memory_config: u8` then `registers_per_thread: u16`, which differs from my recollection of the header; recollection only, **not checked**). Decision: do not freeze the record structs with this crate (keep them in `-sys` as explicitly versioned and unstable), and give `activity` a typed iterator over a completed buffer before the freeze; a typed iterator added later is non-breaking, but changing `get_next_record`'s signature is breaking.
3. **Callbacks passed to C: lifetime and panic rules are left to the caller and not fully stated.** `register_callbacks` (`lib.rs:100-109`) takes two `unsafe extern "C" fn` pointers (typedefs at `-sys` lines 136-150: request gets three out-pointers, complete gets `ctx`, `stream_id`, `buffer`, `size`, `valid_size`); `Subscriber::subscribe` (`lib.rs:159-170`) takes a `CUpti_CallbackFunc` (`-sys` line 172) plus `user_data: *mut c_void`. Both are `unsafe fn` with a `# Safety` section. The `register_callbacks` section says the pointers "must be valid for the lifetime of the activity session" and that CUPTI calls them "from driver-owned threads" (`lib.rs:98-99`); it does not say: registration is process-global and has no unregister in this crate (0 wrapper for it; the loader table in `-sys` was not enumerated here), the buffer the request callback hands out must be freed by the complete callback (CUPTI behaviour, **not checked**), `user_data` must be `Send`/`Sync` in effect since it is used from CUPTI's threads, or that a panic must not unwind out of the callback. The panic point: a Rust `extern "C" fn` that panics aborts rather than unwinding on current stable toolchains (from memory, **not checked** against this workspace's `rust-version`), and the crate has no `catch_unwind` (grep for `catch_unwind` and `extern "C"` in `lib.rs`: 0 hits; control: `unsafe {` finds 39 in the same file, so the grep works), so the safety is entirely the caller's; the doc should say so. Function-pointer types are non-`Option`, so the "no callback" case cannot be expressed and a null pointer is a validity violation before the call even happens; if CUPTI accepts a null here it is not reachable (not checked).
4. **`Subscriber` thread-safety is accidental and its `Drop` races in-flight callbacks.** `Subscriber { handle: CUpti_SubscriberHandle }` (`lib.rs:147-150`), where the handle is `*mut c_void` (`-sys` line 176), so it is `!Send` and `!Sync` by the auto-trait rules (not compiled; no `assert_not_send` test). There are 0 `unsafe impl` in the file (grep, positive control: `unsafe {` finds 39 in the same file), so no claim was ever made. CUPTI invokes the callback from other threads (`lib.rs:99`, for the activity callbacks; for the Callback API, from memory, the thread making the CUDA call, **not checked**), yet the owner of the `Subscriber` can be neither moved to another thread nor shared. `Drop` (`lib.rs:195-203`) calls `cuptiUnsubscribe` and ignores the status; a callback running on another thread while the `Subscriber` drops dereferences `user_data` whose validity the `# Safety` section ties to "until the returned subscriber drops" (`lib.rs:157-158`), which CUPTI's unsubscribe may or may not wait for (**not checked**). Also `enable_callback(&self, enable: bool, domain: u32, cbid: u32)` and `enable_domain` take `domain` and `cbid` as raw `u32`; `CUpti_CallbackDomain` is a module of 7 `u32` constants (`-sys` lines 154-170, read), not an enum, so there is no type to put `#[non_exhaustive]` on and no way to reject an unknown value. Decision: state the `Send`/`Sync` claim (with a `SAFETY` argument) before the freeze; consider a typed `Domain` newtype (adding it later is non-breaking only if the `u32` signatures are kept as well).
5. **`#[non_exhaustive]`: nothing in this crate needs it today, and the enum-like vocabulary is untyped constants.** 0 `non_exhaustive` in `lib.rs` (grep; control: the same pattern finds `baracuda-core/src/error.rs:20`, `:122`, `:169` and `-sys` `finish_non_exhaustive` at line 528, so the pattern works); 0 public enums in the crate (grep `pub enum` is 0 over `lib.rs`; the control is the 2 `pub struct` found by `pub struct`). The 2 public structs, `Subscriber` and `Group`, have only private fields, so they can grow. The `non_exhaustive` census column agrees: 0 for all 49 rows (awk, 0 rows non-zero). The enum-like types the API is built on are `-sys` modules of `u32` constants (`CUpti_ActivityKind`, 15 constants read at `-sys` 103-124; `CUpti_CallbackDomain`, 7), re-exported as a "type" (`lib.rs:69-71`, `:142-144`): CUPTI adds activity kinds every release (from memory, **not checked**), and a module of constants has no exhaustiveness to protect, so it is forward-compatible by construction, at the price of `enable(kind: u32)` and `disable(kind: u32)` (`lib.rs:74`, `:81`) accepting any `u32`. 6. **`activity::enable`, `disable`, `flush_all` take raw integers.** `kind: u32` (`lib.rs:74`, `:81`) and `flags: u32` with the doc "`0` = default; `1` = force-flush" (`lib.rs:87-88`). Typed wrappers added later are non-breaking; this is a "decide, do not rush" row. `flush_all` triggers the user's complete callback on the calling thread or others (from memory, **not checked**), so it is a callback-reentrancy point that the safe signature does not mention.
7. **`profiler`: 14 identical `unsafe fn(params: *mut c_void)` wrappers pin an untyped signature.** All 14 (`lib.rs:389-498`) have one shape, `pub unsafe fn <name>(params: *mut core::ffi::c_void) -> Result<()>`, and 13 of 14 carry the same two-word safety section "See NVPerf SDK." (`initialize` has the one at `lib.rs:387-388`: "See NVPerf SDK for the expected `params` struct."). So the `# Safety` count is 20 (grep `# Safety`; 20 = the 20 `pub unsafe fn`, matched one for one by count only, not by pairing) but 14 of them state no condition a caller can check (not null, struct size field set, struct matches the CUPTI version, session state). The CUPTI Profiler Host `CUpti_Profiler_*_Params` structs carry a `structSize` field set by the caller (from memory, **not checked**); a wrong or unset size is a read/write past the allocation from a function whose only contract is "see the SDK", and the attribution to the NVPerf SDK is also **not checked** (the structs I recall live in CUPTI's own `cupti_profiler_target.h`, from memory). Keeping these `unsafe` is right. The freeze problem is permanence: when the crate later adds typed params, either the 14 names are reused with a new signature (breaking) or they stay and typed siblings are added (surface doubles, the issue nccl finding 8 and nvml finding 2 raised). Decision: move them under `profiler::raw` (or mark the module "unstable until typed") so the typed API can take the top-level names, and write real `# Safety` text for each (the pointer must be non-null, point to the matching `CUpti_Profiler_<Name>_Params` with `structSize` set, and live for the call). Also note `lib.rs:17` says "we expose raw-pointer passthroughs because the struct layouts are version-sensitive", i.e. the crate knows these are placeholders.
8. **`event::Group`: handle ownership is right, three smaller points.** `Group { raw: CUpti_EventGroup }` (`lib.rs:236-238`, `*mut c_void` at `-sys` line 361) frees in `Drop` (`lib.rs:301-309`, error ignored like the other crates), no `Clone`, no `Copy`; `!Send`/`!Sync` automatically (0 `unsafe impl`, grep with the control in finding 4). (b) `Group::read` reads exactly one `u64` (`let mut buf = [0u64; 1]`, `size = size_of::<[u64; 1]>()`, `lib.rs:289-291`) and documents "returns the single first bucket; for per-SM multi-value reads use the raw sys function" (`lib.rs:283-285`): on a multi-instance event domain CUPTI wants a buffer sized `instance_count * 8` (from memory, **not checked**), so `read` may return `Err` rather than a short value on such domains; the doc does not say so. The second argument passed is a literal `0` (`lib.rs:291`), a flags value that has no name. (c) `Group::drop` does not call `disable` first; if CUPTI requires a disabled group before destroy (from memory, **not checked**) the destroy status is dropped silently. `event::id_from_name` and `metric::id_from_name` map an interior NUL to a synthetic `Error::Status { ERROR_INVALID_PARAMETER }` (`lib.rs:225-227`, `:322-324`), acceptable and consistent with the nvml crate. 9. **`metric::get_value` and `get_attribute`: a contradictory contract.** `get_value` is `pub unsafe fn` whose `# Safety` says "`event_ids` and `event_values` must have equal length" (`lib.rs:353`), but the body's first statement is `assert_eq!(event_ids.len(), event_values.len())` (`lib.rs:364`), a panic on violation. The condition is therefore checked, not a safety precondition; the real unsafe input is `metric_value: *mut c_void` ("must be a writable buffer sized for the metric's value type", `lib.rs:353-354`). Decision: pick one (drop the `assert_eq!` and keep the safety line, or return `Err(ERROR_INVALID_PARAMETER)` and trim the safety text). Both slice parameters are `&mut` (`lib.rs:358-359`) though CUPTI only reads them, which forces callers to give a mutable borrow of data they want to keep (the source of the `*mut` in the call is `as_mut_ptr`, `lib.rs:372-373`; whether CUPTI mutates them is **not checked**); changing `&mut [..]` to `&[..]` later is breaking for none of the callers (a `&mut` coerces to `&`) but a `&[..]`-to-`&mut` flip is, so this is a safe-direction change, listed for the record. `get_attribute(.., size: &mut usize, value: *mut c_void)` with `attrib: u32` (`lib.rs:336-341`) is a generic untyped getter; same decision as finding 6.
