## Findings

1. **The crate is a raw FFI pass-through, not the "safe wrapper" its metadata claims.** Of the 49 expanded fn, 30 are `unsafe`; every launch (`compress_async`, `decompress_async`, 12 of them, and the 3 `get_decompress_size_async`) takes `*const *const c_void`, `*const usize`, `*mut c_void` and a `stream: *mut c_void`. There is no typed buffer, no `Stream`, no batch-length check: `Cargo.toml` has no `baracuda-driver` dependency at all (see finding 7). `Cargo.toml` still says "Safe Rust wrappers ... Scaffolding at v0.1" and `lib.rs` ends "this crate is a thin FFI surface". Soundness of the safe subset (19 fn): the size queries (`compress_get_temp_size`, `compress_get_max_output_chunk_size`, `decompress_get_temp_size` x5, `lz4_*_alignment`, `status_string`, `probe`) take only plain values and write to a local `usize` / `nvcompAlignmentRequirements_t`, so I found no way to reach UB from them in source (what nvCOMP does with an out-of-range `opts` value is **not checked**). The freeze decision is not a bug but a scope one: either freeze the `unsafe` pointer surface as the permanent API (the README and `lib.rs` header must then say so) or reserve room for a typed layer; a typed layer added later does not break this surface if it lives in new items.
2. **Inconsistent per-codec surface.** The `lib.rs` module doc says "Every codec shares the same flow: `compress_get_temp_size` ... `decompress_get_temp_size`", and the README says all codecs have "temp-size queries, and chunk-size queries". The five macro modules have them (3 sizing fn each); `deflate`, `bitcomp`, `ans`, `cascaded` have only `compress_async` and `decompress_async` (read: 2 fn per module in the census and the source). Their opts types are different too: the macro modules take a separate decompress-opts type, the four hand-written ones take none (`decompress_async` has no `opts` parameter in the source). So a caller cannot size a Bitcomp or Cascaded temp buffer through this crate. Whether nvCOMP offers those entry points is **not checked**; if it does, they are missing, and adding them later is not breaking. Decision: complete the four modules before the freeze or state in the docs which codecs have which functions.
3. **Doc and signature gaps on the hand-written modules.** The 8 `compress_async`/`decompress_async` fn in `deflate`, `bitcomp`, `ans`, `cascaded` have a doc that is only `# Safety` (no summary line, so rustdoc's one-line description is empty) pointing at `lz4::compress_async` / `lz4::decompress_async`; `raw::compress_async`/`decompress_async` have no `# Safety` at all (suppressed with `#[allow(clippy::missing_safety_doc)]`, reason given in the source). 22 `pub unsafe fn` in the file (textual, macro counted once) against 20 `# Safety` headings: the 2 are the `raw` pair. Alignment helpers exist only for LZ4 (`lz4_compress_alignment`, `lz4_decompress_alignment`) plus the generic `unsafe` `compress_alignment` / `decompress_alignment`; `*_get_decompress_size_async` exists for LZ4, Snappy and Zstd only, while its generic doc says "Shared shape across LZ4/Snappy/Zstd/GDeflate/Gzip/Deflate/ANS/Bitcomp/Cascaded".
4. **`raw::*` and `crc32::*` take untyped pointers where a type exists or is knowable.** `crc32::get_heuristic_conf(.., config_out: *mut c_void)`, `search_conf`, `compute_async(.., config: *const c_void, ..)` take `*mut c_void` for an `nvcompCRC32Config_t` the crate does not export, and `get_properties(props: *mut c_void)` says the layout is "headers-only" and points the caller to `baracuda_nvcomp_sys::PFN_nvcompGetProperties`. `raw::decompress_async` is documented "for any codec that follows the standard 10-argument signature" but its `pfn` has no `opts` argument and no `device_statuses` input, while the 5 macro-generated `decompress_async` have 11 arguments (`opts` and `dev_status_ptrs`); whether any `-sys` PFN matches the `raw` shape is **not checked**. Whether anything uses `raw` was not established: a grep for `baracuda_nvcomp` outside the crate finds only `.coderipper.toml`, `crates/baracuda/src/lib.rs` and `examples/nvcomp_lz4_roundtrip.rs`, and I did not read how they use it. Decision: if nothing uses `raw`, remove it before the freeze; a public `raw` module that mirrors the v4 shape will be hard to retire.
5. **Safe/unsafe boundary of the helpers.** `compress_alignment<Opts: Copy>(pfn, opts)` and `decompress_alignment(pfn)` are `unsafe fn` taking a caller-supplied `unsafe extern "C" fn`, so the contract is the caller's. The same query for LZ4 is a safe `fn` that fetches the PFN itself (`lz4_compress_alignment`), which is the form every codec should have. `status_string` returns `Result<&'static str>` and maps both a null pointer and a non-UTF-8 string to `Ok("unknown")` (read: `unwrap_or("unknown")`), so the `Err` arm is only the loader failing; the claim "nvCOMP returns a static C string" is vendor behaviour, **not checked**. `get_properties` is `unsafe` only because of the untyped pointer (finding 4).
6. **`Error`, the re-export and `#[non_exhaustive]`.** `pub type Error = baracuda_core::Error<nvcompStatus_t>` is a type alias, the same shape as the other wrapper crates, so `baracuda_core`'s `Error` is this crate's public error; fine, but the alias hides that variants are `baracuda_core`'s (0 `#[non_exhaustive]` rows in the census for this crate, since there are no enums here). `nvcompStatus_t` is a newtype `pub struct nvcompStatus_t(pub i32)` in `-sys` (read, line 27), not an enum, so new status codes are not a breaking change. The 17 re-exported names are `-sys` types (14 `nvcompBatched*Opts_t` including the 5 decompress-opts types, `nvcompAlignmentRequirements_t`, `nvcompDecompressBackend`, `nvcompType`): their fields, derives and whether the two enums are `#[non_exhaustive]` are **not checked**. They are the crate's real option API (every codec takes its `Opts` by value), and the `nvcompBatched*Opts_t` types appear by value in the codec signatures, so they freeze with them. The `-sys` file has `finish_non_exhaustive` once (a `Debug` helper) and no `#[non_exhaustive]` attribute (grep, `crates/baracuda-nvcomp-sys/src/lib.rs`); the control is that the same grep finds that one `finish_non_exhaustive` line. Read the 17 types before freezing them.
7. **Dependencies and feature gating.** `Cargo.toml` lists four dependencies: `baracuda-types`, `baracuda-core`, `baracuda-nvcomp-sys`, `thiserror`. In `src/lib.rs` and both test files: `baracuda_core` is used (line 205), `baracuda_nvcomp_sys` is used (lines 35, 37); **`baracuda-types` and `thiserror` have 0 hits** (grep `baracuda_types\|thiserror` over `src` and `tests`; control: the same pattern list with `baracuda_core\|baracuda_nvcomp_sys` finds the hits above). Two unused dependencies. Dev-dependencies are used (`baracuda_runtime` and `require_optional!` from `baracuda-driver` in `tests/lz4_roundtrip.rs`). The only feature is `device-tests` (empty, test gating); nothing in the public API is feature-gated, there is no `[package.metadata.docs.rs]`, so all 63 rows render on docs.rs as long as the `-sys` crate builds there (its loader is a runtime `nvcomp()` lookup; its build was **not checked**).
8. **Documentation drift.** (a) The README example uses `baracuda_nvcomp::lz4::{Lz4Manager, Lz4Options}` with `.compressed_size`, `.compress`: `grep Manager` over `src` and `tests` finds 0 hits (control: `codec_mod` finds the macro), so the example does not compile against this crate; the README lists "Cascaded (multi-pass: bit-pack -> delta -> run-length)" and "CRC32" correctly but the manager-style API it shows does not exist. It is ````rust,no_run````, and the README is not included in crate docs (`include_str!`: 0 in `src`), so CI never compiles it. (b) The README example imports `baracuda_driver::{Context, Device, ..}` while the crate has no driver dependency and its test uses `baracuda_runtime`. (c) README: "Every codec exposes `status_string`, version, and feature properties": `status_string` and `get_properties` are crate-level only and there is no `version` function. (d) The README and `lib.rs` table list "Gzip / Deflate" and Deflate "Strict zlib/raw deflate" with compress and decompress, matching the code only for the two `unsafe` launches (finding 2). (e) `lib.rs` header table has 8 codecs and no CRC32; `crc32` is documented as "(nvCOMP 5+)". (f) `Cargo.toml` description says "Scaffolding at v0.1" and the version is `0.1.0-alpha.172`.
9. **Tests, by name.** 2 `#[test]` in the crate (0 in `src`): `nvcomp_probe` (`tests/gpu_smoke.rs`, not feature-gated, uses `require_optional!` so an absent library is a declared skip) and `lz4_compress_decompress_roundtrip` (`tests/lz4_roundtrip.rs`, `#![cfg(feature = "device-tests")]`). Nothing exercises Snappy, Zstd, GDeflate, Gzip, Deflate, Bitcomp, ANS, Cascaded, `crc32`, `status_string`, `get_properties`, any `*_alignment`, any `get_decompress_size_async`, or `raw`: 1 of the 11 modules has a test. `src/lib.rs` has 29 `unsafe {` (textual; the macro body counts once and is expanded 5 times) and 1 `SAFETY` comment (the `CStr::from_ptr` in `status_string`); the other blocks are one-call `check(cu(..))` pass-throughs under a function-level `# Safety` section, which is the convention here, but it is 1 comment in 29 blocks.

## Recommended order

1. Finding 1 (decide scope: raw `unsafe` surface or typed layer) and finding 4 (remove or retype `raw`, name the CRC32 config type) together, since both set what is frozen.
2. Finding 2 and 3 (complete or document the four hand-written modules; summary lines; the missing alignment and size queries), then finding 6 (read the 17 `-sys` types).
3. Finding 8 (README rewritten against the code or deleted, example compiled via `include_str!`/doctest) and finding 7 (drop `baracuda-types` and `thiserror`, add docs.rs metadata if wanted).
4. Finding 9 (one test per codec, gated by `device-tests`) and finding 5 as cleanup.

Nothing in this review was built, run, or measured against NVIDIA's documentation: findings 2, 3, 7, 8, 9 are read from source and greps with the controls stated; findings 1, 4, 5, 6 rest in part on vendor behaviour or `-sys` types recorded here as **not checked**.
