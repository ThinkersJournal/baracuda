## Findings

1. **The status-code convention is documented, and incomplete.** `lib.rs:19-27` lists `0` success, `1` misaligned, `2` invalid problem, `3` not supported, `4` workspace too small or null, `5` internal CUTLASS error, for "all `*_run` and `*_can_implement` functions". The kernels also return `1000 + cudaError_t` from `cuda_failure_code()` (`kernels/include/baracuda_smem_cap.h:78-81`; all 22 `.cu` files reference it, `grep -c cuda_failure_code kernels/*.cu`: 22 files non-zero, 0 files zero), a range the crate doc does not mention; the safe crate documents it (`baracuda-cutlass/src/error.rs:12-14`, read around). In the `.cu` the plain `return N;` lines are 23 `return 0;` and 21 `return 5;` (`grep -hE '^\s*return [0-9]+;'`), codes 1-4 are `if (status == ...) return N;` forms (read in `gemm_rcr_sm80.cu:111-117`). Not covered by the table: `_workspace_size` and `_scratch_bytes` return `usize` with no error channel (a failing shape returns what? **not checked**), and `_sufficient` returns an `i32` that is a threadblock count (`:2629-2641`), not a status, with no documented failure value. Decision: add the `1000 + n` range to the table, and state what the `usize` functions return for an invalid shape.
2. **`sm90a` declares symbols nothing builds, and "fat binary" does not follow from the build script.** Every extern block is `#[cfg(any(feature = "sm80", feature = "sm90a"))]` (14 blocks plus the module and `pub use`: 16 `#[cfg` lines, `grep -n '#\[cfg' src/lib.rs`), but `collect_kernel_files` adds files only under `cfg!(feature = "sm80")` (`build.rs:182-187`) and the comment says sm_90a kernels are deferred. With `sm90a` alone the list is empty, the build prints a warning and returns (`build.rs:57`), and the 218 declarations stay in the API with no definitions: any caller of one fails at link. With `sm80` + `sm90a` the builder takes the first branch, `compute_cap(90)` and `-DBARACUDA_CUTLASS_HAS_SM90A` (`build.rs:94`), and the `sm80` branch is not taken (`:95`); the `.cu` files are the sm_80 set, and the define is read by 0 `.cu`/header files (`grep -rc BARACUDA_CUTLASS_HAS_SM90A kernels`: 0 total; control: `build.rs` has it once). The README says enabling both "ship[s] a fat binary that runs on both" (`README.md:50`); the build script compiles one target. What `compute_cap(90)` produces in `baracuda-forge` is **not checked**. Decision: gate the declarations on `sm80` only until an sm_90a kernel exists, or build both targets; the feature name `sm90a` is public API either way.
3. **Entry points are positional C signatures with conventions only in comments.** `m, n, k: i32`, `lda, ldb, ldc, ldd: i64`, `workspace_bytes: usize`, `stream: *mut c_void`, 16 to 21 parameters on a `_run` (batched has 21: `:2498-2520`). The `f64` family changes `alpha`/`beta` to `f64` (`:2069-2070`) and is the one place the signature differs by dtype; the only statement is a comment (`:2046-2049`). The 48 macro-generated bias functions have identical signatures for `f32bias` and `i32bias` (`bias: *const c_void`, `:2920`), and their docs are one `concat!` text for all 48 that says "See the section header" and does not name the family (`:2900-2907`), so the bias element type is encoded only in the symbol name. 66 doc lines are the generic "CUTLASS GEMM trampoline (...)" (`grep -c 'CUTLASS GEMM trampoline'`: 66; these are in the RRR, TF32, f32-simt and f64 sections). Every `*mut c_void` is untyped: a wrong pointer is not caught. These are not defects of a `-sys` crate; they matter because the names and parameter orders become the ABI, and `baracuda-kernels-sys` re-exports them under new names (`src/cutlass_reexport.rs`; 210 of the 218 names appear in `baracuda-kernels-sys/src`, 218 in `baracuda-cutlass/src`, 0 in `baracuda-kernels/src`; control: a made-up name gives 0 in `baracuda-cutlass/src`).
4. **Header comments are stale.** `lib.rs:46-50` says the epilogue is Identity only, "the Bias epilogue lands in a follow-up", "there is no `bias` argument and the safe layer's `EpilogueKind` enum has no `Bias` variant"; the file declares bias entry points from `:152` on. `NOTICE:13-14` says the Bias epilogue "was ... removed during round-1 review". `README.md:24-31` ("v0 scope", "Shipped today: sm80 pair only") is corrected by an update note (`:33-40`) that leaves the table in place; the README's "Build cost" section quotes "~50s" for the f16/bf16 pair, while the list in `collect_kernel_files` (`build.rs:182`) names 22 sources. `cutlass_reexport.rs`'s own header counts "162 trampoline symbols" for 54 families; this crate exports 218 (census paragraph above), and which of the two figures is stale there I did not check (`grep -c 'baracuda_kernels_gemm_.*_run' cutlass_reexport.rs`: 70 lines).
5. **Grouped GEMM has an ABI that exists only in prose and in the `.cu`.** `_run` takes `d_problem_sizes`, `d_ptr_a..d`, `d_lda..d_ldd` and `h_problem_sizes` all as `*const c_void` (`:2675-2693`); the element types are `GemmCoord` (3 `i32`), `Element**` and `int64_t*` (`kernels/grouped_gemm_rcr_sm80.cu:165-178`, grep), and the Rust file names `GemmCoord` only in comments (`:2623`, `:2625`, `:2671`; no `#[repr(C)]` struct is defined here, 0 `struct` in the file). The host copy `h_problem_sizes` must equal the device copy (doc, `:2623-2625`), which nothing enforces. The `_sufficient` name returns a block count (finding 1). Only f16 and bf16 are present (4 entry points each plus 4 helpers); `_scratch_bytes` takes `threadblock_count` from `_sufficient`, an order dependency stated only in the argument list.
6. **Macro and re-export shape.** `int8_bias_ffi!` (`:2897`) defines `unsafe extern` inside a macro, inside a private `mod int8_bias_decls` (`:2956`), re-exported by glob (`:3049`): the 48 symbols are therefore reachable as `baracuda_cutlass_kernels_sys::baracuda_cutlass_gemm_bias_*_s8_*`, and the census cannot see them by path (hence `<macro-expanded>`). A future symbol added to that module is public automatically. The 16 macro invocations are written out by hand (`:2960-3045`), each three names long; a typo in one name compiles (an `extern` declaration) and fails only at link or never, since nothing here checks a symbol against the archive. The same applies to the 170: declaration names are matched to `extern "C"` definitions in `kernels/*.cu` only by a developer (60 `extern "C"` lines in the `.cu` files, some of them macro entries; I did not match the 218).
7. **Unsafe accounting, no tests, dependencies.** `src/lib.rs`: `#![no_std]` (`:31`), `use core::ffi::c_void` only. 15 `unsafe extern "C"` lines (14 cfg blocks and the one in the macro, `:2899`), 0 `unsafe {` blocks and 0 `SAFETY:` comments (`grep -c 'unsafe {'`: 0, `grep -c SAFETY`: 0; control: `grep -c '# Safety'` finds 86 lines, 2 of them in the macro text, `:2905`, `:2933`, which expand to 32 docs: the `workspace_size` functions have none, as they take no pointers). Every one of the 218 functions is `unsafe` to call (no `safe fn` items). Every hand-written `pub fn` has a `///` (the two `grep` misses are the macro's `#[doc = concat!(..)]` placeholders). 0 `#[test]` and no `tests/` directory (`ls tests`: no such directory; control: `ls kernels` lists 22 `.cu` files): nothing in this crate checks a declaration. 0 `non_exhaustive` (nothing to apply it to: no type is defined). Dependencies: `[dependencies]` has `baracuda-cutlass-sys`, `[build-dependencies]` has `baracuda-forge`. `baracuda_cutlass_sys` is named 0 times in `src/lib.rs` (and there is no `pub use`, though `Cargo.toml:38` says "Re-export the headers crate so consumers don't have to add it themselves": that comment is false); it is **not unused**: `build.rs` reads `DEP_CUTLASS_INCLUDE` and `DEP_CUTLASS_ROOT` (`:68`, `:83`, grep: 4 mentions of the crate by name) and the `cutlass-2-11` feature forwards to it (`Cargo.toml:35`); removing it would break the build. `baracuda_forge`: 3 hits in `build.rs`, 0 in `src` (positive control for the same grep). Features: `default = ["sm80"]`, `sm80`, `sm90a`, `cutlass-2-11` (mutually exclusive with `sm90a`, `build.rs:47` panics); `links = "baracuda_cutlass_kernels"` (`Cargo.toml:12`). The build skips nvcc under `DOCS_RS` and, with no toolkit, warns and emits no archive (`build.rs:39`, `:101-127`), so a build with `sm80` and no nvcc compiles and fails at link in any binary that calls an entry point; docs.rs renders all 218 (`[package.metadata.docs.rs] features = ["sm80"]`). Only two crates depend on it, `baracuda-cutlass` and `baracuda-kernels-sys` (`Cargo.toml` grep).

## Recommended order

1. Finding 2 (`sm90a` declarations and the "fat binary" claim): it decides which symbols are public at all under each feature set.
2. Finding 1 (status range, `usize` and `_sufficient` returns) and finding 3 (`f64` scalars, bias element type per symbol, naming): the contract the 218 names carry.
3. Finding 5 (grouped ABI) as a freeze decision with `baracuda-cutlass`, the only caller.
4. Findings 4, 6, 7 as cleanup: the stale header, README and NOTICE text, the false `Cargo.toml` comment, census rows for the 170 hand-written declarations (or a stated rule that `-sys` extern blocks are counted by the macro-free census path), and a link-check that every declared symbol exists in the archive.

Nothing in this review was built, run, or checked against CUTLASS or the CUDA runtime: findings 1, 3, 4, 6, 7 are read from source and greps with the controls stated; findings 1 (what the `usize` functions return on a bad shape), 2 (what `baracuda-forge`'s `compute_cap(90)` emits) and 5 (the `.cu` behaviour behind the ABI) rest on code recorded here as **not checked**. **Not checked** beyond that: the 218 declarations against the `extern "C"` definitions in the 22 `.cu` files (I confirmed only that the 48 macro names and the 218 names all appear as text in downstream crates, not that each is defined); parameter lists were read by shape, not each of the roughly 3,000 lines character by character; the `kernels/include` headers beyond `baracuda_smem_cap.h:55-81`; `baracuda-cutlass`'s use of each symbol; and the `.cu` files beyond the status-code paths named above.
