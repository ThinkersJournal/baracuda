## Findings

1. **Every signal function is a safe `fn` that hands unchecked sizes to NPP, so the "safe" label is not earned.** `signal::sum_32f` (`:121-139`) asserts `src.len() >= n` and `!sum_out.is_empty()` and then passes `scratch.as_raw()` with no check that `scratch` is as large as `sum_buffer_size_32f(n)` returns. `signal::min_max_32f` (`:151-169`) has no `assert!` at all: `src`, `min_out`, `max_out` and `scratch` lengths are all unchecked and `n` may be negative. The three in-place ops (`:52`, `:71`, `:90`) check `src.len()` and `src_dst.len()` against `n as usize`, which for a negative `n` wraps to a huge `usize` and so panics by accident rather than by design. NPP writes to device memory through these pointers, so an undersized scratch buffer is memory corruption reachable from safe code. Counts: `assert!` in `src/lib.rs`: 8 (6 in the three in-place ops, 2 in `sum_32f`; control: `#[test]`-free file, the same grep on `tests/gpu_smoke.rs` finds 1, its own `assert!`), 0 on `min_max_32f`, 0 on any `image` function (grep `assert!` positions read). Also no `# Panics` section on the 4 functions that do `assert!`, and no statement of what the scratch size contract is beyond "use [`sum_buffer_size_32f`] to size it". Decision before the freeze: check scratch and output lengths (the buffer-size fns already return bytes), or make these `unsafe`, or take typed scratch/out wrappers; the first is a behaviour change, the others are breaking.
2. **No stream, no `NppStreamContext`: the API is fixed to NPP's default stream, and the repo's own test file says that is the wrong family.** `tests/gpu_smoke.rs:4-8` states that NPP's signal and image functions "moved to `_Ctx`-suffixed variants in CUDA 12+ (they now require an explicit `NppStreamContext`)" and that wrapping them "lands in baracuda-npp v0.2". The wrappers call the non-`_Ctx` names (`nppsAdd_32f_I`, `nppiResize_8u_C1R`, ...): `grep -c '_Ctx' baracuda-npp-sys/src/lib.rs` = 0 (control: `grep -c 'nppsAdd_32f_I'` on the same file finds the declaration, read at `:161-163`). Whether the non-`_Ctx` symbols still exist in a given CUDA 13 toolkit is **not checked**; if they do not, `Npps::npps_add_32f_i()` returns `SymbolNotFound` at call time on those installs. `README.md:17` lists "StreamContext binding" as today's surface; grep for `Stream` in `src/lib.rs`: 0 hits (the `grep -n 'NppLibraryVersion\|StreamContext\|Stream'` run finds only the `NppLibraryVersion` lines in `src/lib.rs` and the README line; control: `Stream` is found in `baracuda-cufft/src/lib.rs:30`, whose `set_stream` is `:139`), so the README line is false. The consequence for the freeze is that adding a stream later means 18 new function names or a new parameter on all 18: every current signature is a commitment to "no stream". Every sibling that is stream-aware (cufft `Plan::set_stream`, `baracuda-driver`) lets the caller order work; here no function takes a stream or tells the caller whether it blocks (NPP's default-stream semantics: **not checked**), and `DeviceBuffer` can be dropped by the caller after the call returns while work may be pending. Decision: settle the stream/context story first (it is the largest hard-to-change item in this crate).
3. **The public types a caller needs are in `-sys` and not all re-exported.** `version()` returns `baracuda_npp_sys::NppLibraryVersion` (`:35`), which is imported at `:20` but not in the `pub use` at `:22`; the `Error` alias is `baracuda_core::Error<NppStatus>` (`:25`) with `NppStatus` likewise not re-exported. A caller who writes `match e { Error::Status { status } => status.0 }` or names the version type must depend on `baracuda-npp-sys` directly (the test only reads `v.major` etc. as fields, `tests/gpu_smoke.rs:16`). The 4 names that are re-exported are `-sys` `repr(C)` structs (`NppiSize`, `NppiRect`, `NppiPoint`: all fields public, `-sys/src/lib.rs:99-131`) and, surprisingly, a **module**: `NppiInterpolationMode` is `pub mod NppiInterpolationMode { pub const NN: i32 = 1; ... }` (`-sys/src/lib.rs:134-153`, 9 `i32` consts), so the `pub use` re-exports a non-camel-case module that reads like a type. Their layouts and field names become this crate's API, so freeze `-sys` and this crate together (as `r6/nvml.md` finding 6 says for nvml). `NppStatus` also has `NPP_STEP_ERROR` and `NPP_INVALID_ARGUMENT_ERROR` both `Self(-14)` (`-sys:50, :54`), and `name()` maps `-14` to the literal string `"NPP_INVALID_ARGUMENT_ERROR_OR_STEP_ERROR"` (`:74`); `description()` has text for 2 of the 5 named codes (`:83-84`); that is a `-sys` freeze item, recorded here because it is the text of this crate's `Error`.
4. **Error-type shape and warnings.** `Error`/`Result` follow the sibling pattern exactly (`baracuda-cufft/src/lib.rs:34-36`, `baracuda-nvml/src/lib.rs:46-48`; same `Result<T, E = Error>` with a defaulted second parameter), so naming is consistent. `Error` is `baracuda_core::Error<NppStatus>`, a `#[non_exhaustive]` enum (`r6/core.md` finding 1). `check` is `Error::check` over `NppStatus::is_success`, which is `self.0 == 0` (`-sys:57-59`, `:89-91`; core `error.rs:154-155`): **every non-zero code is an `Err`, including positive codes**, while the `-sys` doc says "Negative values are errors; positive values are warnings" (`-sys:39`) and the type has an `is_error` (`< 0`) that this crate never calls (grep `is_error` in `src/lib.rs`: 0; control: `is_success` is called via `Error::check` and found in core). Whether any NPP function used here can return a positive warning is **not checked**; if it can, a successful call that warns (from memory NPP has such codes, not checked) comes back as `Err`. Decision: define the contract (warnings are `Ok`, or surfaced), because changing it later changes which calls fail. `version()` fabricates a status for a null result: `NppStatus(-4)` (`:41`), a literal duplicating `NppStatus::NPP_NULL_POINTER_ERROR` (`-sys:48`), synthetic but sensible.
5. **Two modules, two conventions, and one function family.** `signal` takes `&DeviceBuffer<f32>`/`&mut DeviceBuffer<f32>` and returns `Result<()>` (safe, length-asserted); `image` takes raw `*const f32`/`*mut u8` pointers plus `i32` steps and every function but one is `unsafe fn` (9 `pub unsafe fn`, 9 `# Safety` sections: `grep -c '# Safety'` = 9, control: `grep -c 'pub unsafe fn'` = 9, so each has one; their text is "must be device-addressable and cover ..." and refers to "Same as [`add_32f_c1r`]" in 4 of them, which is thin: no mention of ROI/step alignment, aliasing of `src`/`dst`, or which CUDA context must be current). Pitched image code is exactly the case where a `DeviceBuffer`/pitched wrapper would be the safe API; the doc at `:181` already names `baracuda_runtime::memcpy2d::PitchedBuffer`, which this crate does not depend on (not in `Cargo.toml`, grep `baracuda_runtime` in `src/lib.rs`: 0; control: `baracuda_driver` found at `:19`). `image::sum_buffer_size_32f_c1r` is safe but `image::sum_32f_c1r` is `unsafe` with a doc that says `sum_out` is a "device buffer of len >= 1" (`:394`) while the type is `*mut f64` and the `# Safety` section (`:398-400`) says nothing about `sum_out` or `scratch`; whether NPP's `pSum` here is host or device memory is **not checked** and should be before the doc is frozen. Naming: `*_in_place` (signal) vs NPP's `_I` suffix vs `*_c1r`/`*_c1r_sfs` (image, NPP's suffix kept) is two vocabularies; `rgb_to_gray_8u` drops `c3c1r` while its sibling `add_8u_c1r_sfs` keeps `c1r_sfs`; the function that wraps `nppiSumGetBufferHostSize_32f_C1R` is called `sum_buffer_size_32f_c1r` (host-size dropped). Free functions in a module, where cufft/nvjpeg/nvml build handle types, are the shape most likely to be regretted once a context or stream arrives (finding 2).
6. **Raw-integer and `i32` vocabulary.** `resize_8u_c1r` and `resize_32f_c1r` take `interpolation: i32` (`:270`, `:303`) where the doc comment says "the given interpolation mode"; the vocabulary is the `NppiInterpolationMode` constants (finding 3), so a caller can pass any `i32`. Lengths and steps are `i32` throughout (`n: i32`, `*_step: i32`, `NppiSize` fields `c_int`), copying C; `n as usize` appears 10 times in `src/lib.rs` (`grep -c 'as usize'` = 10: 8 `assert!` operands + 2 buffer-size results `bytes as usize` at `:115` and `:147` and `:390`; control: the file is read, count per site above, and the sizes of 3 buffer-size fns is `Result<usize>` from a C `int`, never negative in practice, **not checked**). A typed enum for the mode, and `usize`/checked `i32` conversion for lengths, are additive if they are new functions and breaking if they replace these; the existing signatures freeze the raw shape.
7. **Reductions: shape and scratch handling.** `sum_buffer_size_32f`, `min_max_buffer_size_32f` and `sum_buffer_size_32f_c1r` return `Result<usize>` bytes and the caller allocates a `DeviceBuffer<u8>` scratch; that is faithful to NPP and a fair freeze, but see finding 1 for the missing check. The three scratch-taking functions use `&mut DeviceBuffer<u8>` in `signal` and `*mut u8` in `image` (inconsistent, finding 5). `sum_32f` writes `f32` into `sum_out[0]` while `sum_32f_c1r` writes `f64` (`:405`): both correspond to the `PFN` signatures (`-sys:174-178` `p_sum: *mut f32`, `:293-299` `p_sum: *mut f64`, read), so not a defect, but the doc of neither says so. The result stays on the device for `signal::sum_32f`; no function returns a scalar to the host.

## Recommended order

1. Finding 2 (stream/context and the `_Ctx` question), because it decides whether all 18 signatures survive; with finding 1 (safe functions that do not check scratch/outputs) and finding 5 (one convention for `signal` and `image`).
2. Findings 3 and 6 (re-export `NppLibraryVersion` and `NppStatus`, typed interpolation, integer widths) and finding 4 (warning semantics), as freeze decisions that change signatures or which calls fail.
3. Findings 8, 9, 10, 11 as cleanup: remove `baracuda-types` and `thiserror` after a build check, rewrite README and `Cargo.toml` description against the code, add `SAFETY` comments and `# Errors`/`# Panics`, add tests for the safe `signal` functions and the panics.

Nothing in this review was built, run, or checked against NVIDIA's NPP documentation: findings 1, 3 (structure), 5, 8, 9 (counts), 10, 11 are read from source and greps with the controls stated; findings 2 (symbol existence in CUDA 12/13), 4 (positive status codes), 5 (`pSum` host/device) and 7 rest in part on NPP behaviour recorded here as **not checked**.
