## Findings

1. **`Error` is its own enum, with the freeze-relevant shape in the wrong place.** `Error` (`lib.rs:104-125`) is `#[derive(Debug, Error)] #[non_exhaustive]` on the enum (census 1; control: `grep -n non_exhaustive src/lib.rs` finds the attribute at `:105` and `:157`, plus 2 doc-text hits at `:101` and `:152`, so 4 lines, 2 attributes). It does not use `baracuda_core::Error<S>` that the `-sys`-backed sibling crates (`baracuda-nvml`) use; this crate depends on `baracuda-driver` only and reports its own shim status. Consequences: (a) `Driver(#[from] baracuda_driver::Error)` (`:123-124`) puts a third-party-to-this-crate type in the public signature, so a breaking release of `baracuda-driver` is a breaking release of this crate (and `From<baracuda_driver::Error>` is public API); (b) the five variants are not themselves `#[non_exhaustive]`, but all are unit or one-field tuple variants, so only adding a field to a tuple variant would break (low risk), and `non_exhaustive` on the enum already covers new variants; (c) `ShimInvalidArgument` and `LaunchFailed` hard-code their numeric status in the `Display` strings ("status 1", "status 5", `:112`, `:116`) duplicating `sys::STATUS_INVALID_ARGUMENT`/`STATUS_LAUNCH_FAILED` (`-sys` `lib.rs:260`, `:262`; read by grep); (d) `InvalidArgument(&'static str)` carries a message, not a typed reason, so callers cannot match on which argument was wrong (the 5 messages in the file are at `:270`, `:427`, `:431`, `:491`, `:495`); (e) no `PartialEq`/`Clone` (the same shape as the nvml finding 2 of the sibling review: `baracuda_driver::Error` is not checked for either). None is a defect; they are shape decisions that are hard to change afterwards. Decision: confirm own-enum vs `baracuda_core::Error<S>` (portfolio consistency), and consider boxing/wrapping the `baracuda_driver::Error` source.
2. **The status mapping is lossy and its one catch-all variant is the future.** `status_to_result` (`:130-137`) maps 0, 1 and 5 and everything else to `UnknownStatus(i32)`; the `-sys` crate defines exactly those 3 `STATUS_*` constants (`-sys` `lib.rs:258-262`; control: 3 constants found by `grep -n 'pub const STATUS'`). When the shim gains a status, the safe crate reports `UnknownStatus` until updated; `non_exhaustive` makes adding the dedicated variant non-breaking, so this is fine but should be a conscious freeze of "unknown statuses stay `UnknownStatus`". `status_to_result` is not unit-tested (finding 10).
3. **The FFI integer encoding is public API.** `Fp8Format::to_ffi(self) -> i32` (`:166-172`) is `pub` and its doc says "Integer cast for the FFI shim", and `Fp8WideDtype::FFI_TAG: i32` (`:201-202`) is a public associated const of the public trait. Both publish the shim's numbering (E4M3 = 0, E5M2 = 1; f32/f16/bf16 = 0/1/2, `-sys` `lib.rs:266-276`) as semver-covered. Neither is used outside this crate (grep for `to_ffi` and `FFI_TAG` over `crates` excluding this crate: 0 files; control: `Fp8WideDtype` is re-exported by `baracuda-kernels/src/lib.rs:665-667`, so the pathspec reaches that crate). Decision: make `to_ffi` `pub(crate)` (non-breaking now, breaking later) and decide whether `FFI_TAG` belongs on a public trait; since `Fp8WideDtype` is sealed, moving it to a private supertrait is non-breaking for implementors (there are none) and removes the encoding from the surface.
4. **`max_representable` duplicates a `-sys` function and a constant is a commitment.** `Fp8Format::max_representable` returns the literals 448.0 / 57344.0 (`:176-181`), while `-sys` exposes `baracuda_te_fp8_max_representable(fmt: i32) -> f32` (`-sys` `lib.rs:101`) and the recipe-update kernel computes `max_representable / max_amax` on the device using its own value (doc, `:42-45`). Two sources of the same number can drift; the safe crate's `can_implement` shims (4 in `-sys`, `lib.rs:213`, `:226`, `:238`, `:249`) and `baracuda_te_fp8_max_representable` have 0 references in `src/lib.rs` (`grep -c 'can_implement\|fp8_max_representable' src/lib.rs`: 0; control: `grep -n 'baracuda_te_' src/lib.rs` finds `recipe_init_run`, `recipe_update_run`, `fused_cast_amax_run`, `dequant_run`, 4 hits). So 4 + 1 + 2 format getters of the `-sys` surface are unwrapped. The `Fp8Format` enum is `#[non_exhaustive]` with 2 variants (`:157`); the doc justifies it with MXFP8 (`:152-155`, "in-development", from the doc, **not checked**). MXFP8 would need per-block scales that `Fp8Recipe`'s single `scale` scalar cannot hold (finding 6), so adding it later may not be a one-variant change.
5. **`Fp8WideDtype` is correctly sealed, but its supertrait leaks.** `pub trait Fp8WideDtype: Copy + 'static + DeviceRepr + sealed::Sealed` (`:200`); `sealed::Sealed` is in a private module (`:184-189`) and implemented for `f32`, `half::f16`, `half::bf16` only, so adding dtypes (say an FP8 type, `f64`) is non-breaking, and so is adding a required item. `DeviceRepr` is a `baracuda-types` trait in the public bound, so `baracuda-types` (and its `half-crate` feature, `Cargo.toml:45`) is part of this surface; `half` types appear in public bounds (`Fp8CastPlan<half::f16>`, README, crate doc `:73`) so `half`'s major version is a freeze item too (`half` is a direct dependency, `Cargo.toml:46`). The `Sealed` row is correctly not public API (`reach private-mod`).
6. **`Fp8Recipe` shape: what the struct publishes, and what ties it to a stream.** (a) `new` takes `(ctx, stream, format, history_len: usize)` and rejects `0` and `> 8192` with `InvalidArgument` (`:268-272`); the limit is documented (`:258`) and then fixed forever, as is the use of `i32` inside (`history_len: i32` at `:249`; getters cast back `as usize`, `:309-317`; the `as i32` at `:273` is safe given the 8192 bound). (b) It allocates three buffers, then launches `baracuda_te_recipe_init_run` **asynchronously** on `stream` (`:282-290`) and returns `Ok(Self)` before the init has run; any other stream that then uses the recipe races the init. Nothing documents that `update_after_pass`, `Fp8CastPlan::run` and `Fp8DequantPlan::run` must use the same stream (or one ordered after it) as `new`: the three methods take a bare `&Stream` each (`:328`, `:423`, `:487`) and no check ties it to `ctx` or the recipe's allocation context (read; whether the shim or driver checks is **not checked**). The crate doc mentions "in stream order" once (`:320-322`). Decision: document the single-stream contract on `new`, or store the stream/context in `Fp8Recipe` (breaking later). (c) `write_pos`/`history_len` are host-side mirrors of device state advanced in `update_after_pass` after the launch status is checked (`:342-345`); on a failed launch the pointer is not advanced, which is right. Because `write_pos` is host-only, two `Fp8Recipe`s cannot share a history, and the device never reads it back, so a recipe whose device history is mutated by another path is out of sync (an unlikely misuse). (d) `amax_history`, `scale`, `scale_inv` return `&DeviceBuffer<f32>` (`:351-363`): read-only, so the layout (ring of `f32`, `scale` 1 element) is frozen as documented inspection API; `scale_host`/`scale_inv_host` synchronize the stream and copy 1 `f32` (`:366-380`), so they are blocking and name `&Stream` only to synchronise. (e) The doc says "RAII handle" (`:10`) but the struct only owns `DeviceBuffer`s (their `Drop` frees); no `Drop` of its own and no `Clone`, which is right (clone would double-own device state). (f) Not `Copy`/`Clone`, derive `Debug` only (`:242`).
7. **`update_after_pass(&mut self)` and the `&mut` on `run` are API-shaping.** `Fp8CastPlan::run` takes `recipe: &mut Fp8Recipe` "because each launch mutates the recipe's amax history slot via atomicMax" (`:393-394`) while the host struct is not changed by `run`: the `&mut` encodes a device-side effect and prevents two casts (two tensors) sharing one recipe concurrently, or reading `scale_host` in the middle. It also differs from `Fp8DequantPlan::run`'s `&Fp8Recipe` (`:486`), which is right (pure read). Relaxing `&mut` to `&` later is non-breaking; tightening it is breaking, so keeping `&mut` is the safe-to-freeze choice. But: the crate doc's algorithm says that within one training step "the forward pass(es)" may call `run` many times against one recipe (`:320-321`), so the `&mut` forces them through one borrow at a time, which is fine on a single stream.
8. **`select() -> Result<Self>` returns `Result` with no failing path.** `Fp8CastPlan::select` and `Fp8DequantPlan::select` (`:402-406`, `:471-475`) are `Ok(Self { _marker: PhantomData })` with no fallible step: no `Err` can be produced (read; control: `status_to_result` is the only function that constructs shim errors, and `select` does not call it). The doc says "Cheap; no GPU activity" (`:401`, `:470`). Keeping `Result` is consistent with the sibling "plan" convention (`select()` is used the same way in the optimiser crates; grep `pub fn select()` over `crates/*/src/lib.rs`: 1 hit, this crate only; the sibling naming, from the doc cross-reference at `:521-522` "same pattern as in baracuda-cudnn / baracuda-optim", was not read in those crates, **not checked**). Decision: keep `Result` as an "arch/availability check will land here" freeze placeholder, or return `Self` (breaking later). The unwrapped `*_can_implement` shims (finding 4) are the natural fallible content.
9. **`run` shape: untyped FP8 `u8`, length-only validation.** `Fp8CastPlan::run(input: &DeviceBuffer<TIn>, output: &mut DeviceBuffer<u8>, ..)` and the dequant mirror use `DeviceBuffer<u8>` for the FP8 bytes (`:420-421`, `:484`), so the type system cannot tell E4M3 bytes from E5M2 bytes or from an arbitrary byte buffer; the format lives in the recipe (`recipe.format`, `:446`, `:506`). `baracuda-kernels` already exports `Fp8E4M3FN`/`Fp8E5M2` element types (`baracuda-kernels/src/lib.rs:72`, grep; in which crate they are defined is **not checked**), so a typed `DeviceBuffer<Fp8E4M3>` could be introduced later as a new method or overload, but changing `u8` is breaking. Validation is `input.len() != output.len()` and `is_empty()` only (`:425-432`, `:489-496`); a cast with `input.len() == 0` is an error, not a no-op (documented as "empty input", a deliberate choice that callers with possibly-empty batches must special-case). Alignment, context identity and `input`/`output` overlap are unchecked (the `InvalidArgument` doc at `:107-108` promises "length, alignment, dtype mismatch" validation; only length is performed: `grep -n 'align' src/lib.rs`: 1 hit, `:107`, that doc line, and no executable check; control: `len()` found at `:425`, `:489`).
10. **Unsafe accounting.** `src/lib.rs` has 4 `unsafe {` blocks (`:282`, `:331`, `:438`, `:500`; `grep -n 'unsafe' src/lib.rs` returns exactly 4 lines) and 4 `// SAFETY:` comments (`:279`, `:329`, `:434`, `:498`; `grep -n SAFETY`: 4; control: both greps hit the same 4 call sites, one block each). 0 `unsafe fn`, 0 `unsafe impl`. Each SAFETY comment is 2-3 lines; none state the stream-ordering argument or that the `DeviceBuffer`s' device allocations belong to a live context (the "standard CUDA async contract" is delegated to the public doc at `:415-417`). `device_ptr`/`device_ptr_mut` are safe private fns that take `&DeviceBuffer` and return a `*mut c_void` (`:519-527`); `device_ptr_mut` is used on `&amax_history` with a shared reference (`:284`), a mutable pointer from a shared borrow, which is sound only because the data is device memory the host never dereferences; the cast `as *mut f32` hides it. `buf.as_raw().0 as *const c_void` (`:522`) assumes `CUdeviceptr` is a `u64` tuple struct (`:520-521` comment). All private, so not a freeze item.

## Recommended order

1. Findings 3 and 4 (the `to_ffi`/`FFI_TAG` encoding and the duplicated `max_representable`): cheap, non-breaking now, breaking later.
2. Finding 1 (error type: own enum vs `baracuda_core::Error<S>`, `baracuda_driver::Error` in `Driver`) and finding 9 (`u8` FP8 buffers, the length-only validation vs the documented alignment checks): decide before the freeze because they change signatures callers write.
3. Findings 6 and 7 (stream-ordering contract on `Fp8Recipe::new` and `run`, the `&mut` on the cast): document or encode.
4. Findings 8, 10, 11, 12, 13, 14 as cleanup: `select()` return type decision, SAFETY wording, a non-GPU `#[cfg(test)]` unit test for `status_to_result`/`max_representable`/`history_len` bounds, the `default`-feature doc contradiction between this crate and `-sys`, "cast/transpose" description.

Nothing in this review was built, run, or checked against NVIDIA's or TransformerEngine's documentation: findings 1, 2, 5, 8, 10, 12 (counts), 13, 14 are read from source and greps with the controls stated; findings 3 (the encoding), 6 (stream behaviour), 9 (alignment) and 11 (per-test coverage of the 4 files, only 2 of which I read at the header) rest in part on shim, driver and test code that I did not read, recorded above as **not checked**.
