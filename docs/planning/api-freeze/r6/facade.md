## Findings

1. **The facade freezes 20 crates by alias, and by construction cannot be reviewed on its own.** `pub use baracuda_x as x` makes `baracuda::x::*` identical to the sub-crate, so a break in any of the 20 is a break of `baracuda`, at the same version (`0.1.0-alpha.176` on all, workspace). The workspace has 45 non-`-sys` `baracuda-*` directories (`ls -d crates/baracuda-*/`, minus 29 `-sys`; the listing printed 74 in all); the facade re-exports 20 names of them. Not re-exported (by name, checked against the 20 `pub use`): `baracuda-core`, `-kernels`, `-flashinfer`, `-cutensor`, `-cupti`, `-cutlass`, `-cuvs`, `-nvshmem`, `-tensorrt-builder`, `-forge` (the doc says to add the last as a build-dependency, `lib.rs:59-66`, deliberate). The description calls it an "Umbrella crate" (`Cargo.toml:4`); whether it is meant to cover the whole stack or a curated subset is the decision, and every addition later is non-breaking.
2. **`nvimagecodec` is a feature with no re-export.** `Cargo.toml:48` (feature), `:100` (optional dep), `:71` (member of `imaging`), and `full` includes `imaging` (`:82`). `grep -n nvimagecodec src/lib.rs examples/*.rs`: 0 hits; positive control: `grep -c baracuda_nvml src/lib.rs` finds 1, and the same grep shape finds each of the other 19 aliases. So `--features nvimagecodec` compiles the crate and exposes nothing: `baracuda::nvimagecodec` does not exist, there is no census row for it, and the one root README line that mentions the crate is a workspace listing (`README.md:372`, grep). It is also the only optional dependency without a `pub use` (20 optional deps, 19 used by name: the unused-dependency count for this crate is 1, this one; `baracuda-types` non-optional, used `lib.rs:79`). Decision: add `pub use baracuda_nvimagecodec as nvimagecodec` (non-breaking) or drop the feature.
3. **The feature docs omit what the manifest has.** The matrix (`lib.rs:10-27`) lists 17 features; the manifest has 28 (`default`, 4 bundles, 23 others). Absent from the matrix: `tensorrt`, `cudf`, `nvimagecodec`, `async`, `half-crate`, `driver-runtime-interop` (6; 17 + 6 = 23 non-bundle, non-default). Bundles (`lib.rs:30-33`) against `Cargo.toml:70-82`: `imaging` doc lists NPP, nvJPEG, CV-CUDA and omits `nvimagecodec` (`:71`); `ml` doc omits `tensorrt` (`:80`); `full` doc omits `cudf` (`:82`). The doc says "All features are opt-in; defaults enable just `driver` + `runtime`" (`lib.rs:5-6`), consistent with `default = ["driver", "runtime"]` (`:16`) apart from the word "all". Removing a default feature is breaking; whether `runtime` belongs in the default is a decision (not checked who depends on it).
4. **Feature implications are uneven, and 2 features are no-ops alone.** 10 features imply `driver` (`cublas`, `curand`, `cufft`, `cusparse`, `cusolver`, `cudnn`, `nccl`, `npp`, `nvjpeg`, `nvimagecodec`; `Cargo.toml:30-48`); 8 gated aliases do not (`nvrtc`, `nvjitlink`, `tensorrt`, `cudf`, `nvcomp`, `cvcuda`, `nvml`, `cufile`). Whether those 8 crates need the driver crate is **not checked**; the rule is not written down. `driver-runtime-interop = ["baracuda-runtime?/driver-interop"]` (`:23`) and `async = ["baracuda-driver?/async"]` (`:57`) use the `?` form: without `runtime` (resp. `driver`) enabled they do nothing, and the comment at `:22` ("enabled whenever both sides are on") describes an intent the manifest does not implement (the feature is explicit, read; `baracuda-runtime/Cargo.toml:24`: `driver-interop = ["dep:baracuda-driver"]`). `half-crate` (`:63-67`) forwards to 3 crates with `?`; `baracuda-types/Cargo.toml:17` and the `-cudnn` and `-nccl` features exist (read). Every feature name is a freeze commitment.
5. **Quickstart version string.** `lib.rs:39` tells users `baracuda = "0.1"` while the crate is `0.1.0-alpha.176`; a bare `0.1` requirement does not select a pre-release under Cargo's rules (from memory, **not checked**). The line is unrunnable until a stable 0.1 exists, or wrong now. The doctest at `lib.rs:42-51` is `no_run`, builds under default features only, and calls `Device::get`, `Context::new`, `DeviceBuffer::from_slice`, whose signatures I did not check against `baracuda-driver`.
6. **Examples, `unsafe`, tests.** `src/lib.rs`: 0 `unsafe`, 0 `SAFETY` (grep; control: the same grep finds 5 `unsafe` lines in `examples/`). `examples/`: 5 `unsafe` blocks (`graph_capture.rs:49`, `:75`; `hello_kernel.rs:52`; `hello_nvrtc.rs:51`; `hello_runtime.rs:53`) and 5 `SAFETY:` comments immediately above (`:48`, `:74`, `:51`, `:50`, `:52`); `matmul_cublas.rs` has 0 `unsafe`. Tests: 0 `#[test]`/`#[cfg(test)]` under `src` and `examples`, and no `tests/` directory (`ls crates/baracuda/tests`: no such directory; control: `ls crates/baracuda-flashinfer/tests` lists 10 files). Only `matmul_cublas` declares `required-features` (`Cargo.toml:112-114`); the other 4 examples use `baracuda::driver` (`hello_runtime.rs:16`: `baracuda::runtime`), which exist only under default features, so a `--no-default-features` build of the examples is expected to fail (not built, **not checked**). `hello_nvrtc` imports `baracuda_nvrtc` directly (`hello_nvrtc.rs:11`, `:28`), the reason for the dev-dependency (`Cargo.toml:110`), so that dev-dep is used (positive control for the dependency grep).
7. **Lints and docs.** `#![warn(missing_debug_implementations)]` (`lib.rs:76`) is vacuous with no types of its own; the other lints come from `[lints] workspace = true` (`Cargo.toml:116-117`; the values were read for `baracuda-core`, not re-read here). All 20 `pub use` carry a doc comment (read). `nvcomp` and `cvcuda` are labelled "scaffolding only at v0.1" (`lib.rs:141`, `:145`): the freeze of a scaffolding alias is a decision for those two crates' reviews.
