## Findings

1. **Safe constructors and compile entry points panic on interior NUL.** `Program::new` does `CString::new(source).expect("source must not contain NUL")` and the same for `name` (`lib.rs:57-58`); `compile_raw` does `CString::new(*s).expect("NVRTC option must not contain NUL")` (`lib.rs:80`); `compile` and `compile_with` forward to both. Every other failure in the crate is an `Err`; this one is a panic, and the docs for `new`, `compile_raw` and `compile` (`lib.rs:53, 73-74, 120-124`) do not mention it. `compile_with` can reach it through `CompileOptions::extra` / `define` / `include_paths`, which are arbitrary `String`s. Changing a panic into an `Err` later is not signature-breaking, but needs an `Error` variant that does not exist (`baracuda_core::Error` is `#[non_exhaustive]`, `error.rs:122`, so one could be added there). Decision: return `Err` (or document `# Panics`) before the freeze.
2. **The compile log is not reachable from the one-shot paths, and the error carries only a status.** `Program::compile` and `compile_with` create the program internally and drop it on error (`lib.rs:125-129`), so the log (`Program::log`, `lib.rs:103`) is gone with it; the doc admits this ("call `Program::new` manually if you need to inspect the build log", `lib.rs:122-124`). The error type is `baracuda_core::Error<nvrtcResult>`, whose `Status` variant holds only `status: S` (`error.rs:127-131`), so there is no place for the text. The README says the opposite: "Compile-log retrieval, surfaced inside the typed error on failure" (README:33); the code does not do that. For an NVRTC wrapper the log is the diagnostic users need most; the two convenience entry points (`compile`, `compile_with`) are exactly the ones that discard it. Changing the return type or error shape of `compile`/`compile_with` after 1.0 is breaking. Decision: a crate-local error or a `CompileError { status, log }` on the one-shot paths, or make `compile`/`compile_with` return the log on failure; the error text is owned (`String`) in the existing `log()`, which is the right ownership.
3. **`Program` is `Send`, `!Sync`, with an uncommented `unsafe impl`.** `unsafe impl Send for Program {}` (`lib.rs:42`) has no `SAFETY` comment; `nvrtcProgram` is `*mut c_void` (`-sys lib.rs:23`), so `Program` is `!Sync` by the auto-trait rules (not compiled, no `assert_not_send` test). All compile/get methods take `&self` (`lib.rs:75, 87, 103`) although they mutate state inside NVRTC, so the `&self` signature does not reflect that; that is harmless while `!Sync`, but means `Sync` can never be added later without an argument that NVRTC tolerates concurrent calls on one handle (not checked). The handle owns no borrowed data (no lifetime parameter; `Program::new` copies `source`/`name` into `CString`s that live only for the call, `lib.rs:57-69`), which is the right shape to freeze. `Drop` (`lib.rs:132-140`) destroys through a fresh `nvrtc()` lookup and silently skips the destroy if the loader or symbol lookup fails (leak, not UB); `compile_raw` may be called twice on one program, behaviour not checked.
4. **`CompileOptions` is a struct with 11 `pub` fields, no `#[non_exhaustive]`, and a derive of `Default`.** `lib.rs:175-199`; census column is 0 for both struct rows and all 11 field rows, and `grep -c non_exhaustive src/lib.rs` = 1, which is `finish_non_exhaustive()` at `lib.rs:48` (the `Debug` impl of `Program`), not an attribute. Adding a field (e.g. `maxrregcount`, `device-c`, `lto`) breaks every downstream struct literal `CompileOptions { arch: .., .. }` that does not use `..Default::default()`. The builder methods are the intended path, so `#[non_exhaustive]` on the struct (or making the fields private with getters) costs little now and is breaking later. Same for the 11 `field` rows: the public-field-plus-builder pairing means each field is also a commitment to its exact type (`Option<String>`, `Option<bool>`, `Vec<(String, Option<String>)>`).
5. **Stringly-typed and tri-state options.** `arch: Option<String>` and `cpp_standard: Option<String>` (`lib.rs:178-180`) take free text and are interpolated unvalidated (`format!("--gpu-architecture={a}")`, `lib.rs:279`; `--std={s}`, `lib.rs:282`); a typo is only caught by NVRTC at compile time, though the struct doc sells "compile-time typo protection" (`lib.rs:154-156`). `define` accepts any name or value with no check for `=`/space; `extra` is an unconditional escape hatch emitted last (`lib.rs:311`), so it can override a typed setting. The bool setters are inconsistent: `use_fast_math(false)`, `line_info(false)` and `device_debug(false)` emit nothing (`== Some(true)` tests, `lib.rs:284-292`), while `rdc`, `extensible_whole_program` and `ftz` emit `=false` (`lib.rs:293-301`); so `Some(false)` and `None` are the same for three options and different for three others, and the doc "Turn on (or off)" (`lib.rs:219, 225`) is not true for those three. Typed `Arch`/`CppStandard` values added later would be additive only if the string fields stay; replacing the field type is breaking. Decision: keep strings and add typed setters, or commit now to enums with `#[non_exhaustive]`.
6. **Doc drift inside the source and a duplicate method.** (a) `CompileOptions::line_info` field doc says `--line-info` (`lib.rs:183`), the code emits `--generate-line-info` (`lib.rs:288`) and the method doc agrees with the code (`lib.rs:225`). (b) The `device_debug` field doc says "`--generate-line-info` (alias; same as `line_info`)" (`lib.rs:185`), but the code emits `-G` (`lib.rs:291`) and the method doc says `-G` (`lib.rs:231`): the field doc is wrong and `-G` is not a line-info alias. (c) The struct doc names `Self::into_raw` (`lib.rs:157`); the method is `to_strings` (grep for `fn into_raw`: 0 hits; control: `fn to_strings` is found at `lib.rs:276`). (d) `to_str_refs` (`lib.rs:327`) returns `Vec<String>` and is a one-line forward to `to_strings` (`lib.rs:328`); its name says "refs" and it returns owned strings, and its own doc example has to convert again to `Vec<&str>`. It is the same operation twice; drop one before the freeze. (e) `Program::compile` is documented as returning an error "whose source is an NVRTC `COMPILATION` status" (`lib.rs:122-123`), but `Error::Status` has a field `status`, not a `source` (`error.rs:127-131`).
7. **README drift, 6 places.** (a) The example does `let mut prog = Program::new(..)?; prog.compile(&["--gpu-architecture=compute_80"])?;` (README:21-22): `compile` here is an associated function `compile(source, name, options)` (`lib.rs:125`, no `self`), so the call does not compile; the instance method is `compile_raw` (`lib.rs:75`); `mut` is also unneeded. (b) "PTX retrieval (`ptx()`, `ptx_size()`)": no `ptx_size` (grep `ptx_size` in `src/lib.rs`: only the local variable `size_fn`/`nvrtc_get_ptx_size()` call at `lib.rs:89`; there is no `pub fn ptx_size`; control: `pub fn ptx` is found at `lib.rs:87`). (c) "CUBIN retrieval on CUDA 11.1+" (README:32, intro line 5): 0 hits for `cubin|CUBIN|LTO|NVVM` in `src/lib.rs` and in `-sys` (grep); control: the `-sys` loader table (`-sys lib.rs:196-204`, seen in grep output, not read as a file) lists exactly 9 symbols (version, create, destroy, compile, PTX size, PTX, log size, log, error string), so no CUBIN, LTO or name-expression API is loadable. (d) "Include-path registration (`add_name_expression`, `name_expression`)": neither exists (README:34; grep `name_expression` in both crates: 0; control: the 9-symbol table above), and the symbols named are name-expression APIs, not include paths; "Name-mangled lookup for `__global__` C++ entry points" likewise absent. (e) "compile-log ... surfaced inside the typed error" is false (finding 2). (f) The README says nothing about `CompileOptions` or `compile_with` (grep `CompileOptions` in `README.md`: 0; control: `Program` is found). The README is not `include_str!`'d (0 hits for `include_str` in `src`), so its example is never compiled. The README also does not pin a version, so there is no pin drift to report.
8. **API surface that is missing but forecloses nothing, and `version`.** The crate exposes only PTX output: no CUBIN, no name expressions, no in-memory headers (`nvrtcCreateProgram` is called with 0 headers and null arrays, `lib.rs:60-68`), no way to pass a NULL program name (`name: &str`, `lib.rs:54`), no `nvrtcGetErrorString` use (grep `nvrtc_get_error_string`: 0 in `src/lib.rs`; the symbol is loadable, `-sys lib.rs:204`, 1 hit there). All of these are additive on `Program` (new methods) except that the `name: &str` and `options: &[&str]` parameters of the existing functions are fixed. `version() -> Result<(i32, i32)>` (`lib.rs:143`) is a plain tuple; correct, and the only free function. `ptx()` converts with `from_utf8_lossy` (`lib.rs:99`), which cannot fail and cannot report corruption; PTX is ASCII, so this is acceptable (reasoning, not checked against NVRTC).
9. **Error type.** `Error = baracuda_core::Error<nvrtcResult>` and `Result<T, E = Error>` (`lib.rs:28-30`). The core enum is `#[non_exhaustive]` (`error.rs:122`, read), so the alias inherits that. `nvrtcResult` is a `-sys` newtype `struct nvrtcResult(pub i32)` with 12 associated constants (`-sys lib.rs:28-58`, read) and a public field, so the status type in this crate's signatures is an open newtype and not an enum (no exhaustiveness issue; a new NVRTC code needs no variant). Whether `Display` text comes from NVRTC's `nvrtcGetErrorString` or a static table in `-sys` is not checked (`CudaStatus::description`, `-sys lib.rs:62`).
10. **Dependencies.** `Cargo.toml` has 4 `[dependencies]` (`baracuda-types`, `baracuda-core`, `baracuda-nvrtc-sys`, `thiserror`) and 1 `[dev-dependencies]` (`baracuda-driver`). Grep over `src/lib.rs` and `tests/gpu_smoke.rs`: **`baracuda_types` is not used** (0 hits in both) and **`thiserror` is not used** (0 hits for `thiserror`; `derive(Error` also 0); control: the same grep finds `baracuda_core` (1 in `src`), `baracuda_nvrtc_sys` (1 in `src`) and `baracuda_driver` (2 in `tests/gpu_smoke.rs`). Two unused direct dependencies, to be removed after a build check (not built here; a proc-macro path use inside a macro is excluded by the 0 hits for `derive(Error`).

## Recommended order

1. Findings 1 and 2 (panic on NUL, log lost on the one-shot paths) together: both decide what `Err` carries and what `compile`/`compile_with` return, so they cannot be split after the freeze.
2. Findings 4 and 5 (`#[non_exhaustive]` or private fields on `CompileOptions`; string versus typed `arch`/`cpp_standard`; the `Option<bool>` inconsistency) and finding 6(d) (drop `to_str_refs`).
3. Finding 3 (write the `Send` argument; decide not to promise `Sync`).
4. Findings 6 (a-c, e), 7, 8, 9, 10, 11, 12 as cleanup: fix the four wrong doc lines, rewrite the README against the code (or delete the coverage claims), remove two unused dependencies, add `SAFETY` comments, add pure unit tests for `CompileOptions::to_strings`.

Nothing in this review was built, run, or checked against NVIDIA's documentation: findings 1-7, 10 and 11 (counts) are read from source with greps and controls stated; findings 2, 3 and 8 rest in part on NVRTC behaviour (handle thread-safety, double compile, error text source) recorded here as **not checked**.
