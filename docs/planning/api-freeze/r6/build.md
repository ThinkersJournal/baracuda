## Findings

1. **`CudaInstall` is an all-public-field struct with no constructor and no `#[non_exhaustive]`.** `#[derive(Clone, Debug)] pub struct CudaInstall` (`lib.rs:31-46`) has 5 public fields and is built in the crate by a struct literal (`probe_root`, `:108-114`). Any caller that builds or destructures it without `..` breaks when a field is added (the likeliest additions: the lib dir for a second platform layout, a `cudnn` path); the census column is 0 for all 6 rows. No code outside this crate writes the name `CudaInstall` (`grep -rn CudaInstall --include=*.rs crates`, excluding `baracuda-build/`: 0 hits; control: the same grep finds the 8 hits inside the crate). Field access through `detect_cuda()`'s return value in `baracuda-forge` was not checked. Decision: `#[non_exhaustive]` now; the cost to the one known user is nil unless it constructs the struct.
2. **Most of the public surface has no user in the workspace, and the `bindgen` feature is inert.** `emit_rerun_hints` is called from 17 build scripts (`grep -rl 'baracuda_build::emit_rerun_hints' --include=*.rs crates`, files outside the crate: 17). `detect_cuda`, `find_nvcc` and `parse_nvcc_version` are called only by `baracuda-forge` (`toolkit.rs:35`, `:36`, `:99`; the same grep minus `emit_rerun_hints` finds nothing else, which is also the control for the next claim). `find_library`, `emit_version_cfg` and `bindgen_builder` have 0 callers outside the crate (grep over `crates/**/*.rs`; control: the same grep finds the 3 forge calls). 17 `-sys` manifests declare `bindgen = ["baracuda-build/bindgen"]` (`Cargo.toml:15` in 16 of them, `:19` in `tensorrt-sys`), yet no `build.rs` calls `detect_cuda` or `bindgen_builder` (`grep -rn 'detect_cuda\|bindgen_builder' --include=build.rs crates`: 0; control: `emit_rerun_hints` is found in 17 build scripts), so enabling the feature compiles `bindgen` and nothing uses it. `bindgen_builder` also puts `bindgen::Builder` in a public signature (`:265`), tying this crate's semver to bindgen's (`bindgen = "0.73"` in the root `Cargo.toml:195`, read). Decision: either freeze the three zero-caller items as promised API or drop them and the feature before the freeze; dropping is breaking afterwards.
3. **Docs contradict the code.** (a) The crate doc says nothing here "reads NVIDIA's headers" (`:24-26`); `read_cuda_h_version` reads `include/cuda.h` (`:106`, `:149-168`). (b) `detect_cuda` carries "fall back via CUDA_PATH_V*_*" (`:83`) but both the Windows arm and the fallback arm are the empty slice (`:84`, `:86`), so Windows has no OS-default path and a Windows machine without one of the 4 env vars gets `None`; README says "standard locations on Linux/Windows" (`README.md:29-30`). (c) `emit_rerun_hints` emits a rerun for `CUDNN_LIB` (`:58`) which nothing in this crate reads (grep `CUDNN_LIB` in `src/lib.rs`: 1 hit, the hint; control: `CUDA_PATH` 4 hits) and none for `NVCC` or `PATH`, which `find_nvcc` reads (`:200`, `:218`); whether a `-sys` build script reads `CUDNN_LIB` itself is not checked (the grep over the other crates' `.rs` files for `CUDNN_LIB` found 0, the same files that hold the 17 build scripts). (d) README says the crate is "also re-exported via `baracuda-forge`" (`README.md:49-50`): `baracuda-forge/src` has 0 `pub use baracuda_build` (control: forge names `baracuda_build` 3 times by path in `toolkit.rs`), and forge takes it as a normal `[dependencies]` entry (`baracuda-forge/Cargo.toml:14`), not a build-dependency, against README's "contains no runtime code".
4. **Behaviour that is read as wrong or unchecked.** (a) `read_cuda_h_version` returns `None` for the whole file the first time a line starts with `#define CUDA_VERSION` and the remainder does not begin with digits: `.parse().ok()?` at `:160-161` leaves the function instead of continuing the loop, so a header with a line like `#define CUDA_VERSION_xxx` before the real one yields no version (whether real `cuda.h` files have such a line is **not checked**; no test covers it). (b) `find_library` falls back to major `12` when the version is unknown (`:176`, `:179`), and builds `lib{stem}.so.{major}` / `{stem}64_{major}.dll` assuming the soname major equals the CUDA major; its own doc names `"cudnn"` as an example (`:173`), whose soname major differs from CUDA's (from memory, **not checked**). On Windows it searches `install.lib`, which `pick_lib_dir` makes `lib\x64` (`:127-139`), where `.dll` files do not live (the code's own comment says that directory holds the import libraries, `:128-131`; reasoned, not run). (c) `detect_cuda` returns the first of 4 env vars that points at a dir with `include/` and a lib dir, without comparing versions; `CUDA_PATH` wins over a newer `CUDA_HOME`. (d) `pick_lib_dir` has the `targets/x86_64-linux/lib` fallback only for x86_64 (`:138`), so an aarch64 toolkit layout falls to `lib` or `bin`. (e) `parse_nvcc_version` takes `release 11` as `(11, 0)` (tested, `:323`).
5. **Cargo directive details.** All output uses the single-colon `cargo:` form (`:60`, `:256-257`); `emit_version_cfg` emits two `rustc-cfg` lines per call and no `cargo:rustc-check-cfg`, so a consumer that tests `cfg(cuda_12_6)` would see `unexpected_cfgs` warnings (grep `check-cfg` over `crates/**/*.rs` and `Cargo.toml`: 0 hits; control: `rustc-cfg` is found at `:256`).
