## Findings

1. **`new_host` plus a `DeviceBuffer` argument is a type-confusion in safe code.** `Generator::new_host` (`src/lib.rs:268-279`) builds the same `Generator` type as `Generator::new` (`:190-202`) through `curandCreateGeneratorHost`. Every generation method (`:221-386`) takes `&mut DeviceBuffer<T>` and passes `buf.as_raw().0 as *mut T` to cuRAND (e.g. `:224`). A host generator is documented in this crate as one whose "samples live in host memory" (`:267`), so a device pointer is handed to something that writes through host pointers; that is the standard cuRAND host-generator contract, from memory, **not checked**. The mismatch is not representable in the type system, produces no `Result` check beforehand, and there is no host-buffer generation method at all (every generation method takes a `DeviceBuffer`: 10 of 10, read), so `new_host` has no safe use in this crate at the freeze. Decision before 1.0: either split into `DeviceGenerator`/`HostGenerator` (or a type parameter) with host methods taking `&mut [T]`, or remove `new_host` from the frozen surface. Adding the host methods later is additive, but the single-type shape is the part that cannot change.
2. **The `Send` story contradicts itself, and the effective answer is `!Send`.** `Generator` is `#[derive(Clone)] struct { inner: Arc<GeneratorInner> }` (`:163-166`). `GeneratorInner { handle: curandGenerator_t }` where `curandGenerator_t = *mut c_void` (`baracuda-curand-sys/src/lib.rs:22`), so it is `!Send + !Sync` by default; the crate adds `unsafe impl Send for GeneratorInner {}` (`:172`) but no `Sync`. `Arc<T>` is `Send` only when `T: Send + Sync`, so `Generator` is `!Send` and `!Sync` anyway (reasoned from the auto-trait rules, **not compiled**, no `assert_not_send` test; the file has 0 `#[test]`). The comments say the opposite of the impl: `:195` "!Sync on purpose: cuRAND generators are not thread-safe" and `:198`/`:275` "handle is deliberately !Send/!Sync; the Arc only provides cheap same-thread clones". So (a) the `unsafe impl Send` at `:172` is dead weight with no `SAFETY` comment (0 `SAFETY` in the file, finding 10), and a future refactor that makes the `Arc` payload `Sync` would silently turn it live; (b) a generator cannot be moved to a worker thread, which is a usability decision users will hit (a per-thread-generator design needs creation on the worker). Decision: delete the `unsafe impl Send` and say `!Send`, or deliberately make the type `Send` (own the handle without `Arc`, or `Mutex`) and document why moving a cuRAND generator across threads is allowed (NVIDIA's rule is **not checked**). The two `#[allow(clippy::arc_with_non_send_sync)]` at `:196-199` and `:273-276` exist only to silence the lint that points at this.
3. **`Clone` shares one generator through `&self` mutation, and `set_stream` retains nothing.** `Clone` gives two handles to the same cuRAND state; `seed`, `set_offset`, `set_ordering`, `set_quasi_random_dimensions`, `generate_seeds` and all 10 generation methods take `&self` and mutate the generator (`:206`, `:282`, `:289`, `:296`, `:303`). A clone calling `seed` therefore changes the stream observed through every other clone: surprising for a type that reads like a cheap handle, and breaking to change after 1.0 (`&mut self` or removing `Clone`). It cannot race because of finding 2, but the shared-state semantic is undocumented. `set_stream(&self, stream: &Stream)` (`:214-218`) passes `stream.as_raw() as _` and keeps no `Stream` clone, so the stream can be dropped while the generator still points at it (use of a destroyed `CUstream` on the next generation call; whether `baracuda_driver::Stream` is refcounted so it can be held is **not checked**, `Stream` has `inner` and `context()` per `baracuda-driver/src/stream.rs:245-247`, read). Both are the usual freeze question: hold the stream in `GeneratorInner`, or document the lifetime requirement.
4. **Generator-type enum: `RngKind` is closed, partial, and its naming is not uniform.** `#[derive(Copy, Clone, Debug, Eq, PartialEq, Default)] pub enum RngKind` with 10 variants (`:87-110`) has no `#[non_exhaustive]` (census column 0 for all 41 rows; cross-checked: `grep -rn non_exhaustive crates/baracuda-curand`: 0 hits in the crate; control: the same grep over `baracuda-curand-sys/src` finds `finish_non_exhaustive` at `lib.rs:311`, so the grep works). The sys enum `curandRngType_t` has 11 variants (`baracuda-curand-sys/src/lib.rs:27-51`, `#[repr(i32)]`) including `QUASI_DEFAULT = 200` (`:42`), which `RngKind` has no variant for (`RngKind::raw` `:114-127` is an exhaustive match over 10; control: the same file maps all 10), so the README's "All RNG kinds" (finding 12) is not literal. NVIDIA has added generator types before (Philox, MTGP32, MT19937 and the Sobol family are all listed here), from memory, **not checked**, so adding `#[non_exhaustive]` before 1.0 is nearly free and removing the need later is breaking. Naming: `XORWOW`, `MRG32K3A`, `MTGP32`, `MT19937` are all-caps, `Philox4_32_10` is mixed with underscores, `Sobol32`/`ScrambledSobol32` are CamelCase; there is a variant named `Default` next to `#[derive(Default)]` with `#[default]` on it (`:90-91`), legal but `RngKind::Default` reads as the trait. The pseudo/quasi split is only in doc comments, not in the type (finding 8). Decision: `#[non_exhaustive]`, add `QuasiDefault` or drop the claim, pick one casing convention now.
5. **Generation functions do not validate buffer length against count; the count is always `buf.len()`.** All 10 call sites pass `buf.len()` as `n` (grep `buf.len()`: 12 hits = those 10 at `:224,231,244,260,313,320,330,350,365,380` plus 2 doc mentions at `:24` and `:236`; control: the same file's `check` at `:83` is found by the `Error::` pattern in the same pass). Because the count is taken from the buffer, a count larger than the buffer cannot occur: the memory-safety question is closed by construction, and it matches the `curandGenerate*` signatures taking `n: usize` (`baracuda-curand-sys/src/lib.rs:169-174` read). There is no `assert`, `is_empty`, `is_multiple_of`, `% 2` or `len() ...` comparison anywhere in `lib.rs` (grep for `assert|len() *[%<>=!]|is_empty|Error::` in `src/lib.rs`: 1 hit, `:83`, the `Error::check` line; so 0 length checks, with that line as the positive control that the pattern matches). Consequences: (a) the even-length rule is documentation only (`:236` "must be **even**", also the crate doc at `:24`) and applies, per the doc, to `normal`; `normal_f64`, `log_normal` and `log_normal_f64` carry no such sentence, and the unchecked variants all rely on cuRAND returning `CURAND_STATUS_LENGTH_NOT_MULTIPLE` (from memory, **not checked**) rather than the wrapper, so the failure is a late `Err`, not a precondition; (b) an empty `DeviceBuffer` is passed through with `n = 0` and a possibly null pointer (whether `DeviceBuffer::new(ctx, 0)` allocates is **not checked**); (c) a sub-range cannot be filled (a `DeviceSlice` exists in the driver, `memory.rs:1059`, but no method takes it). Decision: freeze `&mut DeviceBuffer<T>` as is and add slice overloads later, or take `impl DevicePtrMut<T>` now (the driver implements it for `DeviceBuffer`, `memory.rs:1323`, read) which is the shape that survives; and either check the even length (`Err`) or keep the documented contract but say it for all four normal-family methods.
6. **Generator/distribution pairing is not typed.** `uniform_u32` (`:310`) and `uniform_u64` (`:317`) call `curandGenerate`/`curandGenerateLongLong`; cuRAND restricts the 64-bit call to 64-bit quasi-random generators and some distributions to pseudo-random ones, from memory, **not checked**. The wrapper accepts any `RngKind` with any method, so the user's error surface is a `curandStatus_t` code. `poisson`, `binomial`, `log_normal*` and the rest are on one `Generator` regardless of kind. That is a deliberate thin wrapper; the freeze consequence is that tightening it into typestate (`PseudoGenerator`, `QuasiGenerator`, finding 8) is a breaking rewrite, whereas documenting the valid pairings is not.
7. **`Ordering` is a naming and doc problem.** The type is named `Ordering` (`:132`), shadowing `std::cmp::Ordering` and `std::sync::atomic::Ordering` in any file that glob-imports it or names it unqualified; the crate itself imports `std::sync::Arc` only (`:69`), so no collision inside, but the name is a frozen public one (`baracuda_curand::Ordering`); `GeneratorOrdering` or `SequenceOrdering` would avoid it. Variants repeat their domain (`Pseudo*` x5, `QuasiDefault` x1), mirroring `curandOrdering_t` (`baracuda-curand-sys/src/lib.rs:56-68`, 6 variants, read). Doc drift: `Ordering::PseudoLegacy` is documented "Pre-CUDA-11 legacy ordering" (`:140`) while the sys doc says "pre-9.0 compatibility" (sys `:63`); the two disagree and neither is checked here against NVIDIA. Closed enum (`non_exhaustive` 0, same grep as finding 4), 6 variants of a 6-variant sys enum, so the same adds-a-variant risk applies. `set_ordering` (`:289`) accepts any ordering on any generator.
8. **Seed and offset API shape.** `seed(&self, seed: u64)` (`:206`) wraps `curandSetPseudoRandomGeneratorSeed` (sys `:171` area, `seed: u64`, read) and is on every `Generator`, including Sobol kinds where a pseudo-random seed does not apply (cuRAND returns a status, from memory, **not checked**); `Generator::new` takes no seed, so the initial state is whatever cuRAND defaults to, and the doc claim "Call before any `uniform`/`normal` to make subsequent output deterministic" (`:204-205`) leaves open what happens without the call (**not checked**). `set_offset(&self, offset: u64)` (`:282`, doc "Absolute offset into the sequence"), `set_quasi_random_dimensions(&self, num_dimensions: u32)` (`:296`, no range stated in the docs, cuRAND's limit is from memory and **not checked**) and `generate_seeds` (`:303`, "useful before offset resets", with no explanation of ordering relative to `seed`/`set_offset`) are all free-standing setters on one mutable-through-`&self` type. The things that are hard to change after 1.0: (a) `u64` as the seed type (cuRAND's seed is `unsigned long long`; ports to a wider seed or a `[u32; 4]` Philox key would be a new method, not a change), which is fine; (b) the construct-then-mutate shape versus builder/typed constructors (`Generator::pseudo(kind, seed)`, `Generator::quasi(kind, dims)`) which would fix findings 6 and 8 together; (c) `set_ordering` after `seed` ordering sensitivity, undocumented. Decision: pick the construct-then-mutate shape deliberately and document the call order, or move the seed and dimensions into constructors.
9. **`Error`, `Result`, `version`.** `Error = baracuda_core::Error<curandStatus_t>` (`:77`), `Result<T, E = Error>` (`:79`), `version() -> Result<i32>` (`:396-402`) returns cuRAND's raw packed integer ("`10400` = 10.4.0", `:395`; the encoding is from memory, **not checked**); an `i32` is a freeze commitment to the packed number rather than a `(major, minor, patch)` struct. `curandStatus_t` is a newtype `curandStatus_t(pub i32)` (sys `:77`, read), not an enum, so `Error<curandStatus_t>` stays forward-compatible with new status codes (matches the finding-3 treatment in `nvml.md`, which does not apply here). `Drop for GeneratorInner` (`:404-412`) swallows both the loader error and the destroy status with `let _ =` (like the other crates): acceptable for `Drop`, noted.

The FFI calls pass the `handle` owned by `GeneratorInner` (valid until `Drop`), `&mut handle` stack out-pointers, and `buf.as_raw().0 as *mut T` with `n = buf.len()` from the same `&mut DeviceBuffer<T>`, which reads as sound for a device generator on a live context (finding 1 and the `Stream` lifetime in finding 3 aside); no comment states it. The workspace sets `missing_docs = "deny"` and `missing_debug_implementations = "warn"` (root `Cargo.toml:225-226`); there is no `undocumented_unsafe_blocks` lint in `[workspace.lints.clippy]` (read, `:229-234`: only `all`, `too_many_arguments`, `type_complexity`). By name they cover `Generator::new` (Philox only), `seed`, `uniform`, `normal`, `DeviceBuffer::copy_to_host`: 4 of 41 items; untested: `new_host`, `set_stream`, `set_offset`, `set_ordering`, `set_quasi_random_dimensions`, `generate_seeds`, every other generation method (8 of 10 methods), 9 of 10 `RngKind` values, all of `Ordering`, `version`, `as_raw`. `examples/uniform.rs` (read lines 1-50) exercises `new`, `seed`, `uniform` only.

## Recommended order

1. Finding 1 (`new_host` with device-only methods) and finding 2 (`Send` impl versus `Arc`): both change the shape of `Generator` and its constructors, so decide together with finding 8 (constructor and seed/dimension shape) and finding 6 (typestate or documented pairings).
2. Findings 4 and 7 (`#[non_exhaustive]` on `RngKind` and `Ordering`, `QuasiDefault`, the name `Ordering`, casing): near-free before 1.0, breaking after.
3. Finding 5 (length contract: even-count check, `impl DevicePtrMut<T>` versus `&mut DeviceBuffer<T>`) and finding 3 (`Clone` with `&self` mutation, `Stream` retention).
4. Findings 9, 10, 11, 12, 13 as cleanup: `SAFETY` comments (or delete the dead `unsafe impl Send`), unit tests for the pure mappings and the 8 untested methods, remove the 3 unused dependencies after a build check, rewrite the README against the code.

Nothing in this review was built, run, or checked against NVIDIA's documentation: findings 2 (auto-trait result), 3 (`Stream` retention), 5, 9, 10, 11 are read from source and greps with the controls stated; findings 1, 4, 6, 7, 8 rest in part on cuRAND behaviour recorded here as **not checked**.
