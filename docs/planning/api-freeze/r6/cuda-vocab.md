## Findings

1. **The crate's closed vocabulary rests on a foreign enum that is deliberately closed, and `Entry.sku` is a public field of that type.** `pub struct Entry { pub sku: ArchSku }` (`lib.rs:50-53`) puts `unpopped_vocab::ArchSku` in this crate's public signature (grep `unpopped_vocab` in `lib.rs`: 3 hits; control: `manifest.rs` 0, as expected, it reaches the type through `Entry`). `ArchSku` (Unpopped `layout.rs:69`, 4 variants `Sm80/Sm89/Sm90/Sm90a`) is documented "Intentionally NOT `#[non_exhaustive]`" and "New variants are a deliberate breaking-change event" (`layout.rs:~62-68`, read). So: (a) a new token in `cuda-vocab` requires a breaking release of `unpopped-vocab` first, then of this crate (`CATALOG` literal is not `non_exhaustive`-safe either way); (b) the dependency is `unpopped-vocab = "~0.47.0"` in the workspace (`Cargo.toml:74`; `Cargo.lock` has `unpopped-vocab 0.47.0`), a pre-1.0 tilde pin, so every Unpopped minor is a coordinated release; Unpopped `origin/main` is at 0.56.6 (`crates/unpopped-vocab/Cargo.toml`, read; whether that is published is **not checked**), so the pin is behind the working head; (c) the lib doc (`lib.rs:22-26`) says the end state migrates `ArchSku` into this crate; that move would change the type path of `Entry.sku` for every consumer, i.e. the freeze commits to a type that is planned to move. Decision: either freeze with `sku` private and a constructor/accessor (non-breaking later swap of the type), or accept the public foreign type and record that the freeze is coupled to `unpopped-vocab`'s minor.
2. **`Entry` is constructible with any `ArchSku`, and the derived accessors panic on a token they do not expect.** `Entry { sku }` can be built outside `CATALOG` (the field is `pub`; the in-crate tests do it only through `CATALOG`). `sm_number` calls `.expect("a cuda: token from the codec begins `cuda:sm`")` and `.expect("... at least one digit ...")` (`lib.rs:69-76`); `class` is "ends with `a`" (`lib.rs:84`). Today the 4 `ArchSku` variants all satisfy this (test `derivation_matches_the_grammar`, `lib.rs:154`), so the panics are unreachable now; they become reachable the day `ArchSku` gains a variant whose codec token is not `cuda:sm<digits>[a]`. Each of `token`, `sm_number`, `class` re-runs the codec and allocates a `String` (`token()` returns `String`, `lib.rs:59`); `admits` allocates twice (`class()` and `sm_number()`, `lib.rs:97-101`). Not a correctness issue; a signature commitment: `token() -> String` cannot become `&'static str` later without breaking callers that take ownership. Decision: keep and document, or return `&'static str` now (a `match` over the 4 variants is possible only if the crate stops delegating to the codec, which is its stated design).
3. **The manifest is a wire format, and the Rust struct is its schema.** `Manifest`, `Encoding`, `Member`, `DeviceAdmission` derive `Serialize, Deserialize` with no `#[serde(..)]` attribute (grep `serde` in `src`: the `use` at `manifest.rs:28`, 4 derives at `:31,65,76,90`, `serde_json` at `:165` in library code; control: the same grep finds the test-only `serde_json` uses at `:190-211,407`, so the `serde_json` dependency is used in lib code at exactly 1 line). Consequences, each a commitment after the freeze: (a) the JSON key names are the Rust field names and the key order is the struct field order (`to_json` doc, `manifest.rs:161-163`), and the committed `cuda-vocab-manifest.json` (49 lines) is byte-compared with the generator by test `freshness_committed_manifest_matches_the_generator` (`:255`); reordering or renaming a field is a wire change and a test red; (b) all 4 structs are plain `pub` structs with all fields `pub` and none `#[non_exhaustive]` (grep `non_exhaustive` in `src`: 0; control: `derive(` found 6 times, 2 in `lib.rs`, 4 in `manifest.rs`, so the grep reaches the files), so adding a field is breaking for anyone who struct-literals or destructures them; (c) no `#[serde(deny_unknown_fields)]`, so a reader built today silently drops a field added later; (d) 22 of the 25 public fields are `String` for values that are closed sets or enums by the spec (`kind` = `enumerated`, `comparison` = `byte-exact`, `capability_set_shape` = `single-scalar`, `Member.class` = `base`|`a`, `schema`, `namespace`), and a `Manifest` can be built or deserialized with any strings, so it is a free-text record, not a validated vocabulary; (e) `Member.sm_number: u32` and `Manifest.vocabulary_version: u32` are the only typed values. `Manifest::generate()` takes no arguments and returns constants plus `CATALOG`; the hard-coded values `"kiss-namespace-vocabulary-v1"`, `"cuda"`, `1`, `"baracuda"` (`manifest.rs:129-134`) are the schema's identity and move only with a `vocabulary_version` decision. Decision: mark the 4 structs `#[non_exhaustive]` (and say so, since the crate also deserializes them), or document that the shape is frozen and new fields mean a new schema id.
4. **`CATALOG` is called "closed, exhaustive" while KISS's own seed has 13 tokens, and widening it is a version decision the code says it is not making.** The `CATALOG` doc (`lib.rs:105-107`): "The closed, exhaustive `cuda-vocab v1` token set ... `{ sm80, sm89, sm90, sm90a }`". The vendored seed (`kiss-cuda-seed.tsv`, pinned `5b28bf51`, header lines 1-6) has a 13-row token set and a 4-row dispatch set (`grep -c '^cuda:'`: 13; `grep -c '^Sm'`: 4; control: the 4 `Sm` rows are the 4 `CATALOG` members, per test `catalog_is_cuda_vocab_v1`, `lib.rs:140`). `manifest_lists_the_four_dispatch_members_not_the_token_set` (`manifest.rs:435`) pins 4 and states that widening to the 13 is "a `vocabulary_version`/schema decision for the maintainer". The `Cargo.toml` and the README say the same ("the open `cuda:smNN` target model accepts tokens outside this closed set (for example `cuda:sm61`)", `README.md:6`). So the 42 rows freeze the 4-token view; `sm61/70/75/86/100/100a/120/120a/121` (named in the test comment, `manifest.rs:427-428`) have no representation in the API. That is a deliberate scope choice, but "closed" in the public doc and `kind = "enumerated"` in the manifest read as the whole `cuda:` vocabulary. Decision: say in the public doc of `CATALOG` and `Manifest.members` that the set is the dispatch subset, or settle the widening before the freeze, since a wider set changes `ArchSku` (finding 1), `CATALOG`'s length and the committed JSON.
5. **`TokenClass` has no commitments written down, and its names differ from the wire spelling.** `#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)] pub enum TokenClass { Base, Exclusive }` (`lib.rs:36-44`): no `repr`, no explicit discriminants, no `Ord`, no `serde` (grep `repr(` in `src`: 0), no `non_exhaustive`. That is a good shape for a vocabulary type that is never serialised as a number, and it means the absence of a numeric-value commitment is real, not an omission (control: `class_str`, `manifest.rs:100-105`, is the one place a class leaves the Rust type, and it emits strings). Items worth a decision: (a) the variants are `Base`/`Exclusive` but the wire and the spec spell them `base`/`a` (`manifest.rs:102-103`); a reader of the JSON cannot map back to the Rust name without `class_str`, which is private; (b) a third class (the seed has `100a`, `120a`, which are still `a`) would be a spec change, so closed is right, but without `#[non_exhaustive]` an added variant breaks every exhaustive `match` (this crate has 3, `lib.rs:98-101`, `manifest.rs:102-103`, and `lib.rs:85`'s `if`); the crate's own tests use `matches!`. Decision: keep closed (the admission relations are exhaustive by construction, `lib.rs:97-102`) or add `#[non_exhaustive]` and a `_` arm; either is fine, but choose.
6. **The `device_sm` numeric encoding is a documented convention with no type.** `Entry::admits(&self, device_sm: u32)` takes "`major x 10 + minor`" (doc `lib.rs:91-92`, repeated as text in `DeviceAdmission.device_sm_number`, `manifest.rs:145`). Tested for 80/89/90/100/70 (`lib.rs:184-217`). Compute capabilities with a two-digit minor (none today) or the `sm_121`-style numbering fit the formula only if the minor stays below 10, from memory, **not checked**. Same encoding means `sm_number` for `cuda:sm100` is 100 (u32, fine). A bare `u32` for "compute capability" is the public vocabulary here; a newtype would be non-breaking to add only as a second method, not as a replacement. Recommendation: freeze as `u32`, state the formula in the `admits` signature doc (already done) and that no validation of `device_sm` is performed.

The generator is `manifest.rs` (`pub mod manifest`, `lib.rs:28`); the freshness and semantic gates are tests `:255` and `:344`. `manifest.rs:13-14` says agreement "is a separate relation, owed by the agreement gate (a follow-on to this generator)", while `manifest.rs:20-22` and test `semantic_agreement_with_the_pinned_kiss_seed` (`:344`) say the gate is carried in this module. A reader of the rendered docs gets two stories. Also `README.md` (8 lines) does not mention the manifest, `cuda-vocab-manifest.json`, `Manifest`, or `manifest_json` (grep: 0; control: it names `ArchSku` and `unpopped-vocab`), so the `manifest` module, 4 of the 5 structs and 28 of the 42 census rows are not described in the README; the README is also not `include_str!`d (the only `include_str!` in `src` is the seed at `manifest.rs:350`, grep). ## Recommended order

1. Finding 1 (is `Entry.sku` public and `ArchSku`-typed, and what does the freeze promise about `unpopped-vocab`) and finding 4 (is the frozen vocabulary the 4 dispatch tokens or the 13-token set): both change what `CATALOG` and the JSON contain.
2. Finding 3 (`#[non_exhaustive]` on the manifest structs, `deny_unknown_fields`, `String` fields that are enums) and finding 5 (`TokenClass` closed or not): both change what callers write.
3. Finding 2 (`token()` return type, panic paths) and finding 6 (`device_sm` as a bare `u32`) as freeze decisions with cheap options.
4. Findings 7, 8, 9, 10, 11, 12 as cleanup: fix the two stale "follow-on" docs, README against the code (add the manifest module), `serde`/`serde_json` through the workspace table, decide naming, and settle the version-follows-Unpopped question.

Nothing in this review was built, run, or checked against NVIDIA's or KISS's documents. Findings 1 (the `ArchSku` doc and variants), 2, 3, 4, 5, 7, 8, 9, 10, 11 are read from source and greps with the controls stated; the `From<ArchSku> for TargetId` body, the committed JSON's bytes, the packaged file list, the tests' results, and Unpopped 0.56.6's publication status are **not checked**; finding 6's remark on two-digit minors is from memory.
