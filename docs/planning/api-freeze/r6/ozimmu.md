## Findings

1. **`Handle` does not keep the stream it is bound to, and the docs say it does.** The struct doc lists "a copy of the bound CUDA stream" among what the handle owns (`lib.rs:361`); the struct has two fields, `raw` and `_not_sync` (`:375-378`). `set_stream(&self, stream: &Stream)` passes `stream.as_raw()` to the shim and returns (`:414-421`), so the stream can be dropped (and destroyed) while the handle still holds it, and the next `dgemm` enqueues on a dead stream. The SAFETY comment says the raw stream is valid "for the stream's lifetime" (`:416-417`), which is the caller's burden, not enforced. `set_stream` takes `&self` and changes the handle's state, which the doc calls "sticky" (`:413`). Decision: hold an `Arc`/clone of the driver stream in `Handle`, or make `set_stream` `unsafe`, or change the doc to say the caller must outlive it; each is a signature or semantic change. Whether the shim tolerates a destroyed stream is **not checked**.
2. **`dgemm` and `dgemm_with_variant` are two 14- and 15-argument `unsafe fn`s with a copied body, and validation is partial.** The two bodies at `:475-516` and `:555-597` are the same 40 lines except the last FFI argument; `dgemm` could delegate to `dgemm_with_variant(.., OzakiVariant::Base)` (the doc claims they are bit-identical, `:523-524`, from the docs, **not checked**). 14 and 15 positional arguments (`op_a, op_b, m, n, k, alpha, a, lda, b, ldb, beta, c, ldc, compute_mode[, variant]`) are a transposition risk that a descriptor struct would remove; the cost of changing it later is a breaking change, so decide now. Checks: `m, n, k > 0` and leading-dimension minimums for the three matrices (`:475-491`); not checked: null pointers, `lda * k` overflow, buffer sizes (the `# Safety` section states them, `:451-457`). The `InvalidArgument` strings are `&'static str` (`:98`), so the message cannot name the value. The README's quick example does not match either signature (finding 9).
3. **`Handle` is `Send`, not `Sync`, by hand.** `unsafe impl Send` (`:629`) carries a comment arguing device-side state (`:625-628`) and the struct holds `PhantomData<*mut ()>` so it is `!Sync` (`:377`); the `unsafe impl` has no `SAFETY:` prefix, and the argument "`set_stream` re-binds to whichever stream the new-owner thread provides" does not cover a handle still bound to the old thread's stream (finding 1). Whether a cuBLAS handle may move between threads is **not checked**. `Drop` ignores the `destroy` status (`:617-619`); its comment correctly says nothing can be done, but a handle dropped with work still queued on its stream is the usage error the doc names (`:363-369`) and nothing prevents it. `as_raw` is a safe fn that returns the raw handle (`:603`); the doc says not to destroy it, fine for reading, and it puts a `-sys` type (`sys::OzimmuHandleT`, `*mut OzimmuHandle`) in the public signature.
4. **`usize` dimensions go to a C `usize` unchanged.** `m, n, k, lda, ldb, ldc: usize` (`:461-472`) match the shim's `usize` (`ozimmu-sys/src/lib.rs:203-263`); cuBLAS itself takes `int` (from memory, **not checked**), so what the shim does above `i32::MAX` is **not checked**. The `reallocate_working_memory_bytes` doc says it returns "the new total scratch size" or `0` (`:425-427`), a mixed sentinel: `0` means "already large enough", not "failed", and an allocation failure has no channel (it returns `usize`, not `Result`). `precision_guarantee` is a `const fn` without `self` (`:434`) although its doc says "this handle's `dgemm`", so it is the same for every handle by construction (finding 8).
5. **`Error`: 4 variants, `non_exhaustive`, integers as payload.** `#[non_exhaustive]` at `:78`; its two in-workspace consumers match with a `_` arm (`baracuda-cutlass/src/plan.rs:4472-4475`) and destructure one variant with `if let` (`:4540`), so the attribute is honoured. `CreateFailed(i32)`, `DestroyFailed(i32)`, `DgemmFailed(i32)` carry a raw status whose mapping the doc admits is not stable (`:80-82`); `DgemmFailed`'s doc says it is a `cublasStatus_t` (`:91-92`), which makes the number part of the contract. `DestroyFailed` is never constructed: grep for `DestroyFailed` in `src/lib.rs` gives 1 line (the variant definition at `:89`; its `#[error]` and doc lines do not name it) and nothing builds it (control: `CreateFailed` is built at `:397` and `:400`), because `Drop` discards the status. A public variant nothing returns: decide to keep it for a future `Handle::close(self) -> Result` or drop it before the freeze. `Error::CreateFailed(-1)` for a null handle (`:400`) invents a status code.
6. **The two enums are closed by `non_exhaustive` but their variants are a numbering.** `OzakiSlices` has 16 numbered variants plus `Auto` (`:123-165`); a new slice count would be a variant, and 16 of 17 variants encode a number that `slice_count` (`:256`) hard-codes a second time; `S3..=S18` is a range written 3 times (the enum, `to_compute_mode`, `slice_count`). A `Slices(u8)` newtype with consts would be smaller, but `non_exhaustive` already allows adding variants, so this is a taste item, not a freeze blocker. `OzakiVariant` (`:192`) has `Base`, `EF`, `RN`, `H` with doc naming a 2025 variant as a plausible addition (`:186-189`), fine under `non_exhaustive`; it derives `Default` = `Base` (`:190, 195`) and `OzakiSlices` has a manual `Default` = `S8` (`:167`), whereas `Op` and `MallocMode` (`:286`, `:311`) have no `non_exhaustive`: `Op` is documented real-only with no conjugate transpose (`:279-285`), so a future `C` is plausible but would be breaking; `MallocMode` could grow a third allocator. Decision: add `#[non_exhaustive]` to `Op` and `MallocMode`, or state them closed.
7. **FFI integers are public methods.** `OzakiSlices::to_compute_mode` returns `sys::ComputeMode` (a `c_int` alias, `-sys` `:75`), `OzakiVariant::to_ffi` and `Op::to_ffi` return `i32` (`:218`, `:296`); all three are public, so the values (`Op::N = 0`, `T = 1`; variants `0..=3`; compute modes `2..=18`, with `1` = `COMPUTE_MODE_DGEMM` unreachable from `OzakiSlices`, `-sys` `:78`) are frozen as API, not as an implementation detail. Their only in-crate callers are `dgemm` and `dgemm_with_variant`; no caller outside this crate: grep for `to_compute_mode` and `.to_ffi()` over `crates` outside `baracuda-ozimmu` and `-sys` finds 0 uses on an ozimmu type (control: `to_ffi` is found in 2 other crates, `baracuda-optim` and `baracuda-transformer-engine`, which have their own methods of that name, so the grep reaches `.rs` files across the workspace). Decision: `pub(crate)`, or keep them and say the numbers are stable. The host test `slices_enum_round_trip` (`tests/dispatch_smoke.rs:163-187`) asserts `1..=18`, which would also pass for a mapping to `COMPUTE_MODE_DGEMM = 1`.
8. **`PrecisionGuarantee` is a 2-bool struct with public fields, both always `true`.** `bit_stable_on_same_hardware`, `deterministic` (`:336`, `:341`), constructed only by `standard()` (`:346`); no `non_exhaustive` (census 0) and no `Default`, so a third field breaks every struct-literal caller. The docs say `Auto` is "also deterministic" (`:339-340`), so there is no value that is not `standard()`: the type carries no information today. The doc says it mirrors `baracuda_kernels_types::PrecisionGuarantee` without depending on it (`:322-325`), a deliberate duplicate type. Decision: `non_exhaustive` plus constructor, or fold into `baracuda-kernels-types` when the integration exists.
