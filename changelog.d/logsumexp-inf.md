kind: Fixed: `LogSumExp` and `LogCumsumExp` returned NaN for infinite inputs and `LogCumsumExp` dropped a leading NaN
---
`ReducePlan` `LogSumExp` shifted by the row maximum, so a row whose maximum is infinite (all `-inf`, or any `+inf`) computed `inf - inf = NaN`: `logsumexp [-inf, -inf]` returned NaN (torch: `-inf`) and `logsumexp [inf, -inf]` returned NaN (torch: `inf`). A row that is infinite is now shifted by 0, which gives `-inf` and `inf`. `ScanPlan` `LogCumsumExp` had the same flaw in its running-max scan and also lost a NaN seen before any finite value (`[NaN, 1]` returned `[NaN, 1]`, torch `[NaN, NaN]`; `[-inf, 1, -inf]` returned `[NaN, 1, 1]`, torch `[-inf, 1, 1]`; `[inf, inf]` returned `[NaN, NaN]`). The scan now treats a NaN as sticky, a `+inf` as making every later prefix `+inf`, and a `-inf` as adding nothing. Rows of finite values are unchanged. Affected: `baracuda-kernels` and `baracuda-kernels-sys` from 0.0.1-alpha.21 (the first tag containing `reduce_logsumexp_fp.cu` and `scan_log_cumsum_exp_fp.cu`, both added 2026-05-17 by cd6845ad4) through 0.1.0-alpha.190. The backward kernels are not changed here. New `tests/logsumexp_inf_nan.rs` (8 device tests: f32, f64, f16, bf16, forward reduce and scan in both scan directions, rows with NaN, +-inf and finite values, against an f64 closed form).
