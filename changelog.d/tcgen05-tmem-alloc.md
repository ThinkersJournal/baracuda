kind: Added: tensor-memory allocation statements (Tcgen05Alloc, Tcgen05RelinquishPermit, Tcgen05Dealloc) lower in baracuda-cuda-emit for sm_100a (ROADMAP S12a-1)
---
`baracuda-cuda-emit` lowers the unpopped IR's tensor-memory management statements. A `Tensor` allocation becomes the 32-bit tensor-memory address that `tcgen05.alloc` writes, kept in one `__shared__ unsigned int` word (not an array: an ordinary access is still refused); `Tcgen05Alloc`, `Tcgen05RelinquishPermit` and `Tcgen05Dealloc` lower to `tcgen05.alloc.cta_group::1.sync.aligned.shared::cta.b32`, `tcgen05.relinquish_alloc_permit.cta_group::1.sync.aligned` and `tcgen05.dealloc.cta_group::1.sync.aligned.b32` (PTX ISA 9.5 9.7.18.7.1). The source carries an `#error` guard for an older `__CUDA_ARCH__` and the interface requires `tcgen05 (sm_100a or newer)`; the emitter's backstop refuses by name a column count that is not a power of two in 32..=512 and an allocation that does not hold `128 * ncols` elements.

RUNTIME UNVERIFIED on hardware: the lane's box is an RTX 4070 (sm_89) with no tensor memory. Checked: the emitted text; NVRTC for `sm_100a` compiles the source and `ptxas -arch=sm_100a` accepts the PTX (a mutant that corrupts the mnemonic is rejected by ptxas, "Unknown field '.cta_group::1'", so the test can fail); the same source for `sm_89` is refused by the arch guard. That is no claim beyond what ptxas accepted. Not lowered, and not built: `Tcgen05Mma`, `Tcgen05Ld` and `Tcgen05Commit` (S12a-3 to S12a-5; the emitter also refuses a subgroup launch, which `Tcgen05Ld` needs, so that comes first), and the forms ROADMAP S12 holds (a commit multicast with a `ctaMask`, an `mbarrier` arrive with a count or a mask, an `expect_tx` multicast; pm-kernels 2026-11-27, findings not advice, not a clearance). The `unlowered_statements.rs` tests that asserted these statements and allocations were refused now assert they lower (and that `Tcgen05Ld` is still refused by the emitter). New test file `tcgen05_alloc.rs`. The CI device run is queued, not claimed.
