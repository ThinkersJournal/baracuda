kind: Fixed: two baracuda-runtime device tests failed intermittently under cargo's parallel harness (capture on a blocking stream; a shared host-callback counter); `Stream::capture` documents the hazard
---
Device run 45928213378 (main 09d5431d) failed `wave1_smoke` `capture_mode_enum_also_works` (cudaError 901) and `stream_write_value_32` (906), and a local loop reproduced it: the whole `wave1_smoke` binary at the default thread count failed in 3 of 30 runs, always the capture test (901) plus a different victim each time (`stream_write_value_32`, `graph_exec_update_retargets_output`, `pitched_2d_roundtrip`: 906); with `--test-threads=1`, `--test-threads=2` and the capture test alone, 0 of 30 failed each. Cause (measured by the change below, not read from the driver): the capture ran on `Stream::new()`, a blocking stream, which synchronises with the legacy default stream, so another thread's legacy-stream call during the capture invalidated it. The capture tests (`wave1_smoke` and `runtime_extras_smoke`) now use `Stream::non_blocking()`: on one clock, interleaved, the old binary failed 9 and 11 of 80 (and segfaulted once in each loop) and the fixed one 0 of 80 (an intermediate build, with only the capture change, failed 2 of 80 on a second defect below). Second defect: `explicit_graph_kernel_and_host_nodes` and `stream_launch_host_func` shared one static counter, each resetting it and expecting exactly 1, so the graph test read 2 (`left: 2 right: 1`, twice in 80); it has its own counter now. All 8 runtime test binaries then passed 30 of 30. `Stream::capture` documents the blocking-stream hazard. No behaviour change in the library. The CI device run is queued, not claimed.
