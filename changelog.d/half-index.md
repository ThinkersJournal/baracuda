kind: Added: half-precision (f16, bf16) Gather, ScatterAdd, GatherBackward and IndexSelectBackward
---
The half index family (the Fuel GAP-413 set after MaskedFill, alpha.215), one PR and one fragment. Out-of-range indices are still skipped (a documented divergence from torch; `IndexBoundsPlan` detects them); half scatter-add and the backward kernels use the compare-and-swap add, so the order of additions into one cell is undefined, as torch CUDA atomics.

**GatherPlan, f16 and bf16 sources.** `GatherPlan` (`out[..., j, ...] = src[..., index[..., j, ...], ...]`) now accepts f16 and bf16 sources, i32 and i64 indices. It routes them onto the existing 2-byte bit-copy kernels (`gather_u16`, `gather_i64idx_u16`); a gather has no arithmetic, so every value comes back bit-for-bit (NaN payloads, signalling NaN, -0, infinities, subnormals, the largest finite values). The index policy is the one f32 has: an out-of-range or negative index leaves that output cell untouched (a kernel cannot raise an error; `IndexBoundsPlan` detects it), pinned by a sentinel in the test. Before, `select` returned `Unsupported` for a half source (ROADMAP E3 #3; Fuel's GAP-413 asks for the half index ops). Device test `gather_half` (f16 and bf16; sm89): gather dim first and last on rank 2, the middle dim on rank 3, duplicate indices, a size-1 source, i32 and i64 indices, out-of-range and negative indices: 8 of 8 pass, red on the old plan (`select` returned `Unsupported`, all 8). `ScatterPlan` already took f16/bf16 (its own kernels); `GatherBackwardPlan` and `ScatterAddPlan` half are separate rows (new atomic family for the latter). The CI device run is queued, not claimed.

**ScatterAddPlan, f16 and bf16.** `ScatterAddPlan` (`out[..., index[..., j, ...], ...] += updates[..., j, ...]`) now accepts f16 and bf16, i32 and i64 indices (ROADMAP E3 #4; Fuel's GAP-413). Four new symbols, `baracuda_kernels_scatter_add_{f16,bf16,i64idx_f16,i64idx_bf16}_run`, instantiate the existing scatter-add kernel on `__half` / `__nv_bfloat16`; the add is the library's compare-and-swap loop on the 32-bit word that holds the 2-byte cell (`baracuda::atomic::add`), not a native half atomic. With duplicate target indices the ORDER of the additions into one cell is undefined, so a half result is only as reproducible as the rounding of its partial sums (the plan docs say so); an out-of-range or negative index is skipped, the policy of every indexing plan (`IndexBoundsPlan` detects it). Device test `scatter_add_half` (f16 and bf16; sm89): 200 updates into 3 rows with exactly representable partial sums, 20 runs each for i32 and i64 indices, equal to an f64 accumulation rounded once to the dtype; `+inf + -inf` and a NaN update give NaN, `+inf` plus a finite value gives `+inf`, an untouched cell keeps its exact bits (including a NaN payload); out-of-range and negative indices are skipped: 6 of 6 pass, red on the old plan (`select` returned `Unsupported`). Not measured: sums whose partial sums are inexact (the order dependence is by design, not asserted), and throughput. The CI device run is queued, not claimed.

**GatherBackwardPlan and IndexSelectBackwardPlan, f16 and bf16.** `GatherBackwardPlan` and `IndexSelectBackwardPlan` (the adjoints of `GatherPlan` and `IndexSelectPlan`: scatter-adds of the upstream gradient into `dsrc`) now accept f16 and bf16, i32 and i64 indices (ROADMAP E3; Fuel's GAP-413). Eight new symbols, `baracuda_kernels_{gather,index_select}_backward_{f16,bf16,i64idx_f16,i64idx_bf16}_run`, instantiate the existing backward kernels on `__half` / `__nv_bfloat16`; the add is the library's compare-and-swap loop on the 32-bit word holding the 2-byte cell. As with half `ScatterAddPlan`, the ORDER of additions into one cell is undefined when indices repeat (torch's CUDA `index_add_` / `scatter_add_` atomics are order-nondeterministic too), so a half result is only as reproducible as the rounding of its partial sums; an out-of-range or negative index is skipped, the shared policy of every indexing plan (`IndexBoundsPlan` detects it). Device test `indexing_backward_half` (f16 and bf16; sm89): 200 gradient rows into 3 `dsrc` rows with exactly representable partial sums (20 runs, i32 and i64 indices) for both plans, equal to an f64 accumulation rounded once to the dtype; a NaN gradient poisons its cell only and an untouched NaN cell keeps its exact bits; out-of-range and negative indices skipped: 8 of 8 pass, red on the old plans (`select` returned `Unsupported`). Not measured: sums whose partial sums are inexact (order-dependent by design, not asserted) and throughput. The CI device run is queued, not claimed.
