kind: **BREAKING**: `UserObject` owns exactly one reference (driver and runtime): `release` takes `self`
---
Release of a user object whose last reference was already released could double-release: found by a crash at process exit in the device tests. `baracuda_driver::user_object::UserObject` and `baracuda_runtime::user_object::UserObject` now own exactly one reference, as a type-level guarantee: the handle is an `Option` that `release` and `Drop` both `take`, `release(self)` consumes the value (a second `release` does not compile, E0382), and `Drop` gives back only a reference the value still owns. Changed API (all in both crates): `UserObject::new(destroy)` loses its `initial_refcount` argument (the value owns the one initial reference); `UserObject::retain(&self, count)` and `release(&self, count)` are replaced by `duplicate(&self) -> Result<UserObject>` (another owning value) and `release(self)`; `Graph::retain_user_object(&self, object, count)` loses its `flags` argument (flags 0 only: the driver's MOVE flag hands the caller's reference to the graph, which a `UserObject` that gives its reference back in `Drop` cannot express); `Graph::release_user_object` is now `unsafe fn` (the graph's own reference count is the driver's: giving back more than the graph holds releases someone else's references). Not confirmed as the cause of the crash: no deterministic reproduction exists (the driver answered `Ok` to repeated releases of a destroyed object and 2000 repeated create/retain/release/drop-graph/drop cycles in one process survived); the code-level trace is in the PR. Verified: the `wave22_smoke` (driver) and `wave2_smoke` (runtime) device tests pass through `gpu-run` with the new shape, plus two new driver device tests (`duplicate` keeps the object alive until the last value is gone; `release` and `Drop` each give back exactly one reference), and a `compile_fail` doctest on `release` in each crate (checked by hand to fail with E0382, since stable rustdoc does not check the code).
