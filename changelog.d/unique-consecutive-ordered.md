kind: Fixed: unique_consecutive returns runs in row order with run-length counts (it was atomic-race order with counts of 1)
---
`UniqueConsecutivePlan` (`baracuda_kernels_unique_consecutive_{f32,f64,i32}_run`) numbered each run's output slot with a per-row `atomicAdd`, so the runs came back in block-race order, not row order, and wrote `counts = 1` for every run (the plan's own rustdoc said "NOT input-order" and the `return_counts` flag was "reserved"). `torch.unique_consecutive` returns the runs in order and the run LENGTHS, so any caller that used the output as that op got silently wrong order and counts. The kernel is now an ordered scan-based compaction (one block per row, a block scan per 1024-wide chunk with a carry across chunks, no atomics for slot numbering): slot k is the k-th run, `counts[k]` its length, `values[k]` its first element, and `counter[row]` the true run count (it can exceed `max_unique`; the extra runs are dropped, cells past the counter are untouched). Equality is `==`: every NaN is its own run (NaN != NaN, as torch) and `-0.0` and `+0.0` are one run. Rows of any length work (the old grid-stride loop did too; the new one keeps order across chunks). New: `i64` (`baracuda_kernels_unique_consecutive_i64_run`).

**Affected published versions** (read from the published `baracuda-kernels-sys` .crate files, not tags): 0.0.1-alpha.26 (the first published version; it already holds the atomicAdd slot assignment and `counts = 1`) through 0.1.0-alpha.210; `UniqueConsecutivePlan` is a real kernel launch in the `baracuda-kernels` .crate of alpha.26 and alpha.210 (not a stub). Reach: Fuel origin/main 0 hits for `unique_consecutive` / `UniqueConsecutive` in any file (positive control: the same checkout holds 1 `baracuda_kernels_flash_sdpa_` binding), lightbulb 0, rockfish, bonefish, vulkane, fishstringer 0. Not shown to be a vulnerability: no GitHub advisory and no RustSec advisory found.

Device test `unique_consecutive_order` (f32, f64, i32, i64; sm89; each case run 10 to 50 times to expose a slot race): run order and run lengths against a host oracle, an unsorted row, independent rows, NaN never equal and signed zeros one run, rows of 3000 and 5000 elements (runs straddling the 1024 and 2048 chunk boundaries, 2500 short runs, one run spanning three chunks), a count past `max_unique`, zero-width rows. Red on the old kernel: `f32 rep 0 row 0 slot 0: run length` was 1, expected 2. The existing `unique_consecutive_smoke` still passes. The CI device run is queued, not claimed. `UniquePlan` (sort then this dedup, ROADMAP E0b) is still a declining stub; it is wired in a follow-up that composes this kernel.
