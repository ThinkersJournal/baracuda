`baracuda-cuda-emit`, `baracuda-cuda-parse` and `baracuda-cuda-seam` move to 0.59.0 to match unpopped 0.59 (the emitter/parser exception to the one-version rule). The workspace pins `unpopped`, `unpopped-vocab`, `unpopped-convert` and (dev) `unpopped-cpu-c` to ~0.59.1; the seam crates take `fireline-grammar` / `-synth` / `-announce` ~0.10 (0.10.0 is on unpopped-vocab ~0.59: its `JitRequest` carries unpopped types) and the CUDA test dev-dependencies take `fishstringer-slang-emit` / `-parse` ~0.8 (0.8.0 is on unpopped 0.59); `seam_pin` pins fireline ~0.10. `tools/kiss-ref-diff` (a non-member with its own lockfile) moves to unpopped / unpopped-vocab ~0.59.1 too. The dependency graph holds ONE copy of `unpopped-vocab` (0.59.1) in both lockfiles; before, fireline 0.9 and fishstringer 0.7 kept a second 0.58 copy and `baracuda-cuda-seam` failed to compile with type-identity errors.

What unpopped 0.59 changes at run time (U63, behaviour only, nothing breaks at compile time): `check_kernel` / `check_module` refuse a subgroup `Collective` / `CollectiveTuple` after a `Return` under lane-dependent control (`KernelError::CollectiveAfterReturn`, a new unit variant of a `non_exhaustive` enum) and admit control built from `threadIdx.y` / `.z` when the launch states one subgroup size dividing `block.x`. No baracuda test flipped (486 tests passed, 0 failed across `baracuda-cuda-emit`, `-parse`, `-seam`, `-cuda-seam`; the previously red `backend_declines`, `fuzz`, the `convert` tests and the cuda-seam lib build are green). No `KernelError` wildcard arm exists in `crates/*/src` (grep, control: the same grep finds `KernelError` in cuda-emit tests). The emitter lowers none of the divergent-return shapes, so there is nothing to admit or refuse in baracuda's own kernels: the mmvq row guard (`row = blockIdx.x*blockDim.y + threadIdx.y; if (row >= nrows) return;` before a shuffle, block `(32, Y, 1)`) is CUDA source, not IR.
