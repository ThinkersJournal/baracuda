kind: Fixed: `TopkPlan` (and `KthvaluePlan`) returned a wrong selection when a row held a NaN, and unordered ties
---
`TopkPlan` (f32/f64, block-bitonic, `k <= 64`, `row_len <= 1024`) compared with a comparator that called a NaN "equal to everything", which is not a strict weak order, so the bitonic network could **drop a larger finite value**: `[1, NaN, 9, 2]`, `k = 2`, largest returned values `[2, NaN]` at indices `[3, 1]` (the 9 lost); under any NaN convention that is a wrong selection. Equal values also came out in no defined order (`[3,5,5,1,5,2,4,5]`, `k = 3` returned indices `[1,2,7]`). Both are fixed with one strict total order over (value, index): **NaN is the largest value** (first for `largest`, last for smallest) and **ties come out in ascending index order**, the torch.topk and Fuel CPU convention, now stated in the `TopkPlan` rustdoc and `OP-MATRIX.md`. **Affected published versions: `baracuda-kernels` and `baracuda-kernels-sys` from 0.0.1-alpha.26 (2026-05-18, the first release carrying `baracuda_topk.cuh`; the comparator is unchanged in it) through 0.1.0-alpha.186.** Rows without NaNs and with distinct values were always correct. `KthvaluePlan` (which calls `TopkPlan` with `largest = false`) shared the defect. Reach: within baracuda only `KthvaluePlan` calls `TopkPlan` (the MoE routing path `GgufMmvqBatchedPlan` only reads precomputed `topk_weights`, and the sampling kernels are separate code); an external consumer that feeds a NaN logit or score row to `TopkPlan` (Fuel binds it on CUDA) got a silently wrong index or value. Tests: `tests/topk_nan_ties.rs` (device-gated), red on alpha.186 with Fuel's two vectors and 526 of 576 random NaN/tie rows wrong.
