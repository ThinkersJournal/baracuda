kind: Added: plain mbarrier statements (MbarInit, MbarArrive, MbarWait) lower in baracuda-cuda-emit and run on sm_80+ (ROADMAP S12a-2)
---
`baracuda-cuda-emit` lowers the unpopped IR's plain `mbarrier` statements on a `Shared` allocation of 64-bit elements (`I64` in this emitter's table): `MbarInit` to `mbarrier.init.shared::cta.b64`, `MbarArrive` without a transaction count to `mbarrier.arrive.shared::cta.b64` (the sm_80 spelling, no `.sem` or `.scope`: the default release at CTA scope, the default arrival count, no `ctaMask`) and `MbarWait` to a loop of `mbarrier.test_wait.parity.shared::cta.b64` (the labels are scoped in braces so a kernel may wait more than once). The source carries an `#error` guard below sm_80 and the interface requires `mbarrier (sm_80 or newer)`. An `MbarArrive` with a transaction count (`mbarrier.arrive.expect_tx`) and `MbarCompleteTx` are refused by name; the forms ROADMAP S12 holds (an arrive with an explicit count or a `ctaMask`, an `expect_tx` multicast; pm-kernels 2026-11-27, findings not advice, not a clearance) are not built.

Measured on the device (RTX 4070, sm_89, through `gpu-run`): a kernel in which warp 0 runs a 20000-step dependent chain, stores its final value and arrives while warp 1 waits and reads it matches unpopped's oracle and the spec over 20 launches. Two mutants fail it: the wait that does not loop (device != spec) and an init count of 1 (the launch fails). Two weaker test designs did NOT catch the no-wait mutant and were replaced: a handshake through the same waits, and a spin loop the compiler could drop or move after the arrival; the data is now the chain's final value, so no reordering can hide the missing wait. The same source for sm_75 is refused by the guard. New test file `mbarrier.rs`; ROADMAP S12 records S12a-1 and S12a-2 as shipped. The CI device run is queued, not claimed.
