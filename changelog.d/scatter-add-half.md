kind: Added: ScatterAddPlan takes f16 and bf16 (a new atomic kernel family)
---
`ScatterAddPlan` (`out[..., index[..., j, ...], ...] += updates[..., j, ...]`) now accepts f16 and bf16, i32 and i64 indices (ROADMAP E3 #4; Fuel's GAP-413). Four new symbols, `baracuda_kernels_scatter_add_{f16,bf16,i64idx_f16,i64idx_bf16}_run`, instantiate the existing scatter-add kernel on `__half` / `__nv_bfloat16`; the add is the library's compare-and-swap loop on the 32-bit word that holds the 2-byte cell (`baracuda::atomic::add`), not a native half atomic. With duplicate target indices the ORDER of the additions into one cell is undefined, so a half result is only as reproducible as the rounding of its partial sums (the plan docs say so); an out-of-range or negative index is skipped, the policy of every indexing plan (`IndexBoundsPlan` detects it). Device test `scatter_add_half` (f16 and bf16; sm89): 200 updates into 3 rows with exactly representable partial sums, 20 runs each for i32 and i64 indices, equal to an f64 accumulation rounded once to the dtype; `+inf + -inf` and a NaN update give NaN, `+inf` plus a finite value gives `+inf`, an untouched cell keeps its exact bits (including a NaN payload); out-of-range and negative indices are skipped: 6 of 6 pass, red on the old plan (`select` returned `Unsupported`). Not measured: sums whose partial sums are inexact (the order dependence is by design, not asserted), and throughput. The CI device run is queued, not claimed.
