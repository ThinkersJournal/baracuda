kind: Changed: BREAKING numerics: `Max` / `Min` backward splits the gradient evenly across tied positions
---
`ReduceBackwardPlan` for `ReduceKind::Max` / `Min` gave EVERY position with `x == y` the full upstream `dy`, so a row with `k` tied maxima received `k` times the gradient it should (`[3, 3, 1]` with `dy = 4` returned `[4, 4, 0]`). It now splits `dy` evenly across the tied positions of each reduced group: `dx = dy / count`, where `count` is the number of positions with `x == y`, clamped to at least 1 (`[3, 3, 1]` returns `[2, 2, 0]`; an all-equal row of 3 returns `dy / 3` each). A row holding a NaN has no position with `x == y` (`NaN == NaN` is false), so its gradient is all zeros, as in Fuel's CPU kernel (torch computes `0/0` there and returns NaN). This is torch.amax / amin (`scale_grad_by_count`), JAX (`_reduce_chooser_jvp_rule` divides by the location counts) and Fuel's CPU `reduce_max_to_backward`. The old kernel's header called the full-gradient rule "the JAX convention"; that was wrong, JAX splits too. Rows without ties are unchanged. Affected: `baracuda-kernels` and `baracuda-kernels-sys` from 0.0.1-alpha.21 (the first tag containing `reduce_max_min_backward_fp.cu`, 2026-05-17) through 0.1.0-alpha.194; direct users of `ReduceBackwardPlan` only (Fuel does not bind it). Implementation: one block per reduced group counts the ties, then writes `dy / count` to them and 0 to the rest (O(numel), no ABI change). New `tests/reduce_max_min_backward_ties.rs` (5 device tests: f32, f64, f16, bf16 on 3-D strided groups with NaN groups, plus the examples): 5 of 5 failed before, 5 of 5 pass after.
